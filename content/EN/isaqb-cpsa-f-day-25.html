Final architecture mental model

Days 1–24 are complete. At this stage, stop accumulating isolated theory. Practice moving through one chain instead.

Context → Stakeholders → Requirements + Constraints
→ Architecture Drivers → Quality Goals → Options
→ Trade-Offs → Decisions → Views/Documentation
→ Implementation → Analysis + Conformance
→ Feedback → Evolution
Staff Engineer lensEvery strong architecture argument you will make at work walks some part of this chain out loud. The exam only tests whether you can walk it under time pressure.

Architecture driver test

Ask one question:

The question to askIf this requirement changed substantially, would our architecture likely change?

Probably not a driver

The button is blue.

Little architectural significance.

Probably a driver

Order acceptance survives a
30-minute SAP outage.

May affect communication, persistence, failure handling, runtime behavior and consistency.

TrapA measurable requirement is not automatically an architecture driver.

Quality model

Quality Attribute → Quality Requirement → Quality Scenario
→ Architecture Mechanism → Evidence

Worked example:

Attribute:   Availability
Requirement: Order acceptance >= 99.95%
Scenario:    SAP unavailable 30 min during peak load
Mechanism:   Durable local acceptance + async synchronization
Evidence:    Failure-injection test
TrapDo not jump directly from “availability” to a technology.

Coupling & cohesion

Coupling has several kinds:

source-code
runtime
data/schema
temporal
semantic
deployment
organizational/change
Key insightTwo services can compile independently and still be semantically coupled if one assumes undocumented event ordering.

Cohesion asks whether the responsibilities inside a building block belong together. High cohesion usually improves understandability, ownership, change locality and modifiability.

Pattern X = good architecture

Use instead:

View selection

Context:        What surrounds the system?
Building Block: What static software parts make it up?
Runtime:        How do parts interact in important scenarios?
Deployment:     Where does software execute?

Fast mapping:

External systems?               → Context
Internal modules?               → Building Block
What happens on payment timeout? → Runtime
Which service runs on which node? → Deployment
View ≠ notationA runtime view may use a UML sequence diagram, a C4 dynamic diagram, BPMN, plain text, or any other suitable notation.

Analysis vs conformance

Analysis / evaluation

Is the architecture suitable
for the required qualities?

Conformance

Does the implementation follow
the intended architecture?
Load/failure test           → quality analysis/evidence
Forbidden dependency check  → conformance
ShortcutAnalysis → Is it good enough? Conformance → Are we following it?

Drift vs erosion

Drift

Deviation from the
intended architecture.

Erosion

Accumulated deviations that
weaken architecture qualities.

One unauthorized direct DB access may be drift. Years of cross-service DB access forcing coordinated releases can become erosion.

TrapIntentional, documented evolution is not automatically drift.

Trade-off rule

Be suspicious when an answer claims one choice delivers:

better performance
better security
better modifiability
less complexity
lower cost

all at once.

Staff Engineer lensStrong architecture reasoning always names benefit and cost and context.

The “two plausible answers” algorithm

1. Remove unjustified absolutes such as always and never.
2. Prefer requirements before mechanisms.
3. Prefer explicit trade-off reasoning.
4. Prefer stakeholder/context-aware communication.
5. Prefer evidence over opinion.
6. Answer the exact question.

A

Add retries.

B

Clarify failure semantics and
required resilience, then select
a strategy.

B is usually the architecturally stronger answer because it preserves the chain:

Concern → Driver → Options → Trade-Off → Decision → Evidence

Final distinction drill

“The system must use the corporate Kubernetes platform.”

A. Quality requirement · B. Constraint · C. Runtime scenario · D. Metric

Answer: B.

“Under peak load, 95% of requests complete within 500 ms.”

A. Constraint · B. Quality requirement · C. Decision · D. Context view

Answer: B.

“Payment Provider is unavailable for ten minutes during peak traffic; checkout continues accepting orders with >= 99.95% availability.”

A. Quality scenario · B. Deployment rule · C. Style · D. Constraint

Answer: A.

A component contains authentication, tax, PDF generation and email templates.

A. Coupling · B. Low cohesion · C. Deployment · D. Availability

Answer: B.

Two services depend on undocumented event ordering.

A. No coupling · B. Semantic coupling · C. Only source coupling · D. Only deployment coupling

Answer: B.

“What happens when SAP times out?”

A. Context · B. Runtime · C. Deployment · D. Building Block

Answer: B.

“Where does the worker execute?”

A. Deployment · B. Context · C. Runtime only · D. Quality scenario

Answer: A.

A load test shows the latency target is missed.

A. Conformance only · B. Architecture quality analysis/evidence · C. Context documentation · D. ADR status

Answer: B.

A static test detects a forbidden dependency.

A. Conformance checking · B. Usability analysis · C. Context analysis · D. Requirements elicitation

Answer: A.

Years of unplanned cross-database access make independent deployment difficult.

A. Architecture erosion · B. Context refinement · C. Cohesion · D. Quality scenario

Answer: A.

Official mock exam strategy

The official Foundation Level example exam currently contains 38 questions and is modeled on the real exam.

First attempt:

75 minutes
No notes
No searching
Mark uncertain answers

Record answer and confidence for every question:

H = high
M = medium
L = low

Example:
Q17: B / L

Why confidence matters

It tells you what to remediate first:

1. Wrong + High confidence
2. Wrong + Medium confidence
3. Wrong + Low confidence
4. Correct + Low confidence
Key insightWrong + high confidence indicates a misconception, not simply missing recall. Those are the expensive ones.

Classify every weak answer:

A. Definition problem
B. Distinction problem
C. Scenario interpretation problem
D. Trade-off problem
E. Question-reading problem
F. Knowledge gap

Readiness target

The official pass threshold is 60% of achievable points. For practice, aim higher:

>= 80% consistently

with very few high-confidence mistakes.

Time management

Pass 1:     Answer clear questions quickly.
Pass 2:     Return to uncertain questions.
Final pass: Check NOT/EXCEPT, answer-count
            instructions, absolutes and blanks.

Staff Engineer transfer exercise

You join a platform with eight teams:

- each team has a different timeout/retry policy
- three services share a database
- architecture diagrams are outdated
- public events have undocumented semantics
- teams disagree about service boundaries
- incidents are difficult to trace
- architecture decisions happen in meetings and are forgotten
Wrong answer“Rewrite the architecture.”

Higher-leverage response:

1. Establish shared architecture drivers.
2. Expose the current architecture with lightweight views.
3. Record significant decisions with ADRs.
4. Define cross-cutting resilience, observability,
   security and interface concepts.
5. Establish guardrails.
6. Automate objective rules.
7. Build feedback loops through reviews, incidents,
   metrics and fitness functions.

Example guardrails:

All remote calls have explicit timeouts.
Public events have ownership and compatibility rules.
New direct cross-service DB access is forbidden.
Correlation IDs cross service boundaries.
Staff Engineer lensStaff-level architecture leadership means less central control, more shared clarity, more scalable constraints and more evidence.

CPSA-F → CPSA-A bridge

Foundation Level gives you a common vocabulary and disciplined architecture reasoning. Advanced Level is modular and goes deeper.

CPSA-F
→ real architecture responsibility
→ CPSA-A modules aligned with your work
→ apply them in projects
→ broaden technical, methodological and communication skills

For a Staff Engineer trajectory, useful Advanced-Level directions can include architecture evaluation, documentation, requirements for architects, architecture evolution and improvement, DDD, cloud and infrastructure, web architecture, and communication/soft skills.

Key insightChoose modules based on the responsibilities you want to grow into, not by collecting certificates randomly.

Five Staff Engineer questions

Ask these repeatedly at work:

1. What are the real architecture drivers?
2. What assumptions are hidden?
3. What trade-off are we making?
4. How will we know whether the decision works?
5. How can the architecture remain understandable
   and enforceable without me?
Staff Engineer lensThe fifth question is the one that separates Senior from Staff. The first four make a good decision; the fifth makes it survive you.

Your next study session

Do not start another large CPSA-F theory chapter. Instead:

1. Take the official iSAQB mock under timed conditions.
2. Record answer + confidence for every question.
3. Score it.
4. Classify every wrong/uncertain answer.
5. Re-study only weak areas.
6. Retest those distinctions with new scenarios.

This is now higher-value than continuing linearly through more Foundation-Level theory.
