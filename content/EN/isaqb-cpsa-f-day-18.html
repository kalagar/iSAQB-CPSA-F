Learning objectives

By the end of this lesson, you should be able to explain architecture conformance, distinguish intended from implemented architecture, recognize drift and erosion, explain code review / architecture review / tool-supported analysis, convert decisions into explicit rules, understand architecture tests and fitness functions, distinguish structural from operational checks, distinguish triggered from continuous checks, and design lightweight architecture guardrails.

Official alignmentLG 05-03 — Evaluate Conformance to Architectural Decisions (R2). Related: LG 05-01, LG 05-02.

Official CPSA-F focus

The core expectation: assess whether the implementation conforms to architecture design and architectural decisions.

The curriculum explicitly names code reviews, architecture reviews, and tool-supported analysis. Fitness functions are a practical extension that supports continuous feedback — useful, but not the wording of the learning goal.

Intended vs implemented architecture

Intended

What we designed and decided.

Implemented

What the code and runtime actually do.

Healthy architecture keeps them reasonably aligned — not identical, but not contradictory.

Architecture conformance

Conformance asks: does the implemented system obey the intended rules and decisions?

Domain must not depend on UI.
Only Payment Adapter may use the payment SDK.
Services may not read another service's database directly.
All external communication must use TLS.
All events must contain eventId and schemaVersion.

Why conformance matters

Without checks:

Design documentation
        ≠
Source code
        ≠
Runtime behavior

Consequences: stale documentation, hidden dependencies, weakened boundaries, degraded quality attributes.

Drift vs erosion

Drift

Implementation moves away from the intended design.

One service bypasses another's
API and reads its database.

Erosion

Accumulated deviations weaken architectural properties.

Many services now read
each other's databases.
Small deviations
      ↓
Repeated exceptions
      ↓
Drift
      ↓
Accumulation
      ↓
Erosion

How structural decay happens

Usually through local shortcuts:

"We only need one direct DB query."

Later:

"We already do it in one place."

Eventually:

Many services
     ↓
Shared Database

Architecture rules must be explicit

Weak: “Keep the architecture clean.”

Strong:

Domain must not depend on:
- web
- persistence implementation
- messaging implementation

Now the rule can be reviewed, tested and automated.

Decision → rule → verification

Architecture Decision
       ↓
Architecture Rule
       ↓
Verification Method
       ↓
Feedback

Example ADR: each domain module owns its persistence. Derived rule: cross-module database access is forbidden.

The three conformance methods

1 · Code review

Checks dependency direction, boundary violations, direct infrastructure access, security rules, interface contracts.

Strength: contextual judgment, catches semantic problems. Limit: manual, inconsistent, easy to miss.

2 · Architecture review

Do module boundaries still match?
Have new dependencies appeared?
Are cross-cutting concepts consistent?
Are teams bypassing interfaces?

3 · Tool-supported analysis

Dependency analysis
Static architecture analysis
Cycle detection
Forbidden-dependency checks
Code metrics

Best for objective, repeatable structural rules.

Architecture tests

assert no classes in "domain"
       depend on classes in "infrastructure"
assert payment-sdk
       is only referenced from "payment-adapter"

Architecture tests make architectural rules executable.

Layered example

domain
application
infrastructure
web
web → application
application → domain
infrastructure → domain

domain → nothing technical

Possible checks: domain may not depend on the web framework; domain may not depend on the persistence framework; web may not access repositories directly.

Exam noteArchUnit is a common Java tool, but the exam concept is tool-supported analysis, not the product name.

Microservice example

Decision: services own their data.

Intended:
Order → Order DB
Payment → Payment DB
Customer → Customer DB

Violation:
Order → Payment DB directly

Possible enforcement: DB credentials, network policy, repository review, infrastructure checks, access logs.

Guardrails vs gates

Gate

Blocks the change.

Forbidden dependency
→ build fails

Guardrail

Guides behavior and allows controlled exceptions.

Violation
→ warning
→ ADR required
Trap“All rules should block the build” is false. Reserve gates for objective, high-value, regression-prone rules.

Architecture exceptions

Better than quietly ignoring a rule:

Rule violated
        ↓
Explain why
        ↓
Assess consequence
        ↓
Record exception
        ↓
Set expiry/review condition

Fitness functions

A fitness function objectively assesses an architectural characteristic.

Structural

No domain → infrastructure
dependencies

Performance

p95 latency < 500 ms

Resilience

Recovery < 60 s

Security

No public endpoint
without authentication

Fitness function vs ordinary test

Unit test:
calculatePrice() returns 42.00

Fitness function:
No module violates allowed dependency direction.
The key questionIs the check protecting an architectural characteristic?

Structural vs operational

Structural

No cycles; domain independent of frameworks; vendor SDK only in adapters.

Operational

p95 latency; availability; failover time; queue age.

Triggered vs continuous

Triggered

Pull Request
→ CI
→ architecture dependency test

Continuous

Production
→ observability
→ p95 latency
→ threshold

Fitness-function-driven architecture

Define desired characteristic
       ↓
Define measurable fitness function
       ↓
Change architecture
       ↓
Measure
       ↓
Repeat
Goal:
Reduce Orders–Payments coupling.

Fitness function:
Payment SDK imports outside adapter = 0

Runtime conformance

Decision:
Checkout should not depend on Notification availability.

Runtime fitness function:
Given Notification unavailable,
checkout acceptance remains within SLO.

Some architecture decisions can only be validated dynamically — static analysis cannot verify every decision.

Conformance across views

  • Building Block: dependency rules.
  • Runtime: interaction and failure behavior.
  • Deployment: infrastructure placement and boundaries.
  • Context: undocumented external dependencies.

Structural decay signals

Increasing dependency cycles
Growing shared utility module
More cross-module DB access
Increasing architecture exceptions
Frequent changes across many modules
Docs contradicting code

Shared utility trap & cyclic dependencies

shared-utils
├── SecurityUtils
├── DatabaseUtils
├── PaymentHelper
└── OrderRules

At first: reuse. Later: a coupling hub.

Orders → Payments
Payments → Customers
Customers → Orders

Potential consequences: hard independent change, difficult testing, unclear ownership. Useful fitness function:

Number of module cycles = 0

Architecture rule categories

Dependency rules · technology rules · data ownership rules · communication rules · security rules · operational rules · deployment rules. Different rules require different verification mechanisms.

Avoid over-governance

Bad:
500 mandatory rules
+ manual approval for every decision

Better:
Few high-value rules
+ automation where possible
+ clear rationale
+ explicit exception process
Staff Engineer lensThe goal is high architectural integrity with low coordination overhead. Every rule you add is a tax every team pays forever — charge it only where it buys something.

What to automate

Good candidates are objective, repeated, important, cheap to check, and likely to regress.

  • no dependency cycles;
  • no cross-service DB access;
  • required event fields;
  • no forbidden package dependencies.

Common CPSA-F exam traps

  • Conformance means checking that requirements are correct. → False
  • Conformance can only be checked manually. → False
  • Code review is irrelevant. → False
  • Any deviation is automatically bad. → Too absolute
  • “Fitness function” is the exact wording of LG 05-03. → False
  • All rules should block the build. → False
  • Static analysis can verify every decision. → False
  • Documentation alone proves conformance. → False

Practical exercise

Given these rules:

1. Domain must not depend on the web framework.
2. Presentation may not access repositories directly.
3. Payment SDK only in PaymentAdapter.
4. Domain modules must not depend cyclically.
5. Customer PII must never be logged.

And these findings:

6 domain classes import the persistence framework.
3 controllers call repositories directly.
Payment SDK imported in 9 application classes.
Orders ↔ Customers form a cycle.
One production log contains customer email addresses.
  1. Classify each violation.
  2. Decide which can be statically automated.
  3. Decide which needs runtime or log analysis.
  4. Identify the greatest modularity risk.
  5. Define the architecture tests.
  6. Define a fitness function for PII logging.
  7. Decide which checks should block CI.

Review questions

What does architecture conformance evaluate?

Whether the implementation follows the intended architecture design and decisions.

Which three methods are explicitly relevant to LG 05-03?

Code reviews, architecture reviews, tool-supported analysis.

Drift vs erosion?

Drift = deviation from intent; erosion = accumulated deviation weakening architectural properties.

Why make rules explicit?

Only an explicit rule can be reviewed, tested or automated.

What is an architecture test?

An executable check of an architectural rule, typically on structure or dependencies.

What is a fitness function?

An objective assessment of an architectural characteristic.

Structural vs operational fitness functions?

Structure and dependencies vs runtime behavior such as latency, availability, recovery.

Triggered vs continuous?

Triggered runs on an event such as a pull request; continuous observes production.

Why can static analysis not validate every decision?

Some decisions are about runtime behavior and only show under real conditions.

Why is over-governance dangerous?

It raises coordination cost, slows teams and pushes work around the rules rather than through them.
