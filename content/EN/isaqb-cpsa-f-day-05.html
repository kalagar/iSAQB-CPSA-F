Requirements, Quality Attributes & Constraints

A practical, exam-oriented lesson designed to build both CPSA-F knowledge and Staff Engineer architecture skills.

Learning objectives

By the end of this lesson, you should be able to explain and apply the core ideas behind Functional vs quality vs constraints in both exam questions and real architecture discussions.

Official alignmentLG 02-02, LG 02-03, LG 02-04.

Three categories you must distinguish

Functional requirement

What the system must do: place an order, transfer money, search customers.

Quality requirement

How well it must do it: latency, availability, security, modifiability.

Constraint

What limits the solution space: Java is mandatory, PostgreSQL must be used, GDPR applies, budget is fixed.

Why qualities drive architecture

Functional requirements describe capabilities. Quality requirements frequently determine the architecture needed to deliver them.

“View balance” → little architecture information
+ 99.99% availability
+ <300ms p95 latency
+ strict authorization
= major architecture implications

Quality scenarios

Vague qualities should be made measurable.

Context → Stimulus → Response → Measurement

Example: During normal production load, if one application instance fails, traffic is routed to healthy instances and service recovers within 30 seconds without losing confirmed orders.

Quality trade-offs

Qualities interact. Security may reduce usability; availability may increase cost; performance can conflict with consistency; flexibility may increase complexity.

Common CPSA-F exam traps

  1. All requirements are functional. — Treat this as suspicious or false unless the context explicitly supports it.
  2. Constraints are just low-priority requirements. — Treat this as suspicious or false unless the context explicitly supports it.
  3. 'Highly scalable' is a sufficient quality requirement. — Treat this as suspicious or false unless the context explicitly supports it.
  4. Improving one quality cannot hurt another. — Treat this as suspicious or false unless the context explicitly supports it.

Key terms to remember

Functional requirementWhat the system must do.
Quality requirementHow well the system should behave.
ConstraintA restriction on the solution space.
Quality scenarioA measurable description using context, stimulus, response, and measurement.

Practical exercise

Classify these statements:

  1. Users can buy and sell stocks.
  2. 99.99% availability.
  3. Java 21 must be used.
  4. Order placement should feel instantaneous.
  5. EU customer data must remain in the EU.
  6. Four backend developers.
  7. 50,000 concurrent users.

Then rewrite “Order placement should feel instantaneous” as a measurable quality scenario.

Review questions

What is the difference between a quality requirement and a constraint?

A quality requirement describes a desired property; a constraint limits possible solutions.

Why is “the system should be fast” weak?

It lacks context and measurable criteria.

What are the four scenario elements used here?

Context, stimulus, response, measurement.
