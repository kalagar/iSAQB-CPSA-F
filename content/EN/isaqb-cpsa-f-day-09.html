Design Principles: Modularity, Abstraction, Coupling & Cohesion

Learning objectives

By the end of this lesson, you should be able to explain and apply the core ideas behind Modularity and dependency principles in both exam questions and real architecture discussions.

Official alignmentLG 03-04 and bridge to LG 03-06.

Abstraction

Depend on stable concepts rather than unnecessary implementation detail.

OrderService → PaymentGateway ← StripePaymentGateway

Abstraction is useful when it protects a meaningful variability or dependency—not simply because another interface is possible.

Modularization

Structure the system into coherent units with clear interfaces and hidden internal details. Core ideas include information hiding, encapsulation, separation of concerns, high cohesion, and loose but sufficient coupling.

Information hiding vs encapsulation

Information hiding

Design decision: what should clients not know?

Encapsulation

Mechanism: how is access to details restricted?

Coupling categories

  • Static: source/build dependency.
  • Dynamic: runtime dependency.
  • Afferent: who depends on me?
  • Efferent: what do I depend on?

Moving from a local call to HTTP does not automatically make a system loosely coupled.

Conceptual integrity

Similar problems should be solved consistently across the system: API naming, error handling, logging, authentication, and architectural conventions.

Common CPSA-F exam traps

  1. Good architecture eliminates all coupling. — Treat this as suspicious or false unless the context explicitly supports it.
  2. Dynamic coupling is always weaker than static coupling. — Treat this as suspicious or false unless the context explicitly supports it.
  3. More interfaces always means better architecture. — Treat this as suspicious or false unless the context explicitly supports it.
  4. Dependency inversion is the same as dependency injection. — Treat this as suspicious or false unless the context explicitly supports it.

Key terms to remember

AbstractionExpose essential concepts while hiding irrelevant details.
ModularizationDivide the system into coherent units with controlled dependencies.
CohesionHow strongly responsibilities inside a module belong together.
CouplingDegree of dependency between modules.
Dependency inversionDepend on abstractions rather than concrete low-level implementations.

Practical exercise

Review an OrderService that directly depends on PostgreSQLOrderRepository, StripeClient, CustomerDatabase, InventoryDatabase, EmailClient, and SAPClient.

  1. Assess cohesion.
  2. Identify at least three forms of coupling.
  3. Apply dependency inversion to Stripe.
  4. Identify responsibilities that should probably leave OrderService.

Review questions

What is the difference between cohesion and coupling?

Cohesion concerns relationships inside a module; coupling concerns dependencies between modules.

Is all coupling bad?

No. The goal is loose but functionally sufficient coupling.

What does dependency inversion mean?

High-level logic should depend on abstractions rather than concrete low-level implementations.
