Interfaces, Architecture Decisions & ADRs

An interface is a contract, not a signature — and a decision without rationale is a decision nobody can safely revisit. Document both the way a Staff Engineer would.

Learning objectives

By the end of this lesson, you should be able to explain what belongs in interface documentation, distinguish internal from external interfaces, separate contracts from implementation details, explain why architecture decisions need rationale, describe ADR purpose and structure, identify dependencies between decisions, and use ADRs as a Staff Engineer tool.

Official alignmentLG 04-06 — Document Interfaces (R1). LG 04-08 — Explain and Document Architectural Decisions (R1–R2).

Interface as an architectural contract

An interface is more than a method signature.

Building Block A
      |
      | Interface Contract
      v
Building Block B

Useful contracts may include semantics, input constraints, output guarantees, error behavior, timing expectations, security, idempotency, versioning, and pre-/postconditions.

Example: payment interface

Purpose:
Authorize and capture a payment.

Request:
POST /payments

Required:
orderId
amount
currency
paymentMethodToken

Errors:
409 PAYMENT_ALREADY_PROCESSED
422 PAYMENT_DECLINED
503 PAYMENT_PROVIDER_UNAVAILABLE

Idempotency:
Idempotency-Key required

Security:
OAuth2 service identity

Everything above is architecturally relevant: each line changes how a consumer must be built.

Internal vs external interfaces

Internal

Between building blocks inside the system.

External

Crosses the system boundary.

External interfaces often need stronger versioning, compatibility, SLA and security documentation — but “only external interfaces need documentation” is false.

Provided vs required interfaces

Order Service

Provides:
Order API

Requires:
Payment API
Inventory API

This makes dependencies explicit and turns an implicit call graph into something a reviewer can reason about.

Semantic coupling

Stable syntax does not guarantee low coupling.

{"status":"READY"}

If the meaning of READY is undocumented, consumers are coupled to assumptions rather than to a contract. The payload never changes — but the shared understanding silently does.

Versioning and compatibility

  • backward-compatible extension;
  • explicit API versions;
  • event schema evolution;
  • deprecation policy;
  • compatibility testing.

Staff Engineer interface questions

Who owns it?
Who consumes it?
What is guaranteed?
What can fail?
How does it evolve?
Is it idempotent?
What is the timeout?
How is it secured?
How is compatibility validated?
Staff Engineer lensThese nine questions are a review checklist. An interface that cannot answer them will be answered later by an incident.

What is an architectural decision?

A decision with significant consequences for structure, quality attributes, dependencies, technology, future evolution, or cost of change.

Use Kafka for order events.
Use PostgreSQL for transactions.
Use a modular monolith instead of microservices.
Use OIDC for authentication.

Architectural significance

High impact?
Hard to reverse?
Affects multiple teams?
Influences quality requirements?
Constrains future choices?

If several answers are yes, the decision is probably architectural.

Why document decisions?

Without rationale, future engineers know what exists but not why.

Decision:
Use PostgreSQL.

Reason:
- strong consistency
- relational reporting
- existing operational expertise

Exam noteNo single ADR template is mandatory for CPSA-F. What matters is that context, rationale and consequences are preserved.

Example ADR

# ADR-017: Asynchronous Order-to-SAP Integration

Status:
Accepted

Context:
SAP outages must not block order acceptance.

Drivers:
Availability
Durability
Throughput

Options:
1. Direct REST
2. Database queue
3. Kafka

Decision:
Publish accepted orders to Kafka.

Positive:
+ decouples order acceptance from SAP
+ buffers bursts

Negative:
- eventual consistency
- duplicate handling
- operational complexity

Validation:
- throughput test
- broker failure test
- SAP outage simulation

ADR status

Proposed
Accepted
Rejected
Deprecated
Superseded

Do not silently rewrite architectural history. Supersede old decisions explicitly so the reasoning chain stays readable.

Decision interdependencies

Use async events
      ↓
Need idempotent consumers
      ↓
Need event identifiers
      ↓
Need schema versioning

Architecture decisions form a graph, not a list.

When not to write an ADR

Do not create ADRs for minor implementation details. Good ADR candidates are high-impact, hard to reverse, cross-team, quality-relevant, and likely to be questioned later.

ADRs are not meeting minutes

Meeting minutes capture conversation. ADRs capture architectural knowledge:

Context
Drivers
Options
Decision
Rationale
Consequences

ADRs and feedback loops

Assumption:
Kafka can sustain 20k orders/min.

Validation:
Representative load test.

Review:
Before production launch.

An ADR that names its assumptions and how they will be validated turns a guess into a managed risk.

Interface documentation + ADRs

ADR

Explains why — why asynchronous messaging, why Kafka.

Interface contract

Explains how — topic, schema, semantics, ordering, idempotency, versioning.

Common CPSA-F exam traps

  • Interface documentation means only method signatures. → False
  • Only external interfaces need documentation. → False
  • Every technical decision deserves an ADR. → False
  • ADRs contain only the final decision. → False
  • Architecture decisions are independent. → False
  • One mandatory ADR template exists. → False

Practical exercise

For a Fraud Service:

  1. Define purpose, inputs, outputs, errors, timeout, retry, idempotency, versioning and security.
  2. Compare synchronous REST vs asynchronous messaging vs a local cache.
  3. Write a short ADR for your choice.
  4. Identify three decisions that depend on it.

Review questions

What does LG 04-06 require?

That interfaces are documented as contracts — not only as syntax.

Why is a method signature insufficient?

It omits semantics, errors, timing, security, idempotency and evolution rules.

Provided vs required interface?

Provided = capability offered; required = capability depended upon.

What makes a decision architecturally significant?

High impact, hard reversal, cross-team consequences, quality influence, or future constraints.

Why preserve rationale?

So future engineers know why the decision made sense in its context.

What is an ADR?

A documented record of an architectural decision, its context, rationale and consequences.

Name five ADR fields.

Title, status, context, decision, consequences.

Why preserve superseded ADRs?

They preserve the reasoning history and prevent repeating rejected options.

Why do decision dependencies matter?

One decision creates obligations for others; decisions form a graph.

How do ADRs differ from meeting minutes?

Minutes record conversation; ADRs record architectural knowledge.
