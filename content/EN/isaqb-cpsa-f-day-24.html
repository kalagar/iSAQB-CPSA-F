The core exam skill

Days 1–23 are complete. Today is the last theory-driven remediation: when several answers seem plausible, the exam is testing a reasoning procedure, not a definition.

1. What concept is actually being tested?
2. What are the architecture drivers?
3. What constraints apply?
4. Which answer addresses the concern most directly?
5. Which makes fewer unsupported assumptions?
6. Which avoids unjustified absolutes?

Prefer the reasoning chain:

Concern → Driver → Options → Trade-off → Decision → Evidence
Staff Engineer lensThis is not an exam trick. It is exactly how a credible architecture review is argued in front of teams who disagree.

Architecture driver — significance test

R1

Users can sort claims by date.

Feature-level. Architecture is unlikely to change.

R2

Claims remain available when
Fraud Provider fails.

Can alter runtime interaction, failure handling, persistence, communication, timeout/retry policy and consistency.

Useful test:

The question to askIf this requirement changed substantially, would our architecture likely change? If yes, it is probably an architecture driver.
TrapMeasurable does not automatically mean architecturally significant.

Quality attribute vs requirement vs scenario

Attribute

Availability

Requirement

Checkout availability >= 99.95%.

Scenario:

Source:      Payment provider
Stimulus:    Provider unavailable
Environment: Peak traffic
Artifact:    Checkout
Response:    Orders follow defined fallback behavior
Measure:     Availability remains >= 99.95%
ShortcutAttribute = category. Requirement = desired level. Scenario = concrete evaluable situation.

Constraint vs decision

Constraint

Customer data must remain
in Germany.

Decision

Deploy customer-data workloads
in two German cloud regions.

The same technology can be either:

As constraint

Company policy mandates
PostgreSQL.

As decision

Alternatives were evaluated and
PostgreSQL was selected.
ShortcutThe difference is why the choice is fixed — imposed on you, or chosen by you.

Interface syntax vs semantics

Event:

claimId: string
status:  APPROVED

Syntax describes fields, types, schema and serialization. Semantics answers:

What exactly does APPROVED mean?
Can it later change?
Can delivery duplicate?
Does ordering matter?
When is the event final?
ShortcutStable interfaces require shared meaning, not merely compatible JSON.

Semantic coupling

Service B assumes:

CustomerUpdated always arrives
before InvoiceCreated.

No contract guarantees it. This is semantic / behavioral coupling through an undocumented ordering assumption.

TrapChanging REST to Kafka does not remove it. Transport is not the coupling — the assumption is.

Cohesion and change locality

If adding one document vendor changes Claims, Billing, Customer, Notification and Reporting, predictable change is poorly localized.

Document Port
     ↓
Vendor A Adapter
Vendor B Adapter
The pointThe goal is not “more interfaces.” The goal is localizing related change.

Reasoning applied to a specific context.

Architecture views — hard mapping

QuestionView
Which external systems participate?Context
What internal software parts exist?Building Block
What happens when Fraud times out?Runtime
Where is Fraud Adapter deployed?Deployment
ShortcutA view is a stakeholder-oriented architectural perspective. A diagram is only one possible representation of it.

Decision, rationale, consequence

Decision:
Use durable asynchronous SAP synchronization.

Rationale:
Order acceptance must survive SAP outages and
delayed sync is acceptable.

Positive consequence:
Temporal decoupling.

Negative consequence:
Eventual consistency and duplicate handling.

These are different pieces of architectural knowledge — an exam option that merges them is usually the weaker answer.

ADR evolution

Proposed → Accepted → Deprecated/Superseded
Why it mattersWhen a decision changes, preserve history rather than silently rewriting the old rationale. The superseded record explains why the system looks the way it does today.

Analysis vs validation vs conformance

Analysis:
Will the architecture satisfy required qualities?

Validation:
Does observed evidence support our assumptions?

Conformance:
Does implementation follow intended architecture?

Examples:

Analyze synchronous Fraud dependency  → analysis
Inject Fraud outage                   → validation/evidence
Check domain cannot import vendor SDK → conformance

Qualitative vs quantitative analysis

Qualitative

Scenario walkthrough indicates
shared DB creates change coupling.

Quantitative

p95 = 1.4 s
Availability = 99.7%
17 classes import Vendor SDK
TrapQuantitative evidence is not automatically superior; a precise number can measure the wrong thing.

The metric trap

Component X has 18 dependencies.

Correct chain:

Metric → Signal → Contextual interpretation → Possible action

Not:

Metric → Automatic verdict

Drift, evolution and erosion

  • Intentional evolution changes architecture intent through an explicit decision.
  • Drift is divergence between implementation and current architecture intent.
  • Erosion is accumulated harmful drift that degrades architecture properties.
One unauthorized direct DB access → drift

Years of cross-DB access causing
coordinated releases             → erosion

Architecture rule vs fitness function

Rule + check

Only document adapters may
import vendor SDK.

Check: CI dependency test.

Runtime fitness function

During simulated downstream outage,
claim acceptance remains above
target.
ShortcutFitness functions can evaluate runtime architecture characteristics, not only static dependencies.

Hard “two answers look correct” drills

Requirement p95 < 500 ms, observed p95 = 900 ms. What now?

A. Replace PostgreSQL immediately · B. Requirement is violated; analyze contributors before selecting a remedy · C. Add Redis · D. Split into microservices

Answer: B. Evidence identifies the problem, not its root cause.

Fraud API takes 15 seconds; the user target is < 2 seconds. First question?

A. Which queue? · B. Can fraud evaluation complete after durable claim acceptance? · C. Kafka or RabbitMQ? · D. How many replicas?

Answer: B. Business semantics precede mechanism.

Twenty classes import a vendor SDK and a new vendor is planned. Which quality dominates?

A. Performance · B. Change localization / modifiability · C. Accessibility · D. UI consistency

Answer: B.

The organization mandates Java 21. Which statement holds?

A. Java 21 is automatically optimal · B. Java 21 is a constraint even if architects would otherwise choose it · C. It is a quality requirement · D. It is a runtime view

Answer: B. What makes it a constraint is that the choice is imposed, not its quality.

A Product Owner needs the system boundary and neighboring systems. What do you produce?

A. Detailed class diagram · B. Stakeholder-tailored context view · C. Kubernetes manifests · D. DDL

Answer: B.

An ADR says: Decision: Kafka. Reason: Kafka is scalable. Main weakness?

A. ADRs cannot name technology · B. Rationale is insufficiently tied to drivers, alternatives and consequences · C. Kafka cannot scale · D. An ADR needs source code

Answer: B.

Teams use different retry policies. What is the right cross-cutting concept?

A. Same retry count for every operation · B. Shared principles for eligible failures, limits, backoff, idempotency and exceptions · C. Disable all retries · D. Developer choice only

Answer: B.

Rule: Domain → Infrastructure forbidden. The build detects a violation. What is it?

A. Quality scenario failure · B. Conformance violation · C. Context-view problem · D. Requirement conflict

Answer: B.

Which statement about pattern selection is defensible?

A. Event-driven is best for scalable systems · B. Layered is always easiest · C. Evaluate patterns against drivers and consequences · D. Microservices maximize modifiability

Answer: C. The other three are unjustified absolutes.

Five teams repeatedly make incompatible architecture decisions. Staff Engineer response?

A. Personally approve every PR · B. Establish shared drivers, decision records, principles, review mechanisms and automated guardrails · C. Put all code in one team · D. Ban local decisions

Answer: B. Leverage scales; personal review does not.

Suggested solution

Drivers

D1. User-facing p95 < 2 seconds
D2. Zero loss of accepted transactions
D3. SOAP retirement within two years
D4. Different consistency semantics by operation
D5. Independent team delivery
D6. Operability of async flows

Risks

R1. Slow SOAP violates latency.
R2. SOAP types across 23 classes increase migration cost.
R3. Inconsistent retries create duplicate effects/retry storms.
R4. Async flows are hard to troubleshoot.
R5. Making immediate-confirmation operations async
    may violate semantics.

Assumptions to validate

A1. Which operations can legally/business-wise
    complete asynchronously?
A2. Can external operations be idempotent?
A3. Can persistence/queue meet no-loss requirements?
A4. Is 15-minute sync acceptable to all consumers?
A5. Can correlation IDs propagate across SOAP/REST/Kafka?

Decisions and their costs

1 — Legacy integration boundary

Create a domain-oriented
integration port.
Keep SOAP-generated types
inside legacy adapters.

Benefits: migration locality, reduced vendor coupling, easier REST transition.

Costs: migration effort, mapping code, extra abstraction.

2 — Selective asynchrony

Use durable async
synchronization only where
business semantics allow
delayed confirmation.

Benefits: protected latency, temporal decoupling, failure buffering.

Costs: eventual consistency, duplicate/retry handling, harder observability.

3 — Shared resilience concept

timeouts
retry eligibility
retry limits
backoff/jitter
idempotency
circuit-breaking criteria
metrics

Benefits: consistent failure behavior, reduced retry storms, easier operations.

Cost: governance and managed exceptions.

Quality scenarios

Performance

Source:      Interactive user
Stimulus:    Submit operation
             whose external sync
             may be delayed
Environment: Peak load
Artifact:    Application +
             integration subsystem
Response:    Persist transaction
             and acknowledge
             without slow SOAP
Measure:     p95 < 2 seconds

Reliability

Source:      SOAP provider
Stimulus:    Provider unavailable
             30 minutes
Environment: Production
Artifact:    Delayed-sync workflow
Response:    Accepted transactions
             remain durable and
             retry per policy
Measure:     0 accepted
             transactions lost

Architecture rules

1. SOAP-generated types only inside legacy adapters.
2. Every outbound remote call defines a timeout.
3. Retries only for classified transient failures
   and are bounded.
4. Async messages carry correlation IDs.
5. Domain code cannot depend on vendor/transport classes.

Runtime fitness function

Nightly:

1. Disable SOAP provider in test.
2. Submit 1,000 delayed-sync transactions.
3. Verify user-facing p95 < 2 s.
4. Restore provider.
5. Verify all accepted transactions synchronize.
6. Verify duplicate business effects = 0.

This evaluates performance, resilience, durability and recovery together.

Review questions

Best test for architecture significance?

Ask whether changing it would materially alter architecture.

Quality attribute vs requirement vs scenario?

Category vs desired level vs evaluable scenario.

Constraint vs decision?

Restriction vs selected solution.

Interface syntax vs semantics?

Format vs meaning/behavior.

Example of semantic coupling?

An undocumented event-order dependency.

What does change locality reveal?

Whether predictable changes are localized.

Pattern vs decision?

Reusable knowledge vs context-specific choice.

Which view explains timeout interaction?

Runtime.

Which view maps software to infrastructure?

Deployment.

View vs diagram?

Perspective vs one representation.

Decision vs rationale vs consequence?

Choice vs why vs resulting effects.

Why preserve superseded ADRs?

To preserve architectural history and reasoning.

Analysis vs conformance?

Meets goals vs follows intent.

Qualitative vs quantitative analysis?

Reasoned judgment vs numerical evidence.

Why is a metric not a verdict?

Context determines significance.

Drift vs intentional evolution?

Evolution changes intent; drift diverges from intent.

Drift vs erosion?

Deviation vs accumulated degradation.

Rule vs runtime fitness function?

Structural rule vs executable ongoing quality evaluation.

When two answers look correct, which reasoning chain helps?

Concern → Driver → Options → Trade-off → Decision → Evidence.

What makes Staff-level architecture leadership scalable?

Shared drivers, decisions, principles, guardrails, automation and feedback.
