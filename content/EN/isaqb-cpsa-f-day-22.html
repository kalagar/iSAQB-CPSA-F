Core decision model

Architecture rarely has one universally correct solution. Every choice is evaluated relative to requirements, constraints, drivers, risks, assumptions and context.

Need → Architecture Driver → Options → Quality Consequences
     → Trade-Off → Decision → Validation → Feedback

Applied to a concrete case:

Need:       Checkout survives SAP outages.
Driver:     Availability.
Option A:   synchronous SAP call.
Option B:   durable asynchronous integration.
Decision:   B.
Benefits:   temporal decoupling, availability.
Costs:      eventual consistency, duplicates, operations.
Validation: simulate a 30-minute SAP outage.
Exam pointA decision is incomplete if its consequences and rationale are ignored.

Prioritize quality attributes

Suppose a system's stakeholders agree on this ranking:

Availability:   critical
Security:       critical
Modifiability:  important
Performance:    important
Portability:    low priority

Good architecture does not maximize every quality. Qualities frequently conflict, so stakeholder priorities — not engineering preference — decide which one wins.

Caching trade-off

Benefits

+ latency
+ read scalability
+ lower database load

Costs

- stale data
- invalidation complexity
- extra operations
- harder debugging

Caching is appropriate only when these consequences fit the drivers.

Asynchronous messaging trade-off

Benefits

+ temporal decoupling
+ buffering
+ failure isolation
+ potentially better availability

Costs

- eventual consistency
- duplicate processing
- ordering issues
- tracing difficulty
- operational complexity
TrapAsynchronous communication does not automatically mean loose coupling. Event semantics can create strong semantic coupling.

Shared database trade-off

Benefits

+ easy joins
+ simple transactions
+ low initial integration effort

Costs

- schema coupling
- ownership ambiguity
- coordinated changes
- harder independent evolution

The question is not “Are shared databases bad?” but whether they conflict with this system's drivers.

Scenario — SAP integration

Requirements:

Order acceptance availability >= 99.95%
SAP unavailable ~20 minutes/week
Confirmation < 1 second
SAP sync may be delayed 10 minutes
No accepted order may be lost

Option A

Order Service → synchronous REST → SAP

Option B

Order Service → Persist Order
  → Durable Queue → SAP Worker → SAP

Dominant drivers: availability, latency, durability.

B is likely stronger because delayed synchronization is explicitly acceptable. Its costs are real: eventual consistency, queue operations, duplicate and recovery handling.

Scenario — payment provider replaceability

Current coupling:

Checkout
├── Vendor SDK
├── Vendor DTOs
├── Vendor Exceptions
└── Vendor Webhooks

Requirement: add a second provider within five developer-days.

Checkout → Payment Port → Provider Adapter
Staff Engineer viewThe abstraction has a cost, but modifiability is now an architecture driver. Abstraction is justified when the expected variation is significant enough.

Scenario — monolith vs microservices

Context:

12 developers
One product
Moderate load
Deployment every 2 weeks
Strong transactions
Small operations team

Before choosing microservices, ask:

  • Which components need independent deployment?
  • Which need independent scaling?
  • Are team boundaries causing coordination problems?
  • Is fault isolation a major driver?
  • Can operations support distributed systems?

Potential benefits

+ deployment autonomy
+ independent scaling
+ ownership boundaries

Costs

- network failure
- distributed tracing
- consistency complexity
- operational overhead
TrapMicroservices are not inherently “better architecture.”

Strong consistency vs availability

Inventory requirements:

Never sell the last item twice.
Checkout should survive network partitions.

These conflict. The architectural work is asking:

Which requirement dominates?
Can reservation be temporary?
Can overselling be compensated?
What is the business cost of rejection vs inconsistency?

Architecture cannot resolve conflicting priorities without stakeholder input.

Security vs usability

Re-authenticating every admin action may improve security but damage usability. Step-up authentication for high-risk operations only is often the better trade-off.

Even security architecture contains trade-offs.

Logging vs privacy

Operations wants full request bodies; privacy forbids exposing personal data. A cross-cutting concept reconciles both:

Structured logging
Correlation IDs
PII redaction
Field allowlists
Separate protected audit logs

Evidence beats opinion

Useful architecture evidence:

  • load tests;
  • failure injection;
  • prototypes;
  • production telemetry;
  • architecture metrics;
  • incident history;
  • security analysis;
  • change history.

Weak

Kafka will scale.

Stronger

Representative tests show the event
pipeline handles 3× expected peak load
within the latency target.

Assumption → experiment

Assumption:
PostgreSQL handles 8,000 writes/sec.

Experiment:
Production-like schema, indexes, transactions and workload.

Success criterion:
p95 write latency < 100 ms at 8,000 writes/sec.

This converts opinion into feedback.

Reversibility

More reversible

Internal library
Local implementation pattern
Monitoring dashboard

Less reversible

Public API
Data partitioning
External event contract
Widely consumed service boundary

Useful heuristic:

Impact × Uncertainty × Reversal Cost

High values deserve deeper analysis and earlier validation.

Architects should make these consequences explicit instead of arguing from engineering preference.

Standardization vs team autonomy

Six teams choose different retry, logging, tracing and authentication approaches. Maximum autonomy improves local flexibility but may reduce operability, consistency, security and knowledge sharing.

Staff-level architecture often uses guardrails:

Required outcomes:
- trace ID propagated
- sensitive fields excluded
- retries bounded
- auth claims validated

Implementation:
teams retain controlled freedom

Guardrail vs prescription

Prescription

Every service must use
Library X version Y.

Guardrail

Every outbound HTTP call must:
- have a timeout;
- use bounded retries only for
  eligible failures;
- emit latency/error metrics.

Guardrails protect architecture qualities while preserving implementation flexibility.

Decision → rule → verification

Decision:     Domain logic remains framework-independent.
Rule:         Domain packages cannot import Spring, JPA
              or infrastructure.
Verification: Architecture test in CI.

The full chain:

Driver → Decision → Rule → Verification → Feedback

Exam traps

“Always use async messaging to reduce coupling.”False. It introduces other forms of complexity and semantic coupling.
Technology before requirementWeak. Prefer requirements → drivers → options → choice.
One metric = verdictFalse. 18 dependencies is a signal requiring context.
No trade-offBe suspicious when an option supposedly improves every quality while reducing every cost.

Practical exercise — legacy integration

System:

Angular Frontend
Spring Boot Backend
PostgreSQL
External SOAP System
New REST API
Batch Processing

Requirements:

R1. Existing SOAP consumers work for 18 months.
R2. New consumers use REST.
R3. Peak load triples.
R4. SOAP system sometimes takes 15 seconds.
R5. User-facing requests complete < 2 seconds.
R6. Data must not be lost.
R7. SOAP-specific code should gradually disappear.

Your task:

  1. Identify the top four architecture drivers.
  2. Compare: backend → SOAP synchronously; backend → REST facade → SOAP synchronously; backend → durable async integration → SOAP.
  3. Compare availability, latency, modifiability, consistency, operations and migration effort.
  4. Draft one ADR.
  5. Define one measurable quality scenario.
  6. Define one automated architecture rule.
Show possible reasoning

Likely drivers:

User latency < 2 seconds
SOAP compatibility for 18 months
No data loss
Gradual SOAP removal / modifiability

Candidate decision:

Introduce a stable internal integration boundary.
Use async processing where immediate SOAP
confirmation is not semantically required.
Isolate legacy adapters.

Benefits: legacy isolation, protected user latency, migration path.
Costs: eventual consistency, more operations, migration complexity.

Important: if immediate SOAP confirmation is functionally required, asynchronous processing may be invalid.

Review questions

Why is there rarely a universally best architecture?

Choices depend on requirements, constraints, drivers, risks, assumptions and context.

What should precede technology selection?

Clarifying requirements and drivers.

Why can async communication improve availability?

It can remove temporal dependence on downstream availability.

What problems can async communication introduce?

Eventual consistency, duplicates, ordering, tracing, operations.

Why is a shared database not automatically wrong?

Strong transactions and simplicity may outweigh its coupling costs in some contexts.

When is abstraction architecturally justified?

When expected variation or another driver justifies its cost.

Why prioritize quality attributes?

Qualities conflict.

What is the purpose of a decision matrix?

To expose priorities and consequences, not to mathematically prove a decision.

Why validate hard-to-reverse decisions early?

Mistakes are expensive to reverse.

Assumption vs evidence?

An assumption is unverified belief; evidence supports or refutes it.

Name three forms of architecture evidence.

Load tests, prototypes, telemetry, failure injection, incident history.

How can microservices reduce and increase coupling?

They can reduce deployment and source coupling while increasing network and semantic coupling.

What is a guardrail?

A rule protecting architecture qualities while preserving some implementation freedom.

Why must metrics be interpreted contextually?

A number alone does not establish architectural appropriateness.

How does a Staff Engineer scale architecture decision-making?

Clarify drivers, facilitate decisions, document rationale, create guardrails and feedback.

Mini scenario exam

Q1. Immediate transactional consistency is critical and traffic is low.

  1. Kafka is always preferable
  2. A synchronous transactional design may be appropriate depending on other drivers
  3. Microservices are mandatory
  4. Eventual consistency is always superior
Show answer

B — “always” answers ignore drivers and context.

Q2. A vendor must be replaceable yearly. Which quality is particularly relevant?

  1. Modifiability
  2. Usability
  3. Accessibility
  4. Visual consistency
Show answer

A — planned replacement is a modifiability driver.

Q3. Which is the strongest architecture argument?

  1. Everyone uses Kubernetes
  2. I prefer Kafka
  3. This option meets availability but introduces eventual consistency, which the business accepts
  4. This is a best practice
Show answer

C — it names driver, consequence and stakeholder acceptance.

Q4. Which deserves the most early validation?

  1. Variable naming
  2. Public event schema consumed by 30 teams
  3. IDE theme
  4. Unit-test naming
Show answer

B — high impact and high reversal cost.

Q5. A performance test contradicts an assumption.

  1. Ignore it
  2. Reassess the assumption and the affected decision
  3. Remove the requirement
  4. Freeze documentation
Show answer

B — evidence feeds back into decisions.

Q6. Independent services rely on undocumented event ordering. What coupling remains?

  1. None
  2. Semantic coupling
  3. Only source coupling
  4. UI coupling
Show answer

B — shared implicit meaning is semantic coupling.

Q7. Architecture trade-offs:

  1. Good architects eliminate them
  2. They prove bad architecture
  3. Make them explicit relative to priorities and context
  4. Only performance has trade-offs
Show answer

C — trade-offs are made explicit, not removed.

Q8. Which is the best guardrail?

  1. Identical variable naming
  2. All external calls have bounded timeouts
  3. Exactly ten lines per method
  4. Same number of classes per service
Show answer

B — it protects a quality while leaving implementation free.
