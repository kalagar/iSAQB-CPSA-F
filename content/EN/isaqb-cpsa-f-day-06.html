Explicit Assumptions, Quality Scenarios & Architecture Drivers

A practical, exam-oriented lesson designed to build both CPSA-F knowledge and Staff Engineer architecture skills.

Learning objectives

By the end of this lesson, you should be able to explain and apply the core ideas behind Assumptions, metrics, drivers in both exam questions and real architecture discussions.

Official alignmentLG 02-04, LG 02-05 and bridge to LG 03-01.

Make assumptions explicit

Implicit assumptions create architecture risk because stakeholders may not know the design depends on them.

Assumption A-01
The API will initially serve fewer than 1,000 requests/minute.
If this changes, scalability requirements must be reassessed.

Quality requirements need analysis methods

A measurable target becomes much more useful when you also define how to verify it.

  • Performance → load test and p95 latency measurement.
  • Security → review, automated authorization tests, penetration testing.
  • Availability → failover test and recovery-time measurement.

Goodhart's Law

Exam conceptWhen a metric becomes a target, teams may optimize the number instead of the underlying goal. Always ask whether the metric truly represents the quality you care about.

Architecture drivers

An architecture driver is a requirement, quality, concern, or constraint with significant structural impact.

Requirement → Architecture driver → Decision → Improved quality → Trade-offs

Common CPSA-F exam traps

  1. Assumptions do not need documentation. — Treat this as suspicious or false unless the context explicitly supports it.
  2. Every metric is automatically useful. — Treat this as suspicious or false unless the context explicitly supports it.
  3. Every requirement has equal architectural impact. — Treat this as suspicious or false unless the context explicitly supports it.
  4. Architecture decisions only improve qualities and introduce no trade-offs. — Treat this as suspicious or false unless the context explicitly supports it.

Key terms to remember

AssumptionA belief about context or environment that may be unverified.
Architecture driverA requirement, quality, concern, or constraint with strong architectural impact.
Analysis methodA way to verify whether a quality target is met.
Goodhart's LawA warning that optimizing a metric can distort the real objective.

Practical exercise

Payment platform statements:

  1. Traffic will probably never exceed 1,000 TPS.
  2. Payments must never be lost after confirmation.
  3. The platform should be very fast.
  4. Java 21 is mandatory.
  5. The payment provider is usually available.
  6. 99.99% availability.
  7. Developers want independent deployment.

Classify each as requirement, quality requirement, constraint, or assumption. Then choose the three strongest architecture drivers.

Review questions

Why should assumptions be explicit?

Because hidden assumptions create misunderstandings and architectural risk.

What is an architecture driver?

A requirement, concern, quality, or constraint with major influence on architecture.

What does Goodhart's Law warn about?

Optimizing a metric can distort the real objective the metric was supposed to represent.
