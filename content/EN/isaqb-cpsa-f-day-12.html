Learning objectives

By the end of this lesson, you should be able to explain and apply Layers, Pipes and Filters, and Microservices, connect each pattern to quality requirements, compare their trade-offs, and reason about pattern selection at a Staff Engineer level.

Official alignmentLG 03-08 — Describe, Explain and Apply Important Architectural Patterns. Exam priority: R1 for Layers, Pipes and Filters, and Microservices.

Architectural patterns

An architectural pattern is a reusable approach to a recurring architectural problem in a particular context. A pattern is not just a diagram — it describes a recurring problem, a structural solution idea, responsibilities, interactions, and consequences.

Problem + Context + Quality Goals
             ↓
       Architectural Pattern
             ↓
Structure + Responsibilities + Interaction Rules
             ↓
Benefits + Consequences + Trade-offs
Staff Engineer lensDo not ask “Which architecture pattern is best?” Ask “Which pattern best supports our architecture drivers with acceptable trade-offs?”

Layered architecture

The Layers pattern organizes a system into ordered groups of responsibilities.

┌─────────────────────────┐
│ Presentation Layer      │
├─────────────────────────┤
│ Application Layer       │
├─────────────────────────┤
│ Domain / Business Layer │
├─────────────────────────┤
│ Infrastructure Layer    │
└─────────────────────────┘

Typical responsibilities: Presentation — controllers, APIs, request/response handling. Application — use-case orchestration and transaction boundaries. Domain — business rules and domain concepts. Infrastructure — databases, messaging, external APIs.

Potential benefits

Maintainability, understandability, separation of concerns, testability, replaceability of technical mechanisms.

Possible trade-offs

Extra abstractions, mapping code, indirection, pass-through layers, possible performance overhead.

Layer vs tier

A layer is mainly a logical structure. A tier normally refers to deployment separation. A three-tier deployment can still contain many logical layers.

Browser
   ↓
Application Server
   ↓
Database Server

Pipes and Filters

The Pipes and Filters pattern organizes processing into independent transformation stages. Each filter performs a transformation; each pipe carries data between filters.

Raw XML
   ↓
Parse
   ↓
Validate
   ↓
Normalize
   ↓
Enrich
   ↓
Persist

Potential strengths

Composability, testability, reuse, incremental processing, parallelism, separation of transformations.

Possible trade-offs

Serialization overhead, state-management difficulty, debugging across stages, error-handling complexity, latency.

If Filter 4 fails after Filters 1–3 succeed, you may need retries, idempotency, checkpoints, dead-letter handling, and compensation.

Microservices

A Microservices architecture decomposes a system into focused, independently deployable services.

                    ┌──────────────┐
                    │ API Gateway  │
                    └──────┬───────┘
                           │
         ┌─────────────────┼─────────────────┐
         ↓                 ↓                 ↓
   Order Service     Customer Service   Payment Service
         │                 │                 │
     Order DB          Customer DB        Payment DB

Potential benefits: independent deployability, selective scaling, team autonomy, evolvability, fault isolation.

Important warningMicroservices do not automatically mean loose coupling. If all services must be available simultaneously, temporal coupling may still be strong — data, semantic, version, and operational coupling can all remain.
Order Service
   ↓ HTTP
Customer Service
   ↓ HTTP
Inventory Service
   ↓ HTTP
Payment Service

Distributed-system costs

Microservices introduce concerns such as network failures, latency, retries, duplicate messages, distributed tracing, service discovery, eventual consistency, inter-service authentication, API compatibility, and deployment orchestration.

A local call:

paymentService.pay(order);

becomes a remote interaction where you must consider:

Timeout?
Retry?
Authentication?
Network failure?
Duplicate request?
Version mismatch?
Partial success?

Microservices vs modular monolith

Modular monolith

May fit well when the team is small, operational simplicity matters, independent scaling is not yet needed, strong consistency is valuable, or boundaries are still evolving.

Microservices

May be attractive when teams need independent delivery, components have different scaling characteristics, fault isolation matters, domain boundaries are mature, or operations capability is strong.

Neither is universally better.

Comparing the three R1 patterns

PatternCore ideaTypical strengthsTypical trade-offs
LayersOrganize responsibilities by abstraction/purposeMaintainability, understandability, separation of concernsIndirection, pass-through layers
Pipes & FiltersProcess data through independent stagesReuse, testability, composabilityError handling, latency, state complexity
MicroservicesSplit into independently deployable servicesIndependent evolution, scaling, team autonomyDistributed-system and operational complexity

Pattern selection must follow architecture drivers

Do not choose a pattern because it is popular.

  • “Individual processing stages must be independently testable and replaceable.” → Possible fit: Pipes and Filters
  • “Business logic should remain isolated from UI and database technology.” → Possible fit: Layers
  • “Several teams need independent deployment and different scaling characteristics.” → Possible fit: Microservices

This is stronger reasoning than “Microservices are modern.”

Patterns can be combined

Patterns are not mutually exclusive. A microservice can internally use layers:

Order Service
 ├── Presentation Layer
 ├── Application Layer
 ├── Domain Layer
 └── Infrastructure Layer

Another service might use Pipes and Filters:

Upload
 ↓
Virus Scan
 ↓
Extract
 ↓
Validate
 ↓
Index

One system can use multiple patterns at different levels.

Common CPSA-F exam traps

  1. Microservices automatically create loose coupling. — False.
  2. Layers and tiers are the same thing. — False.
  3. A system must use only one architectural pattern. — False.
  4. Pipes and Filters means every filter must run as a separate service. — False.
  5. Microservices are better than a monolith. — Too absolute.
  6. Patterns are primarily technology choices. — False.

Key terms to remember

Architectural patternReusable architectural approach for recurring problems in a given context.
LayerLogical grouping of responsibilities according to abstraction or purpose.
PipeConnection carrying data between filters.
FilterIndependent processing or transformation stage.
MicroserviceFocused, independently deployable service with explicit interfaces.
Independent deployabilityAbility to deploy a service without requiring simultaneous deployment of the entire system.
Pattern consequencePositive or negative effect resulting from using a pattern.

Practical exercise

You are designing a document-processing platform. Requirements: users upload PDF documents; uploaded files must be virus-scanned; metadata must be extracted; text must be indexed; workloads arrive in large batches; stages should be independently testable; failed stages should be retryable; the product team contains only six developers.

The CTO proposes: “Every processing stage should be its own microservice.”

  1. Which architectural pattern naturally fits this workflow?
  2. Draw the processing flow.
  3. Which quality requirements support your choice?
  4. Does Pipes and Filters require each filter to be a separate microservice?
  5. What additional complexity would separate microservices introduce?
  6. Would a modular monolith containing the pipeline be reasonable?
  7. What evidence would justify splitting one filter into an independent service later?

Staff Engineer extension

Suppose the extraction stage now requires GPU processing and receives 20× more load than the other stages. Ask:

Does Extraction need independent scaling?
Does it require different infrastructure?
Does it fail independently?
Does it have a stable input/output contract?
Would deployment independence provide measurable value?
Staff Engineer lensIf several answers are yes, splitting that stage into an independently deployed service has stronger architectural justification.

Review questions

What are the three LG 03-08 architectural patterns at R1?

Layers, Pipes and Filters, and Microservices.

What is the core idea behind layered architecture?

Organizing responsibilities into ordered logical groups.

Why are layers and deployment tiers not equivalent?

Layers are logical; tiers usually describe deployment separation.

What are the two basic elements of Pipes and Filters?

Filters and pipes.

Name three qualities Pipes and Filters can support.

Examples: testability, composability, reuse, incremental processing, parallelism.

What is one major benefit of microservices?

Examples: independent deployment, selective scaling, team autonomy.

Name four kinds of complexity introduced by distributed microservices.

Examples: network failure, latency, tracing, retries, distributed consistency, versioning, authentication.

Why does replacing local calls with HTTP not automatically reduce coupling?

Runtime, semantic, temporal, and data dependencies may remain.

Can multiple architectural patterns coexist?

Yes.

What should drive pattern selection?

Requirements, quality goals, constraints, architecture drivers, and context.

Mini exam check

Which pattern is based most directly on a chain of data transformation stages?
Answer: Pipes and Filters. Layers organize by abstraction, and Microservices organize by independent deployability — neither is defined by a transformation chain.
Which statement is most accurate?
Answer: Multiple architectural patterns can be combined in one system. Layers do not require separate machines, microservices do not require different languages, and Pipes and Filters does not require asynchronous messaging.
Six autonomous teams need independent deployment and different scaling characteristics. Which pattern is especially relevant to evaluate?
Answer: Microservices. Independent deployability and selective scaling are its core strengths.
Which statement about architectural patterns is correct?
Answer: Patterns help achieve qualities for particular problems and contexts. A pattern does not guarantee a good architecture, does not remove the need for decisions, and is not merely a framework choice.
Which is a likely disadvantage of microservices?
Answer: They introduce distributed-system complexity. They can scale independently, they add (not eliminate) network communication, and they do not require one shared database.
