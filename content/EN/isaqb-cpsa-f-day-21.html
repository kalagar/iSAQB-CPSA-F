Requirement vs architecture driver

Days 1–20 are complete. Today is remediation: the distinctions below are where most CPSA-F mistakes actually happen, and each one is also a real review skill.

Requirement

Expresses a need.

Users can export invoices as PDF.

Architecture driver

A requirement, constraint, risk or assumption that materially influences architecture.

Order acceptance must remain
available if SAP is unavailable.

The second may influence communication style, runtime dependencies, persistence, integration and failure handling.

Exam distinctionNot every requirement is an architecture driver.

Driver identification test

Ask whether the item influences:

system structure
distribution
data ownership
technology choice
runtime interaction
quality trade-offs
deployment
security boundaries

If yes, it is more likely to be an architecture driver.

Quality requirement vs constraint

Quality requirement

Describes how well the system should behave.

95% of API requests must
complete in < 500 ms.

Constraint

Limits the solution space.

The system must run on the
corporate Kubernetes platform.
ShortcutQuality requirement = desired behavior. Constraint = restricted choices.

Quality scenario vs vague statement

Weak:

The system must be reliable.

Strong:

Source:      Payment provider
Stimulus:    Provider becomes unavailable
Environment: Peak traffic
Artifact:    Checkout workflow
Response:    Orders remain accepted
Measure:     Order acceptance availability >= 99.95%

A scenario is what makes a quality analyzable.

Cohesion vs coupling

Cohesion — inside

Payment Module
├── Payment authorization
├── Payment capture
└── Payment refund

Low cohesion:

Utility Module
├── Payment authorization
├── Email generation
├── Customer search
├── PDF export
└── Tax calculation

Coupling — between

Order Service
   ├── Payment
   ├── Inventory
   ├── Notification
   └── Fraud
ShortcutCohesion = inside a building block. Coupling = between building blocks.

Is low coupling always better?

No. Architecture seeks appropriate coupling, not zero coupling. Problematic coupling is usually:

  • unnecessary;
  • hidden;
  • unstable;
  • bidirectional;
  • semantically unclear.

Change coupling

Staff Engineer questionWhich components must change together?

If adding a payment provider requires edits in Order, Customer, Notification and Billing, modularity is poor — regardless of what the dependency diagram claims.

Context vs building block vs runtime vs deployment

QuestionView
Who/what interacts with the system?Context
What are the software parts?Building Block
What happens during a scenario?Runtime
Where does software run?Deployment
  • Context: system boundary, external actors, external systems, external interfaces.
  • Building Block: static software structure, responsibilities, relationships, interfaces.
  • Runtime: dynamic interaction, sequence, failure propagation, concurrency.
  • Deployment: infrastructure, nodes, runtime environments, software-to-infrastructure mapping.

View vs notation

Runtime View ≠ UML Sequence Diagram

A runtime view can be expressed using UML, BPMN, C4 dynamic diagrams, or plain text. View = perspective. Notation = language.

Concern vs cross-cutting concept

Concern

The problem or topic.

How should retries work?

Cross-cutting concept

The consistent architecture-wide solution.

Retries:
- transient failures only
- maximum 2
- exponential backoff
- jitter
- idempotent operations only
ShortcutConcern = what must be handled. Concept = how it is handled consistently.

Architecture analysis vs conformance

Analysis

Does this architecture satisfy the required qualities?

Performance test · scenario walkthrough · dependency analysis · security review.

Conformance

Does the implementation still follow the intended architecture?

Forbidden dependency checks · architecture code review · tool-supported structural analysis.

ShortcutAnalysis = good enough for the goal? Conformance = following architecture intent?

Drift vs erosion

Drift

Deviation from intended architecture.

One service bypasses another
service API and directly
accesses its database.

Erosion

Accumulated drift weakens architecture properties.

Many services now directly
access one another's databases.

Trade-off thinking

Asynchronous messaging

Benefits:
+ availability
+ temporal decoupling
+ buffering

Costs:
- eventual consistency
- duplicate handling
- operational complexity
The right questionNot “is messaging good?” but: does messaging improve the architecture drivers enough to justify the costs?

Staff Engineer decision framework

  1. What are the architecture drivers?
  2. What options exist?
  3. What qualities improve?
  4. What qualities get worse?
  5. What assumptions are we making?
  6. What evidence do we have?
  7. How reversible is the decision?
  8. How will we validate it?

High-error distinction drills

“Customer data must remain inside the EU.” — quality requirement or constraint?
Answer: constraint. It restricts the solution space rather than describing how well the system behaves.
“95% of requests must complete within 500 ms.” — quality requirement or constraint?
Answer: quality requirement. It is measurable desired behavior.
“Which external systems interact with us?” — context or runtime view?
Answer: context view.
“What happens when Fraud Service times out?” — context or runtime view?
Answer: runtime view.
“Maximum 2 retries, exponential backoff, jitter, transient failures only.” — concern or concept?
Answer: cross-cutting concept. It is the consistent solution, not the problem statement.
“The domain layer imports a database adapter.” — analysis result or conformance violation?
Answer: conformance violation. The implementation contradicts an intended rule.
“Payment Service has 15 outbound dependencies.” — proof of bad architecture or a signal?
Answer: a signal requiring context. The component may legitimately orchestrate.
“Use Kafka for order events.” — complete ADR or a decision without rationale?
Answer: an architecture decision without sufficient rationale. No context, options or consequences.

Staff Engineer case — insurance claims platform

Web
 ↓
Claims Service
 ├── Customer DB
 ├── Fraud API
 ├── Payment API
 ├── Document Provider SDK
 └── Kafka

Evidence:

- Fraud API occasionally takes 8 seconds.
- Claims availability target is 99.95%.
- 14 classes directly use the Document Provider SDK.
- A new document provider will be added this year.
- Several services directly read Customer DB.
- Teams use different retry policies.
- Customer email addresses have appeared in logs.

Architecture drivers

  1. Claims availability >= 99.95%
  2. New document provider must be easy to add
  3. Protection of customer personal data
  4. Fraud-provider latency and availability
  5. Independent service evolution

Risks

Fraud API latency

Claims
  ↓ synchronous
Fraud API

Potential impact: claims latency, availability, resource exhaustion. Options: a strict synchronous timeout, asynchronous fraud evaluation, accept-then-evaluate, or fallback / circuit breaker — depending on business semantics. No universal answer exists; context decides.

Proposed ADRs

ADR 1 — Isolate the document provider SDK behind a port

Context: 14 classes directly depend on a provider-specific SDK.

Driver: a new provider must be added efficiently.

Decision: introduce a DocumentProvider interface and provider-specific adapters.

Benefits: localized vendor dependency, easier testing, better replaceability. Costs: migration effort, extra abstraction.

ADR 2 — Standard retry policy

Context: teams use inconsistent retry behavior.

Driver: resilience without retry storms.

Decision: adopt shared retry rules.

ADR 3 — Customer data ownership

Context: multiple services read Customer DB directly.

Driver: independent service evolution.

Decision: restrict direct DB access to the owning component and its interface.

Suitable architecture rules

Rule 1:
Provider SDK imports allowed only in document adapters.

Rule 2:
Services may not access Customer DB directly
except the owning component.

Rule 3:
PII fields are forbidden in application logs.

Verification: static dependency tests, DB and network permissions, log-policy scanning.

Which rules should block CI?

Strong gate candidates:

  • provider SDK used outside an adapter;
  • forbidden module dependency;
  • known sensitive-data logging patterns.

Because they are objective, important, repeatable, and likely to regress.

Staff Engineer takeaway

A Staff Engineer should not solve this by personally coding every adapter. Higher leverage:

Clarify drivers
        ↓
Make trade-offs explicit
        ↓
Create shared decisions
        ↓
Define boundaries
        ↓
Automate important guardrails
        ↓
Let teams implement independently

Advanced exam traps

  1. A measurable requirement is automatically an architecture driver. → False
  2. High coupling always means bad design. → False
  3. A runtime diagram is the same thing as a runtime view. → False
  4. A cross-cutting concern must become a shared service. → False
  5. An ADR guarantees a good decision. → False
  6. Architecture analysis and conformance are synonyms. → False
  7. Drift always means architecture failure. → Too absolute

Review questions

What distinguishes an architecture driver from an ordinary requirement?

A driver materially influences architecture decisions or structure.

What distinguishes a quality requirement from a constraint?

A quality requirement specifies desired system behavior; a constraint restricts the solution space.

What is the difference between cohesion and coupling?

Cohesion is internal relatedness; coupling is dependency between elements.

Is low coupling always the goal?

No. The goal is appropriate, controlled coupling.

Which view answers “What happens during a timeout?”

Runtime view.

Which view answers “Which external systems exist?”

Context view.

View vs notation?

View = perspective; notation = expression language.

Concern vs cross-cutting concept?

Concern = problem/topic; concept = coherent solution.

Decision vs ADR?

Decision = choice; ADR = documented record.

Architecture analysis vs architecture conformance?

Analysis asks whether the architecture satisfies goals; conformance asks whether implementation follows architecture intent.

Drift vs erosion?

Drift = deviation; erosion = accumulated degradation.

Why can architecture metrics mislead?

Metrics need context and can be gamed.

Why are trade-offs central to architecture?

Improving one quality often affects another.

What makes a good candidate for automation as an architecture rule?

Objective, important, repeatable, cheap-to-check rules likely to regress.

What is the Staff Engineer's role in architecture governance?

Enable consistent distributed decision-making through drivers, communication, guardrails and evidence.

Difficult mini exam

Q1. “Claims must be available 99.95% of the time.”

  1. Automatically an architecture driver
  2. A quality requirement and potentially an architecture driver
  3. A constraint
  4. A runtime view
Show answer

B — measurable quality behavior; whether it drives architecture depends on impact.

Q2. “The application must run on the corporate Kubernetes platform.”

  1. Quality requirement
  2. Constraint
  3. Runtime scenario
  4. Architecture metric
Show answer

B — it restricts the solution space.

Q3. Which is primarily about cohesion?

  1. Order Service calls six services
  2. Payment Module contains payment and unrelated PDF-export logic
  3. Fraud API has high latency
  4. Two services share a protocol
Show answer

B — unrelated responsibilities inside one building block.

Q4. Which view explains how a customer request moves through six services?

  1. Context
  2. Runtime
  3. Deployment
  4. Building Block
Show answer

B — dynamic interaction is the runtime view.

Q5. A team defines maximum 2 retries, exponential backoff, jitter, and transient-failure-only behavior.

  1. Cross-cutting concern
  2. Cross-cutting concept
  3. Context view
  4. Architecture metric
Show answer

B — it is the consistent solution, not the problem.

Q6. “Use Kafka for OrderCreated events.”

  1. Complete ADR
  2. Architecture decision but not a complete decision record
  3. Quality scenario
  4. Deployment view
Show answer

B — no context, options, rationale or consequences.

Q7. A load test shows p95 = 1.4 s while the requirement is p95 < 700 ms.

  1. Architecture conformance
  2. Architecture quality analysis
  3. Deployment documentation
  4. Cross-cutting design
Show answer

B — measuring whether a quality goal is met is analysis.

Q8. A static check detects domain → infrastructure despite an explicit rule forbidding it.

  1. Architecture conformance checking
  2. Business analysis
  3. Requirements elicitation
  4. User testing
Show answer

A — implementation is checked against architecture intent.

Q9. One service bypasses another service's API and directly accesses its DB.

  1. Architecture drift
  2. Automatically architecture erosion
  3. Quality scenario
  4. Architectural style
Show answer

A — a single deviation is drift, not yet erosion.

Q10. After years, many services directly access each other's databases and independent deployment is difficult.

  1. Architecture erosion
  2. Context modeling
  3. White-box refinement
  4. Quality requirement
Show answer

A — accumulated drift has degraded architectural properties.
