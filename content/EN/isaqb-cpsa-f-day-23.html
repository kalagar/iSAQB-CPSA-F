Exam setup

The official CPSA-F exam is about 75 minutes with roughly 40 multiple-choice questions; the exact number can vary because questions have different point values. Passing requires 60% of achievable points. This mock contains 40 original practice questions.

Time: 75 minutes
Questions: 40
Practice score: 1 point/question
Practice pass: 24/40
Strong readiness target: >= 32/40 consistently
DisciplineDo not open a single answer until you have finished all forty. Several questions here have two answers that look correct; revealing early destroys exactly the calibration you came for.

Part A — Drivers, requirements & constraints

Q1. A marketplace has these requirements: (1) product names must be at most 200 characters, (2) checkout availability must be at least 99.95%, (3) the logo goes in the upper left, (4) products are sorted alphabetically. Which is most likely to be an architecture driver?

  1. Requirement 1
  2. Requirement 2
  3. Requirement 3
  4. Requirement 4
Show answer

B — A 99.95% availability target shapes redundancy, failover, deployment and integration decisions. The other three are satisfied inside a single component without changing the structure.

Q2. “All customer data must remain within Germany.” What is this?

  1. A functional requirement
  2. A quality scenario
  3. An architecture constraint
  4. A runtime view
Show answer

C — It restricts the solution space (hosting regions, providers, replication topology) rather than describing a function or a measurable quality response.

Q3. The team assumes peak traffic stays below 2,000 requests per second. What is the strongest response?

  1. Treat it permanently as an established fact
  2. Make the assumption explicit and validate it if significant decisions depend on it
  3. Ignore it until production fails
  4. Turn it directly into an ADR
Show answer

B — Assumptions are legitimate, but they must be written down and validated in proportion to what depends on them.

Q4. Which statement about architecture drivers is most accurate?

  1. Every requirement is a driver
  2. Only quality requirements can be drivers
  3. Drivers are those influences that significantly shape architecture decisions
  4. Constraints can never be drivers
Show answer

C — Drivers are defined by influence, not by category. Functional requirements, quality requirements and constraints can all be drivers.

Q5. Which is the strongest quality requirement?

  1. The system should be fast
  2. The API should perform well
  3. Under peak load, 95% of searches complete within 400 ms
  4. Developers should optimize their code
Show answer

C — It names the stimulus (peak load), the measure (400 ms) and the coverage (95%), so it can be tested. The others are unmeasurable wishes.

Part B — Design, coupling & cohesion

Q6. A class named CustomerUtils contains address validation, PDF generation, tax calculation, authentication and email templates. What is the main problem?

  1. Excessive cohesion
  2. Low cohesion
  3. Too few deployment nodes
  4. Too few interfaces
Show answer

B — Unrelated responsibilities live in one element. Every unrelated change reaches the same place.

Q7. Adding a new payment provider requires changes in eight unrelated modules. Which quality is most directly threatened?

  1. Modifiability
  2. Accessibility
  3. Portability
  4. Learnability
Show answer

A — The cost of a foreseeable change is the definition of modifiability.

Q8. A developer proposes an abstraction layer around a stable library that is unlikely to change. What is the best response?

  1. Every dependency needs an abstraction
  2. Abstraction is valuable only when its benefits justify the added complexity
  3. Abstraction always improves architecture
  4. All third-party libraries must be hidden
Show answer

B — Abstraction has a real cost. Without expected variation or another driver, that cost buys nothing.

Q9. Which statement about coupling is best?

  1. Good architecture eliminates coupling
  2. Coupling is always undesirable
  3. Dependencies should be appropriate and deliberately controlled
  4. Coupling exists only between microservices
Show answer

C — A system with no coupling does nothing. The goal is intentional, visible, justified dependencies.

Q10. A service is independently deployable, but its consumers rely on undocumented event ordering. This is:

  1. No coupling
  2. Semantic coupling
  3. Only deployment coupling
  4. Only source coupling
Show answer

B — The dependency is on meaning and ordering, not on code or deployment. Independent deployability hides it without removing it.

Part C — Patterns, styles & trade-offs

Q11. A ten-person team has moderate load, strong transactional requirements and little operational experience. Which statement is strongest?

  1. Microservices are automatically preferable
  2. A modular monolith may fit well if independent deployment and scaling are weak drivers
  3. Event-driven architecture is mandatory
  4. Every capability needs its own process
Show answer

B — With weak distribution drivers and strong transactional ones, distribution mostly adds cost. Drivers decide the style.

Q12. What is a typical consequence of asynchronous messaging?

  1. It eliminates all coupling
  2. It guarantees immediate consistency
  3. It can improve temporal decoupling while adding eventual consistency and operational complexity
  4. It removes the need to handle duplicates
Show answer

C — Asynchrony trades immediate consistency and simple operations for temporal decoupling and buffering.

Q13. Before adding a cache, what is the most important architectural question?

  1. Which cache product has the nicest logo?
  2. What staleness is acceptable, and what latency and load target must be achieved?
  3. Which product is most popular?
  4. Can everything be cached indefinitely?
Show answer

B — Quality target and acceptable freshness come first; technology selection is downstream of them.

Q14. Patterns are:

  1. Context-independent best practices
  2. Reusable solution approaches with both benefits and consequences
  3. Replacements for architecture decisions
  4. Guarantees of quality
Show answer

B — A pattern documents a solution together with the trade-off it imposes. It never removes the need to decide.

Q15. A shared database gives simple transactions but creates schema coupling. This is:

  1. Proof that shared databases are always wrong
  2. An architecture trade-off
  3. A conformance violation by definition
  4. Only a documentation problem
Show answer

B — Benefit and cost together, evaluated against this system's drivers, is precisely a trade-off.

Part D — Interfaces & cross-cutting concepts

Q16. Which is the strongest interface description?

  1. POST /payment
  2. The method name and schema only
  3. Semantics, inputs, outputs, errors, timing, security, idempotency and versioning where relevant
  4. The implementation language
Show answer

C — A contract is what a consumer may rely on. Syntax alone leaves every failure mode undefined.

Q17. A consumer interprets HTTP 404 as “permanently deleted,” but the provider only guarantees “currently not found.” This is:

  1. Deployment coupling
  2. Semantic coupling
  3. Visual coupling
  4. Hardware coupling
Show answer

B — The syntax matches; the meaning does not. Mismatched meaning is semantic coupling.

Q18. Six teams use incompatible retry strategies. What is the best response?

  1. Allow unlimited retries everywhere
  2. Define a coherent cross-cutting resilience and communication concept
  3. Add runtime diagrams only
  4. Rename the services
Show answer

B — Retry, timeout and backoff behaviour is a system-wide concern and needs one coherent concept, not six local inventions.

Q19. Which statement is correct?

  1. Every cross-cutting concern needs its own service
  2. A cross-cutting concept provides a coherent solution across multiple elements
  3. Cross-cutting concepts are only implementation details
  4. Logging cannot be cross-cutting
Show answer

B — The concern is the topic; the concept is the one coherent way the system addresses it everywhere.

Q20. Detailed request logging improves debugging but risks exposing personal data. This is:

  1. An observability versus privacy and security trade-off
  2. A context-view error
  3. Proof that logging should be disabled
  4. Proof that qualities are independent of each other
Show answer

A — Two legitimate qualities pull in opposite directions, so the decision must be explicit rather than accidental.

Part E — Decisions & feedback

Q21. Which decision most deserves an ADR?

  1. Renaming a private variable
  2. Integrating SAP asynchronously because SAP outages must not block order acceptance
  3. Reformatting a test
  4. Changing an IDE setting
Show answer

B — It is architecturally significant, costly to reverse, and its rationale will not be obvious from the code later.

Q22. Why record the alternatives considered in an ADR?

  1. To make the document longer
  2. To preserve why the selected option beat credible alternatives
  3. To ensure the decision can never change
  4. To replace the requirements
Show answer

B — Without the rejected options, a future reader cannot tell whether the decision was reasoned or accidental.

Q23. Which needs the strongest early validation?

  1. A local code formatting choice
  2. A public event schema consumed by 30 teams
  3. A test class name
  4. A local log message
Show answer

B — Widely consumed public contracts are the most expensive things to reverse, so validate them before they spread.

Q24. A performance test disproves a key assumption. What comes next?

  1. Ignore it, because the architecture was already approved
  2. Reassess the assumption and every decision that depended on it
  3. Remove the requirement
  4. Stop testing
Show answer

B — Feedback that invalidates an assumption invalidates the decisions resting on it. That is the point of testing early.

Q25. Which is the best iterative sequence?

  1. Decision → never revisit
  2. Assumption → decision → validation → evidence → refinement
  3. Technology → requirement → stakeholder
  4. Code → driver → ignore feedback
Show answer

B — Architecture work is a feedback loop: decide under uncertainty, validate, then refine on evidence.

Part F — Documentation & views

Q26. Which view shows that an external identity provider communicates with the system?

  1. Context view
  2. Runtime view
  3. Deployment view
  4. Class view
Show answer

A — System boundary and external communication partners belong to the context view.

Q27. Which view shows which internal components belong to the Claims subsystem?

  1. Context view
  2. Building block view
  3. Deployment view
  4. Runtime view only
Show answer

B — Static internal decomposition is the building block view.

Q28. Which view shows where the Claims Service runs and which database instance it uses?

  1. Context view
  2. Building block view
  3. Deployment view
  4. Glossary
Show answer

C — Mapping software to infrastructure is the deployment view.

Q29. Which view explains what happens when the Fraud Service times out during claim submission?

  1. Runtime view
  2. Context view
  3. Deployment view
  4. Static view only
Show answer

A — Interaction over time, including failure and timeout behaviour, is the runtime view.

Q30. Which statement is correct?

  1. Every runtime view must use UML
  2. A view is an architectural perspective; a notation is a means of expressing it
  3. C4 and the runtime view are identical
  4. A diagram is always a complete view
Show answer

B — Perspective and expression language are separate concerns. A diagram is one artefact inside a view, not the view itself.

Part G — Analysis & conformance

Q31. A load test shows p95 checkout latency of 1.4 s against a requirement of 700 ms. This is primarily:

  1. Architecture quality analysis
  2. Conformance checking only
  3. Context documentation
  4. Requirements elicitation only
Show answer

A — It measures whether the architecture meets a quality goal. Conformance would ask whether the implementation follows the intended architecture.

Q32. A component has 18 outbound dependencies. What is the strongest conclusion?

  1. It is definitely bad
  2. It is a signal that requires architectural context
  3. It must be split immediately
  4. Such numbers must always be reduced below five
Show answer

B — A metric is evidence, not a verdict. An orchestrating component may legitimately have many outbound dependencies.

Q33. A rule forbids Domain → Infrastructure dependencies, and an automated test detects a violation. This is:

  1. Architecture conformance checking
  2. Business analysis
  3. Usability evaluation
  4. Requirements prioritization
Show answer

A — Comparing the implementation against an intended architecture rule is conformance checking.

Q34. One team bypasses the Customer API and reads the Customer database directly, despite an explicit rule. Initially this is:

  1. Architecture drift
  2. An architecture style
  3. A quality scenario
  4. A deployment optimization
Show answer

A — A single deliberate deviation from the intended architecture is drift.

Q35. Years later, many teams access each other's databases directly and independent evolution has become difficult. This is:

  1. Architecture erosion
  2. Context refinement
  3. Runtime modeling
  4. Increased cohesion
Show answer

A — Accumulated, unaddressed drift that has degraded the structure is erosion.

Part H — Staff Engineer scenario

The last five questions share one context.

Online Claims Platform

Claims API
  ├── Fraud Provider
  ├── Payment Provider
  ├── Customer DB
  └── Document Vendor SDK

Evidence:
- Fraud Provider sometimes takes 12 seconds.
- Claims availability target: 99.95%.
- User response target: < 2 seconds.
- 17 classes import Document Vendor SDK.
- Second document vendor planned.
- Multiple services query Customer DB directly.
- Teams use different timeout/retry rules.

Q36. What is the strongest architecture driver in this evidence?

  1. The number of Java classes
  2. The availability and response-time targets
  3. The IDE in use
  4. DTO naming
Show answer

B — 99.95% availability and a sub-2-second response target directly constrain how the slow Fraud Provider may be integrated.

Q37. What is the best change for document-vendor modifiability?

  1. Add more direct SDK imports
  2. Introduce a stable document-provider port with vendor-specific adapters
  3. Move the document code into the UI
  4. Duplicate the vendor logic per caller
Show answer

B — Here the abstraction is justified: a second vendor is planned, and 17 direct imports make that change expensive.

Q38. What is the first question to ask about the 12-second Fraud Provider latency?

  1. Is synchronous fraud confirmation required before acknowledging a claim?
  2. Which font should the diagram use?
  3. Does the provider use Java?
  4. Should the service be renamed?
Show answer

A — Business semantics decide whether asynchronous evaluation is even permissible. Mechanism comes after that answer.

Q39. Different timeout and retry behaviour across teams indicates the need for:

  1. A cross-cutting resilience and communication concept
  2. More database tables
  3. A new UI framework
  4. A larger context diagram
Show answer

A — Inconsistent resilience behaviour is a missing cross-cutting concept, not a missing component.

Q40. What is the highest-leverage Staff Engineer response to this situation?

  1. Personally implement every integration
  2. Clarify drivers, facilitate decisions, define guardrails, automate conformance and enable teams
  3. Personally approve every method
  4. Avoid documenting trade-offs
Show answer

B — Leverage comes from shared drivers, guardrails and automated feedback, not from becoming the bottleneck.

Key explanations

Q8 — Abstraction

Abstraction has a cost. Introduce it when expected variation or another driver justifies that cost.

Q10 / Q17 — Semantic coupling

Components can be source-independent yet tightly coupled through assumptions about meaning, timing, ordering or behaviour.

Q11 — Architecture style

Microservices are not synonymous with good architecture. Drivers determine suitability.

Q13 — Caching

First define the quality target and acceptable freshness; technology comes later.

Q23 — Reversibility

Widely consumed public contracts are costly to reverse, so validate them carefully.

Q32 — Metrics

Metrics are evidence, not verdicts. Architectural context determines their meaning.

Q38 — Staff-level reasoningUnderstand the business semantics before introducing queues or other mechanisms. If fraud approval must happen before acceptance, asynchronous processing is simply invalid — no matter how good the latency numbers look.

Common exam traps

  1. Absolute claims such as “always” and “never”.
  2. Fashion-driven technology choices.
  3. Treating patterns as universal solutions.
  4. Treating a metric as a conclusion.
  5. Confusing a diagram with an architectural view.
  6. Assuming asynchronous means uncoupled.
  7. Assuming abstraction is automatically good.
  8. Assuming more documentation is always better.
  9. Treating architecture as immutable.
  10. Treating the architect or Staff Engineer as the central approver of everything.

Practical exercise

For the Claims Platform in Part H, prepare:

1. Five architecture drivers
2. Five risks
3. Two explicit assumptions
4. Three candidate decisions
5. Consequences of each
6. One availability scenario
7. One modifiability scenario
8. Three architecture rules
9. One automated conformance/fitness check
10. One ADR title + rationale

Use this chain throughout:

Evidence → Driver → Option → Trade-Off → Decision → Validation

Worked example:

Evidence:
Fraud provider sometimes takes 12 seconds.

Driver:
Response < 2 seconds; availability >= 99.95%.

Assumption:
Fraud approval may happen after durable claim acceptance.

Option:
Persist claim, acknowledge it, evaluate fraud asynchronously.

Benefit:
Fraud latency no longer blocks acknowledgement.

Cost:
Eventual consistency and retry/failure handling.

Validation:
Simulate provider outage and verify availability + no lost claims.
The hingeIf the assumption is false, reconsider the decision. The assumption — not the queue — is what the design rests on.

Review questions

  1. What makes a requirement an architecture driver?
  2. Why make assumptions explicit?
  3. Quality requirement versus constraint?
  4. Cohesion versus coupling?
  5. What is semantic coupling?
  6. Why are patterns context-dependent?
  7. What are the trade-offs of messaging?
  8. When is abstraction justified?
  9. Why validate hard-to-reverse decisions early?
  10. Decision versus ADR?
  11. Context view versus building block view?
  12. Runtime view versus deployment view?
  13. View versus notation?
  14. Concern versus cross-cutting concept?
  15. Analysis versus conformance?
  16. Metric versus conclusion?
  17. Drift versus erosion?
  18. Why can asynchronous communication improve availability?
  19. Why can asynchronous communication still be invalid?
  20. How does a Staff Engineer scale architecture quality?
Show compact answers 
1.  It materially influences architecture.
2.  To expose and validate uncertainty.
3.  Quality = how well; constraint = restricted solution space.
4.  Cohesion = inside; coupling = between.
5.  Dependency on meaning/behaviour.
6.  Benefits/costs depend on drivers and context.
7.  Eventual consistency, duplicates, ordering, tracing, operations.
8.  When benefits against drivers justify complexity.
9.  Errors are costly to reverse.
10. Choice vs documented record.
11. Environment/boundary vs static internal structure.
12. Dynamic behaviour vs infrastructure mapping.
13. Perspective vs expression language.
14. Problem/topic vs coherent system-wide solution.
15. Meets goals? vs follows intended architecture?
16. Metric is evidence requiring context.
17. Deviation vs accumulated degradation.
18. Removes temporal dependence on downstream availability.
19. Business semantics may require immediate confirmation.
20. Shared drivers, decisions, guardrails, automation, feedback.
