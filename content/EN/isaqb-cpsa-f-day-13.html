Feedback Loops, Uncertainty & Architectural Risk

Learn how iterative architecture, feedback, and risk reduction work together—and how to apply them like a Staff Engineer.

Learning objectives

By the end of this lesson, you should be able to explain why architecture work must often be iterative, connect uncertainty, risk, feedback, and predictability, make architectural decisions incrementally, and systematically obtain stakeholder feedback.

Official alignmentLG 03-05 — Correlation between Feedback Loops and Risks. Exam relevance: R1 for iterative decision-making, R2 for systematically obtaining stakeholder feedback.

The core relationship

Uncertainty
    ↓
Architectural Decision
    ↓
Potential Risk
    ↓
Experiment / Implementation / Discussion
    ↓
Feedback
    ↓
New Evidence
    ↓
Refined Decision

The goal is not to avoid decisions. The goal is to make decisions with appropriate confidence and obtain evidence early enough to correct mistakes before they become expensive.

Uncertainty vs risk

Uncertainty

We do not know enough yet. Examples: can the new API handle 10,000 requests/second? Will users need real-time results? Is a vendor API reliable enough? Can the team operate Kubernetes effectively?

Risk

An uncertain condition may negatively affect an important goal.

Uncertainty:
Can the external payment provider handle peak load?

Risk:
Checkout availability may fall below 99.95%.

Not every uncertainty is architecturally important. Risk matters when it threatens availability, security, performance, maintainability, cost, compliance, or business goals.

Architecture risk starts with drivers

Quality Requirement
99.95% checkout availability
        ↓
Architecture Driver
Payment availability must not unnecessarily block ordering
        ↓
Architecture Decision
Synchronous payment interaction
        ↓
Risk
Payment outage causes checkout outage

The architecture driver explains why the risk matters.

Why iteration reduces risk

Compare:

Design for 12 months
→ implement everything
→ load test at the end

with:

Identify critical assumption
→ build a small slice
→ load test
→ analyze evidence
→ refine

Shorter feedback loops expose incorrect assumptions sooner. Iteration does not guarantee success. It makes learning cheaper and earlier.

Prediction vs feedback

Architecture uses both.

Prediction

Reason about expected traffic, failures, requirements, and team needs.

Feedback

Observe prototypes, users, production metrics, developers, and real failures.

Strong architecture combines:

Reason → Decide → Validate → Learn → Adjust

Short vs long feedback loops

Long loop

Decision → 6 months implementation → production → first performance test.

Short loop

Decision → prototype → load test → feedback → refine.

Short loops are especially valuable for expensive, irreversible, unfamiliar, or high-risk decisions.

Risk and reversibility

High impact
+
High uncertainty
+
Low reversibility
=
Strong need for early feedback

A local helper-library choice needs little validation. A company-wide data partitioning strategy deserves much more.

Feedback techniques

Architecture feedback can come from:

  • Prototype — validate feasibility.
  • Proof of Concept — test whether a technology or integration can solve the problem.
  • Spike — time-boxed investigation to reduce uncertainty.
  • Load Test — validate performance/scalability.
  • Failure Test — validate resilience.
  • Architecture Review — obtain experienced stakeholder input.
  • Developer Feedback — reveal coupling, unclear responsibilities, poor interfaces.
  • Operations Feedback — reveal latency, failure rates, resource use, observability gaps.

Systematically obtaining stakeholder feedback

Do not rely on: “If someone disagrees, they will tell us.” Use a deliberate process:

Decision
   ↓
Identify affected stakeholders
   ↓
Identify concerns
   ↓
Choose feedback method
   ↓
Collect feedback
   ↓
Resolve conflicts / update decision

Example decision: asynchronous notification delivery. Possible stakeholder concerns:

  • Developers → complexity and testing
  • SRE → broker reliability and retries
  • Product → user-visible delay
  • Security → sensitive event data
  • Finance → infrastructure cost

Feedback does not mean consensus

Feedback informs decisions. It does not mean everyone must agree.

Stakeholder A prefers A.
Stakeholder B prefers B.
Architecture Driver favors B.
Decision: B.
Rationale documented.

Architecture involves trade-offs.

ADRs as feedback tools

ADR-042: Asynchronous notification delivery

Context:
Notification outages currently block checkout.

Architecture Driver:
Checkout availability >= 99.95%.

Options:
1. Synchronous HTTP
2. Queue + async processing

Decision:
Use asynchronous delivery.

Risks:
- duplicates
- delayed emails
- broker dependency

Validation:
- failure test
- load test
- retry simulation

Review Date:
After first production release

The important part is validation. Decisions can be revisited when evidence changes.

Staff Engineer scenario

You are designing an order-processing platform. Requirements: 2,000 orders/minute today; possible growth to 20,000; 99.95% order-acceptance availability; confirmed orders must never disappear; SAP is mandatory; SAP has occasional outages; the team has never operated Kafka.

Current proposal:

Client
  ↓
Order API
  ↓
SAP

Alternative:

Client
  ↓
Order API
  ↓
Kafka
  ↓
Order Processor
  ↓
SAP

Identify uncertainties: can synchronous processing meet availability? Can Kafka handle required throughput and durability? Can the team operate Kafka? How should SAP outages affect accepted orders?

Choose feedback:

Kafka throughput → load test
Durability → broker failure test
Operational readiness → spike + runbook exercise
SAP outages → outage simulation

Now the decision becomes evidence-driven.

Production feedback

Architecture feedback continues after deployment. Useful signals include:

Latency
Error rate
Availability
CPU / memory
Queue depth
Database contention
Deployment failure rate
Recovery time

If an assumption says notification delay should stay under 5 minutes, but p95 is 22 minutes, the architecture has new evidence and should be revisited.

Fitness functions — advanced connection

A fitness function is an automated or measurable check showing whether an architecture continues to satisfy an important characteristic.

p95 latency < 500 ms
No forbidden dependency from Domain → Infrastructure
Recovery time < 60 seconds

Not the main focus of LG 03-05, but highly useful for Staff Engineer practice because it makes feedback continuous.

Common CPSA-F exam traps

  1. Architecture decisions should be finalized before implementation. — False.
  2. Iteration eliminates architectural risk. — False.
  3. Feedback is only needed when a decision fails. — False.
  4. Feedback only means production monitoring. — False.
  5. More planning always creates more predictability. — False.
  6. All decisions require the same validation effort. — False.
  7. Stakeholder feedback means consensus is required. — False.

Key terms to remember

Feedback loopA cycle in which results influence subsequent decisions.
Architectural riskPotential negative consequence threatening architecture goals.
UncertaintyLack of sufficient knowledge about a decision or outcome.
Iterative decision-makingRefining decisions progressively as evidence becomes available.
PrototypeSmall implementation used to explore or validate an idea.
Proof of ConceptFocused implementation used to determine feasibility.
SpikeTime-boxed investigation used to reduce uncertainty.
ValidationObtaining evidence that a decision or assumption is appropriate.
PredictabilityDegree to which outcomes can reasonably be anticipated.

Practical exercise

You are designing an AI-assisted customer-support platform. Requirements: responses should usually begin within 2 seconds; customer data must remain in the EU; users may upload documents up to 100 MB; the team predicts 100,000 users within one year; the AI provider has not been load-tested; launch target is four months.

Web App
   ↓
Backend
   ↓
AI Provider
   ↓
Vector Database
  1. Identify at least five uncertainties.
  2. Which create significant architectural risk?
  3. Rank them by impact × uncertainty.
  4. Choose one feedback mechanism for each high-risk item.
  5. Which decisions should be made now?
  6. Which can safely be deferred?
  7. What evidence would change your architecture?
  8. Which stakeholders should provide feedback?

Review questions

Why are iterative approaches important in architecture?

Decisions are often made under uncertainty; iteration enables refinement as evidence appears.

What is the difference between uncertainty and risk?

Uncertainty means not knowing; risk means that uncertainty may harm an important goal.

How can shorter feedback loops reduce risk?

They expose incorrect assumptions earlier.

Does iterative architecture mean avoiding upfront design?

No. It combines intentional design with incremental learning.

Name four ways to obtain architecture feedback.

Prototype, PoC, load test, failure test, review, developer feedback, production monitoring.

Why should hard-to-reverse decisions receive more validation?

Incorrect decisions have larger consequences and are more expensive to undo.

What is the role of stakeholder feedback?

It reveals stakeholder concerns and consequences.

Does stakeholder feedback require consensus?

No.

How can an ADR participate in a feedback loop?

ADRs can record assumptions, rationale, validation, and review conditions.

Why can a prototype be more valuable than additional planning?

Experiments can produce evidence that analysis alone cannot.

Mini exam check

Why does CPSA-F emphasize iteration?
Answer: Decisions are often made under uncertainty. Architects should not avoid decisions, iteration is not a mandate for Agile specifically, and documentation still matters.
Which activity gives strongest feedback about a scalability assumption?
Answer: A realistic load test. Renaming a diagram, adding documentation, or asking only the original architect does not produce evidence.
Which statement is correct?
Answer: Iterative decisions can improve predictability by incorporating evidence. Iteration does not eliminate risk, and decisions can change; feedback is useful before and after production.
Which situation most strongly justifies early validation?
Answer: A high-impact, uncertain, hard-to-reverse decision. Low-impact reversible decisions, variable naming, and documentation formatting need little or no validation.
What is the main role of stakeholder feedback?
Answer: Providing information about concerns and consequences. It does not guarantee consensus, replace architecture responsibility, or eliminate trade-offs.
