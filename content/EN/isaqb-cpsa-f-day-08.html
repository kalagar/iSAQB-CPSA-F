Architecture Development Approaches & Heuristics

Learning objectives

By the end of this lesson, you should be able to explain and apply the core ideas behind Top-down, bottom-up, view-based, iterative in both exam questions and real architecture discussions.

Official alignmentLG 03-03 — Architecture Development Approaches and Heuristics.

Top-down development

Start from business goals, requirements, and qualities, then progressively refine structure.

Business goals → Requirements → Qualities → Subsystems → Components

Bottom-up development

Start from existing technical reality: legacy systems, APIs, databases, infrastructure, reusable components, and organizational constraints.

Most real systems combine both

Practical realityTop-down gives the desired direction. Bottom-up exposes constraints and existing assets. Architecture emerges from the negotiation between the two.

View-based development

Use complementary views to reason about different concerns.

  • Building-block view → static structure.
  • Runtime view → interactions and behavior.
  • Deployment view → where software executes.

Iterative and risk-driven design

Hypothesis → Prototype → Measure → Feedback → Refine

Validate the decisions with the highest uncertainty and potential impact first.

Common CPSA-F exam traps

  1. Top-down is always better than bottom-up. — Treat this as suspicious or false unless the context explicitly supports it.
  2. Bottom-up means requirements are irrelevant. — Treat this as suspicious or false unless the context explicitly supports it.
  3. Views are only documentation after design is finished. — Treat this as suspicious or false unless the context explicitly supports it.
  4. Evolutionary architecture means no intentional design. — Treat this as suspicious or false unless the context explicitly supports it.

Key terms to remember

Top-downDesign from goals and requirements toward finer structure.
Bottom-upDesign from existing technical elements and constraints upward.
View-based designUse complementary architectural perspectives during design.
Evolutionary architectureArchitecture designed for controlled change over time.

Practical exercise

Modernize a 15-year-old insurance platform: Java monolith, Oracle, SAP integration, 20 batch jobs, 3 teams. New goals: faster releases, selective independent scaling, cloud migration, no full rewrite, SAP must remain.

Identify what comes from top-down analysis, what comes from bottom-up analysis, and which three architecture views you would create first.

Review questions

When is top-down useful?

When requirements and architectural drivers can guide decomposition.

When is bottom-up important?

When existing systems and constraints strongly shape the solution.

Should the two approaches be mutually exclusive?

No. Most real architecture work combines them.
