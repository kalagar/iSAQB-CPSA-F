Architecture Documentation & Architectural Views

Write documentation people actually use: understandable, correct, efficient, appropriate and maintainable — and pick the view that answers the question a stakeholder is really asking.

Learning objectives

By the end of this lesson, you should be able to explain why architecture documentation exists, name the quality requirements of good technical documentation, tailor documentation to stakeholder needs, explain and use the context, building block, runtime and deployment views, distinguish views from diagrams and notations, select the right view for a stakeholder concern, and recognize the common CPSA-F exam traps around documentation.

Why architecture documentation exists

Architecture documentation supports design, implementation, communication, maintenance, evolution, onboarding, decision-making and risk reduction.

Appropriate documentation

The same architecture may need different representations for developers, testers, management, operations, security and product stakeholders. Documentation is not one artifact for everyone — it is a set of answers to different questions.

Documentation quality requirements

The official curriculum emphasizes five qualities:

  • Understandability — can the intended audience understand it?
  • Correctness — does it match reality?
  • Efficiency — can readers find what they need quickly?
  • Appropriateness — is the content suitable for its purpose?
  • Maintainability — can it be kept current with reasonable effort?
Trap“More documentation is always better” is false. Documentation that nobody can maintain becomes wrong documentation, and wrong documentation is worse than none.

View vs diagram vs notation

View

An architectural perspective focused on specific concerns.

Diagram

A visual artifact used to communicate part of a view.

Notation

The language or convention used to draw it — UML, C4, ArchiMate, or plain text.

View ≠ Diagram ≠ Notation
Exam distinctionA runtime view is not “a UML sequence diagram”. The same runtime view can be expressed with UML, BPMN, a C4 dynamic diagram, or a numbered list of steps.

Context view

Shows the system in its environment and its external interfaces.

                Customer
                   |
                   v
         +-------------------+
         | E-Commerce System |
         +-------------------+
          |       |        |
          v       v        v
      Payment   CRM     Shipping
      Provider  System   Provider

It answers:

  • What is inside our system boundary?
  • Who uses the system?
  • Which external systems interact with it?
  • Which interfaces cross the boundary?

Business vs technical context

  • Business context: actors, business systems, information flow.
  • Technical context: protocols, interfaces, external technical systems.

Building block / component view

Describes the static decomposition of the software.

E-Commerce System
│
├── Order Management
│   ├── Order API
│   ├── Order Application Service
│   └── Order Repository
├── Payment
│   ├── Payment API
│   └── Payment Provider Adapter
└── Customer Management
    ├── Customer API
    └── Customer Repository

It answers: what are the main software building blocks, what responsibilities do they have, how are they related, and which interfaces exist?

Black box

Responsibility and externally visible interfaces only.

White box

Internal decomposition and relationships.

Runtime view

Describes dynamic behavior and collaboration at runtime.

Customer
  |
  | Place Order
  v
Order Service
  |
  | Reserve
  v
Inventory
  |
  | OK
  v
Order Service
  |
  | Pay
  v
Payment

Useful scenarios: successful checkout, payment timeout, login, message retry, failover, batch import.

Staff Engineer lensRuntime views are the cheapest way to make temporal coupling and failure propagation visible. If a synchronous call appears in a critical path, the availability risk shows up on the whiteboard instead of in production.

Deployment view

Shows technical infrastructure and the mapping of software onto it.

+------------------------+
| Kubernetes Cluster     |
|  Order Service Pods    |
|  Payment Service Pods  |
+-----------+------------+
            |
            v
+------------------------+
| PostgreSQL Cluster     |
+------------------------+

It answers: where does software run, which infrastructure does it depend on, how are components distributed, which network boundaries exist, and where is data stored?

Consistency across views

Views must not contradict each other.

Context:        System → Payment Provider
Building Block: Payment Adapter → Payment Provider
Runtime:        Order Service → Payment Provider directly

If those differ, readers cannot trust any of the documentation — and inconsistency is usually a symptom that the implementation has already drifted.

Template-based documentation

A lightweight template:

1. Context
2. Architecture Drivers
3. Building Block View
4. Runtime Scenarios
5. Deployment
6. Cross-Cutting Concepts
7. Architecture Decisions
8. Risks

arc42 is one well-known documentation template. The exam tests the idea of structured, stakeholder-oriented documentation — not one specific product.

Common CPSA-F exam traps

  • A view is the same as a UML diagram. → False
  • Context view shows internal decomposition. → False
  • Deployment view only shows servers. → False
  • Runtime view is static decomposition. → False
  • More documentation is always better. → False
  • All stakeholders need the same documentation. → False
  • C4 is mandatory for CPSA-F. → False

Review questions

Which five documentation qualities are explicitly named in LG 04-01?

Understandability, correctness, efficiency, appropriateness, maintainability.

What are the four R1 architectural views?

Context, building block/component, runtime, deployment.

What does a context view primarily show?

System boundary, environment, external actors and systems, interfaces crossing the boundary.

What does a building block view primarily show?

Static software decomposition.

What does a runtime view primarily show?

Dynamic interaction and runtime behavior.

What does a deployment view primarily show?

Infrastructure and software-to-infrastructure mapping.

What is the difference between a view and a notation?

View = perspective; notation = the language used to express it.

Why should documentation be stakeholder-oriented?

Different stakeholders have different concerns.

Why is maintainability important?

Stale documentation becomes misleading.

Can multiple notations express the same view?

Yes.
