Learning objectives

By the end of this lesson, you should be able to explain and apply the core ideas behind Interface design and dependency management in both exam questions and real architecture discussions.

Official alignmentLG 03-06 and LG 03-07.

Dependencies are not automatically bad

The right question is not “How do we remove every dependency?” but “Is this dependency necessary, and is the form of coupling appropriate?”

Temporal coupling

Synchronous calls require both parties and the network to be available at the same time.

Order → Payment (HTTP)

Queues can reduce temporal coupling but introduce eventual consistency, retries, duplication, and observability complexity.

Data and semantic coupling

Data coupling occurs when consumers know more of a producer's data model than necessary. Semantic coupling occurs when components depend on shared meaning and behavior even if schemas are technically compatible.

Interfaces are contracts

A useful interface contract covers more than endpoints or method names:

  • Inputs and outputs
  • Errors
  • Preconditions and postconditions
  • Timing expectations
  • Idempotency
  • Security
  • Semantics
  • Versioning expectations

Characteristics of good interfaces

  • Easy to learn, use, and extend.
  • Hard to misuse.
  • Functionally complete for consumers.

Synchronous vs asynchronous

Synchronous

Immediate response, simpler control flow, but stronger temporal coupling and failure propagation.

Asynchronous

Buffering and looser availability coupling, but more consistency and operational complexity.

Versioning and backward compatibility

Stable contracts allow components to evolve independently. External interfaces typically require stronger compatibility guarantees and longer deprecation periods than internal ones.

Common CPSA-F exam traps

  1. Dynamic dependencies imply low coupling. — Treat this as suspicious or false unless the context explicitly supports it.
  2. Async always reduces complexity. — Treat this as suspicious or false unless the context explicitly supports it.
  3. Public and internal interfaces can evolve identically. — Treat this as suspicious or false unless the context explicitly supports it.
  4. A remote call has the same failure characteristics as a local call. — Treat this as suspicious or false unless the context explicitly supports it.

Key terms to remember

Temporal couplingComponents must be available or act at the same time.
Data couplingA consumer depends on unnecessary details of another component's data model.
Semantic couplingComponents depend on shared meaning or behavior.
InterfaceA contract through which components interact.
Backward compatibilityExisting consumers continue to work after interface evolution.

Practical exercise

Current order flow:

Order → Customer → Inventory → Payment → Notification

Creating an order takes three seconds and fails whenever any downstream service is unavailable.

  1. Which interactions truly require synchronous responses?
  2. Should Notification failure block order creation?
  3. How would you redesign that interaction?
  4. Why does replacing every HTTP call with Kafka not automatically remove coupling?

Review questions

What is temporal coupling?

A dependency that requires components to be available or act at the same time.

Does replacing a compile-time dependency with HTTP automatically reduce coupling?

No.

What should a good interface be?

Easy to learn/use/extend, hard to misuse, and functionally complete.

Why are public interfaces harder to change?

Because you do not control all consumers.
