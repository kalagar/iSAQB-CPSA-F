Learning objectives

By the end of this lesson, you should be able to explain why architectures are analyzed, distinguish design-time from runtime analysis, choose analysis methods for quality attributes, distinguish qualitative and quantitative analysis, use quality scenarios, interpret coupling metrics, identify evidence sources, explain the difference between analysis and conformance, and conduct a lightweight architecture assessment.

Official alignmentLG 05-01, LG 05-02. Related: LG 05-03.

Why analyze architecture?

Architecture analysis asks:

The core questionDoes this architecture actually support what the system needs?

A system can be functionally correct but architecturally unhealthy:

Features work,
but deployments take 4 hours,
one failure breaks checkout,
and changes touch 12 modules.

Reasons for analysis

  • identify risks and improvement opportunities;
  • determine whether requirements are fulfilled;
  • assess conformance;
  • verify stakeholder concerns.

It can happen before, during, or after implementation.

Evidence-based analysis

Weak: “This architecture looks scalable.”

Stronger:

Quality Requirement
       ↓
Analysis Method
       ↓
Evidence
       ↓
Conclusion

Example:

Requirement:
p95 latency < 500 ms

Method:
Load test

Evidence:
p95 = 420 ms at 2,000 req/s

Qualitative vs quantitative

Quantitative

Latency = 420 ms
Throughput = 3,000 req/s
Availability = 99.96%
Outbound dependencies = 14

Qualitative

Structured judgment: architecture review, interviews, security review, scenario walkthrough, stakeholder survey.

Trap“Quantitative methods are always superior” is false. A number without interpretation is not an architectural conclusion.

Match method to quality

QualityPossible method
PerformanceLoad test, runtime metrics
AvailabilityFailure test, uptime metrics
SecurityThreat analysis, penetration testing
MaintainabilityCode review, coupling metrics
UsabilityUser testing
ModifiabilityChange scenarios
DeployabilityPipeline analysis

Scenario-based analysis

Instead of “the system should be maintainable”, use:

Stimulus:
Add a new payment provider.

Response:
Implement without modifying order logic.

Measure:
Completed within 3 developer-days.

Watch outAverages hide tail latency. A healthy mean with a terrible p99 is a real user-facing problem.

Coupling metrics

Inbound / afferent

How many other elements depend on this component?

Outbound / efferent

How many other elements does this component depend on?

High outbound coupling can signal failure exposure, low autonomy, harder testing and harder deployment.

Metrics need context

A high dependency count does not automatically prove bad architecture — the component may legitimately be an orchestrator.

Rule of thumbMetrics are evidence, not verdicts.

Goodhart's Law

If a metric becomes a rigid target, teams optimize the number instead of the quality.

Every service must have <= 3 dependencies.

Teams may create a MegaGateway: the metric improves while the architecture gets worse.

ATAM (R3)

You do not need deep ATAM mastery for CPSA-F. The basic idea: evaluate the architecture against quality attributes and identify risks, trade-offs, sensitivity points and important decisions.

Analysis vs testing

Testing

Does the implemented system behave correctly?

Architecture analysis

Does the structure support future change? Are dependencies appropriate? Are quality goals met? Does the implementation conform?

Design-time vs runtime

Design-time

Diagrams, scenarios, dependency reasoning, design reviews.

Runtime

Load tests, metrics, logs, traces, failure tests.

Strong assessments combine both.

Conformance preview

Conformance asks whether the implementation matches architecture decisions and design.

UI → Application → Domain

If Domain imports UI code, conformance is violated. Drift is implementation moving away from intended architecture; erosion is accumulated deviation weakening important properties. Day 18 goes deeper.

Staff Engineer review framework

  1. Identify drivers.
  2. Identify scenarios.
  3. Inspect structure.
  4. Gather evidence.
  5. Identify risks.
  6. Recommend action.

Possible actions:

Accept
Measure
Prototype
Refactor
Add guardrail
Revisit decision

Communicate findings in a fixed shape:

Observation
Evidence
Risk
Affected Quality
Recommendation
Validation
Staff Engineer lensA finding without evidence is an opinion; a finding without a recommendation is a complaint. The six-line shape forces both.

Common CPSA-F exam traps

  • Analysis happens only after implementation. → False
  • Analysis only checks functionality. → False
  • Quantitative methods are always superior. → False
  • High coupling proves bad architecture. → False
  • Scenario analysis requires production. → False
  • Testing and architecture analysis are identical. → False
  • ATAM must be mastered in depth. → False

Practical exercise

Given a customer portal with:

p95 = 1.2 s
60% of classes depend on Document Provider SDK
Notification outages caused incidents
Authorization exists in UI and backend
Document Service has 18 outbound dependencies
  1. Identify four risks.
  2. Map each to a quality attribute.
  3. Classify each finding as qualitative or quantitative.
  4. Choose an analysis method per risk.
  5. Write an availability and a modifiability scenario.
  6. Prioritize the highest risk and justify it.

Review questions

What does architecture analysis ask?

Whether the architecture actually supports the required qualities.

When can analysis happen?

Before, during, or after implementation.

Qualitative vs quantitative?

Structured judgment vs numerical evidence; strong analysis combines both.

What is a quality scenario?

Source, stimulus, environment, artifact, response, response measure — making an abstract quality analyzable.

Why are averages dangerous?

They hide tail latency problems that users actually experience.

What does high outbound coupling signal?

Possible failure exposure, low autonomy, harder testing and deployment — a signal, not a verdict.

What is Goodhart's Law in architecture?

When a metric becomes a target, teams optimize the number instead of the quality.

Analysis vs testing?

Testing checks behavior; analysis checks structure, dependencies, qualities and conformance.

Drift vs erosion?

Drift = deviation; erosion = accumulated degradation.

How should findings be communicated?

Observation, evidence, risk, affected quality, recommendation, validation.
