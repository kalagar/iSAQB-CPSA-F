Requirements, constraints and drivers

Functional requirement:
Users can submit insurance claims.

Quality requirement:
95% of claims should be accepted within 2 seconds.

Constraint:
Customer data must remain inside the EU.

Organizational constraint:
The team already operates PostgreSQL and Kubernetes.

An architecture driver is a requirement, constraint, risk or assumption that materially influences architecture decisions.

Exam distinctionRequirement ≠ architecture driver automatically.

Explicit assumptions

Architectural significance

Not every technical choice is architectural. A choice becomes more significant with high impact, high reversal cost, cross-team consequences, quality-attribute impact, or long-term constraints.

Patterns and trade-offs

Microservices may improve independent deployment, team autonomy and independent scaling — and may worsen operational complexity, distributed debugging, consistency and network failure exposure.

High-frequency exam traps

  1. Good architecture minimizes all coupling. → False
  2. More documentation is always better. → False
  3. Architectural decisions should never change. → False
  4. A pattern is automatically a best practice. → False
  5. Architecture analysis requires completed software. → False
  6. Metrics objectively prove architecture quality. → False
  7. Stakeholder feedback means unanimous agreement. → False
  8. Cross-cutting concerns always require separate services. → False
  9. Context view shows internal decomposition. → False
  10. Conformance means architecture may never evolve. → False

Integrated Staff Engineer case

Current load:      2,000 orders/min
Future load:       20,000 orders/min
Availability:      Order acceptance >= 99.95%
Compliance:        Customer data remains in EU
Business:          New payment provider within 5 developer-days
Operational:       SAP has occasional outages

Current proposal:

Web
 ↓
Order Service
 ├── Payment Provider SDK
 ├── Inventory
 ├── Notification
 └── SAP

Potential architecture drivers

  1. Order acceptance availability
  2. Expected 10× growth
  3. Payment-provider modifiability
  4. SAP instability
  5. EU data-residency constraint

Risks

Risk 1

Order → SAP synchronously

Threatens availability.

Risk 2

Payment SDK embedded
in Order Service

Threatens modifiability.

Risk 3

Notification synchronous
in checkout path

Threatens availability and latency.

Risk 4

No evidence for 20,000 orders/min. Threatens scalability confidence.

Candidate decisions

1. Introduce PaymentProvider interface + adapters.
2. Decouple SAP using durable asynchronous processing.
3. Publish notifications asynchronously.
4. Validate expected load with representative performance tests.
5. Define EU deployment/data-storage rules explicitly.

Conformance rules

Payment vendor SDK may only be used in payment adapters.
Order Domain may not depend on infrastructure.
Order acceptance may not synchronously call SAP.
All integration events contain eventId, schemaVersion, timestamp.

Possible checks: static dependency tests, schema validation, CI architecture tests, runtime resilience tests.

Mini mock — 10 questions

Which best describes an architecture driver?
Answer: A requirement or constraint that materially influences architecture — not every functional requirement, not any coding convention, and not only performance requirements.
Which view best explains a failure interaction during checkout?
Answer: Runtime view. Context shows the environment, building block shows static structure, deployment shows infrastructure.
Which statement about an ADR is correct?
Answer: It records the decision's rationale and consequences. It does not replace architecture documentation, is not required for every code-level choice, and can be superseded.
A service has 15 outbound dependencies. What can you conclude?
Answer: It is a signal requiring contextual analysis — not proof of bad architecture, not a mandate to split, and not a reason to drive dependencies to zero.
Which is a cross-cutting concept?
Answer: A system-wide error-handling strategy. A single entity method, SQL query or variable convention is local.
Which statement about feedback is correct?
Answer: Feedback can validate assumptions before full implementation. It is not production-only, iteration does not eliminate risk, and feedback does not require consensus.
Which most directly checks architecture conformance?
Answer: Forbidden dependency analysis.
What is the main purpose of a quality scenario?
Answer: To make an abstract quality concrete and analyzable.
Which statement about architecture patterns is correct?
Answer: Pattern suitability depends on drivers and context. Patterns are not automatically best practices, do not eliminate trade-offs, and CPSA-F does not prefer microservices.
Which is the strongest Staff Engineer behavior?
Answer: Create guardrails and enable teams to make consistent decisions — rather than personally approving every decision, centralizing knowledge, or replacing documentation with meetings.

Review questions

What turns a requirement into an architecture driver?

It materially influences architecture decisions or structure.

Why should assumptions be explicit?

Hidden assumptions create unmanaged risk.

What makes a decision architecturally significant?

High impact, reversal cost, quality influence, cross-team consequences, or future constraints.

Cohesion vs coupling?

Cohesion is how well responsibilities belong together; coupling is dependency between elements.

Black box vs white box?

Black box = external responsibility and interfaces; white box = internal decomposition.

Why is interface semantics important?

Stable syntax can still hide semantic coupling.

Concern vs cross-cutting concept?

Concern = problem/topic; concept = architectural solution.

Why do cross-cutting concepts interact?

One concept can affect another quality or constraint.

Why are patterns not universal best practices?

They are context-dependent.

What is the benefit of short feedback loops?

They expose incorrect assumptions earlier.

What are the four core views?

Context, building block, runtime, deployment.

View vs notation?

View = perspective; notation = language.

What is scenario-based analysis?

Evaluating architecture using concrete quality scenarios.

Qualitative vs quantitative?

Structured judgment vs numerical evidence.

Why are metrics insufficient alone?

Metrics need context and can be gamed.

What does conformance evaluate?

Whether implementation aligns with architecture intent.

Drift vs erosion?

Drift = deviation; erosion = accumulated degradation.

What is a fitness function?

An objective assessment of an architectural characteristic.

Why are ADRs useful?

They preserve context, rationale, alternatives and consequences.

What is the Staff Engineer role in architecture governance?

Enable distributed good decisions through guardrails, communication and evidence.
