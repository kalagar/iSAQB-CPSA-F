Cross-Cutting Concerns and Cross-Cutting Concepts

Identify concerns that cut across the whole architecture, and design coherent concepts—for persistence, communication, error handling, concurrency, UI, security, and observability—like a Staff Engineer.

Learning objectives

By the end of this lesson, you should be able to explain cross-cutting concerns, distinguish a concern from a cross-cutting concept, identify cross-cutting concerns in an architecture, design coherent concepts for persistence, communication, error handling, concurrency, UI, security, and observability, identify interdependencies between cross-cutting concepts, recognize common CPSA-F exam traps, and apply these ideas at Staff Engineer level.

Official alignmentLG 03-10 — Identify, Design and Implement Cross-Cutting Concerns (R1). Related: LG 04-07 — Document and Communicate Cross-Cutting Concerns (R2).

What is a cross-cutting concern?

A cross-cutting concern affects multiple parts of the architecture rather than belonging neatly to one building block.

Order Service
Customer Service
Payment Service
Inventory Service

All may need:

Logging
Authentication
Authorization
Error handling
Monitoring
Tracing
Configuration
Persistence rules
Communication conventions

These concerns cut across multiple architectural elements.

Concern vs concept

Cross-Cutting Concern

The problem or topic that affects several parts of the system.

How should errors be handled consistently?

Cross-Cutting Concept

The architectural solution used to address that concern.

Standard error taxonomy
Correlation IDs
Retry rules
Safe API error responses
Centralized exception mapping
Structured logging
Exam distinctionConcern = what must be addressed. Concept = how the architecture addresses it.

Why cross-cutting concerns matter

Without a common concept, teams may solve the same problem differently.

Order Service    → JSON logs
Payment Service  → plain-text logs
Customer Service → stack traces
Inventory Service→ almost no logging

Possible consequences:

  • difficult troubleshooting;
  • inconsistent observability;
  • missing correlation across services;
  • security leaks;
  • duplicated implementation effort.

A shared logging concept might define:

Log format
Log levels
Mandatory fields
Correlation IDs
Sensitive-data policy
Retention
Central collection

Cross-cutting concern ≠ separate service

A cross-cutting concern does not automatically require its own component.

Logging might be implemented with:

  • a shared library;
  • a platform SDK;
  • an agent;
  • a sidecar;
  • framework configuration;
  • infrastructure policy.

Security might involve:

  • an identity provider;
  • API gateway rules;
  • application authorization;
  • certificate management;
  • secret storage;
  • audit logging.

The concept can span multiple architectural elements.

Persistence as a cross-cutting concept

Persistence is more than choosing a database. A persistence concept can include: data ownership, transaction boundaries, repository conventions, schema migration, caching, concurrency control, consistency, backup and restore, encryption, audit requirements.

Database:
PostgreSQL

Ownership:
Each domain module owns its tables.

Access:
Only repository adapters access SQL.

Transactions:
One business use case = one local transaction.

Schema Changes:
Versioned migrations.

Concurrency:
Optimistic locking.

Communication as a cross-cutting concept

Questions include: synchronous or asynchronous? REST, messaging, or gRPC? timeout rules? retry rules? idempotency? versioning? authentication? serialization? tracing? error semantics?

Internal synchronous calls:
REST/JSON

Default timeout:
2 seconds

Retries:
Only idempotent operations

Correlation:
X-Correlation-ID propagated

Versioning:
Backward-compatible APIs

Error handling

Without a common concept:

Service A → HTTP 500 for everything
Service B → internal stack traces
Service C → swallows exceptions
Service D → retries forever

A stronger concept:

Business errors
→ explicit domain error codes

Transient technical errors
→ bounded retry

Permanent technical errors
→ fail fast + alert

Public API
→ no internal stack traces

Logs
→ technical detail + correlation ID

This improves reliability, supportability, security, and observability.

Logging and observability

A system-wide observability concept may define:

Logging

Structured JSON
Correlation ID
Service name
Environment
Severity
No passwords/tokens

Metrics

Request rate
Error rate
Latency
Queue depth
Database pool usage
Tracing:
Client
 ↓ trace-id
API Gateway
 ↓
Order
 ↓
Payment

At Staff Engineer level, observability is architectural because it determines whether teams can understand production behavior.

Security as a cross-cutting concern

Questions include:

Who authenticates users?
How do services authenticate each other?
Where is authorization enforced?
How are secrets stored?
How is data encrypted?
What is audited?

Example concept:

Authentication:
Central OpenID Connect provider

Authorization:
Domain permissions enforced server-side

Service identity:
OAuth2 client credentials

Secrets:
Managed secret store

Transport:
TLS

Audit:
Security-relevant changes recorded

Security cannot be solved by adding one "security component."

Concurrency

Concurrency is explicitly named in LG 03-10. A concurrency concept may address: threads, async tasks, shared state, synchronization, locking, race conditions, optimistic vs pessimistic concurrency, ordering.

Order updates:
Optimistic locking

Background processing:
Worker pool

Shared mutable state:
Avoided between requests

Duplicate events:
Handled idempotently

UI / GUI

A UI concept can define: navigation, state management, validation, accessibility, error presentation, design system, localization.

Design System:
Shared component library

Validation:
Client + authoritative server validation

Accessibility:
Defined accessibility target

Errors:
Consistent error component

Energy efficiency

Energy efficiency is explicitly named in the curriculum. Possible architectural concerns: polling frequency, unnecessary network calls, CPU-heavy processing, transferred data volume, workload scheduling, cloud overprovisioning.

Instead of:

Every client polls every second

consider push notifications or adaptive polling, depending on requirements.

Interdependencies between cross-cutting concepts

Cross-cutting concepts are not independent.

Security
   ↓
Encrypted communication
   ↓
Higher CPU cost
   ↓
Performance impact
Retry strategy
   ↓
More requests
   ↓
Higher load
   ↓
Possible cascading failure
Detailed logging
   ↓
Better observability
   ↓
More storage
   ↓
Higher cost
   ↓
Potential privacy risk

The official curriculum expects architects to identify and assess these interdependencies.

Staff Engineer example: retry policy

Suppose every team independently decides:

Retry failed calls 5 times immediately.

If Payment Service fails:

20 upstream instances
        ↓
each retries 5 times
        ↓
traffic multiplier
        ↓
Payment receives even more load

This can create a retry storm.

A shared resilience concept might define:

Retries:
Maximum 2

Backoff:
Exponential + jitter

Allowed for:
Idempotent transient operations only

Timeout:
Per call + overall request budget

Circuit breaker:
For unstable dependencies
Staff Engineer lensThis is typical Staff Engineer-level cross-team architecture work: one bad local decision, replicated across 20 callers, becomes a systemic outage.

Standardization vs flexibility

A useful model is:

Standardize architectural rules
Allow flexibility inside those rules

Mandatory:

All services propagate trace IDs.
All logs are structured.
Secrets are not stored in source code.

Flexible:

Java → Logback
Python → structlog
Node → pino

The architecture defines required behavior, not necessarily one implementation library.

Reuse across systems

Cross-cutting concepts may be reused across systems.

Company Authentication Concept
Company Logging Standard
API Error Model
Deployment Concept
Observability Standard

Benefits: reduced design effort, easier onboarding, consistent operations, stronger governance, fewer repeated mistakes.

Common CPSA-F exam traps

  1. A cross-cutting concern always needs its own component. — False.
  2. Cross-cutting concerns are only infrastructure topics. — False.
  3. Cross-cutting concepts are independent. — False.
  4. Persistence means selecting a database. — Too narrow.
  5. Every team can define logging independently without architectural impact. — False.
  6. Cross-cutting concepts cannot be reused across systems. — False.
  7. Standardization requires exactly one implementation library. — False.

Key terms to remember

Cross-Cutting ConcernA concern affecting multiple architectural elements.
Cross-Cutting ConceptA coherent architectural solution for a cross-cutting concern.
InterdependencyA relationship where one architectural concept influences another.
ConsistencyUniform application of architectural rules across relevant parts of the system.
ReuseApplying an established concept across multiple systems.
GovernanceMechanisms used to ensure architectural rules are followed.

Practical exercise

You review an e-commerce architecture:

Web
 ↓
API Gateway
 ↓
────────────────────────────
| Orders | Payment | Search |
────────────────────────────
       ↓
    Databases

You discover: each service uses a different log format; only Payment has distributed tracing; each service chooses its own timeout; Orders retries every failed request five times; Payment never retries; authentication is checked only at the gateway; database migrations are manual; user-facing errors sometimes contain Java stack traces.

  1. Identify at least six cross-cutting concerns.
  2. Which inconsistencies create the greatest risk?
  3. Design a minimal communication concept.
  4. Design a minimal error-handling concept.
  5. Design a minimal observability concept.
  6. Which concepts interact with security?
  7. Which decisions should be organization-wide?
  8. Which implementation choices can remain team-specific?

Staff Engineer extension

Create a concept map:

                Security
                /      \
               /        \
      Communication    Logging
           |              |
           |              |
      Error Handling — Observability
           |
           |
       Persistence

For each connection, explain the interdependency.

Example:

Logging ↔ Security

Logging needs enough detail for investigations.

But logs can expose:
- tokens
- passwords
- personal data

Therefore the logging concept must include security/privacy rules.

Review questions

What is a cross-cutting concern?

A concern that affects multiple parts of the architecture.

What is the difference between a concern and a cross-cutting concept?

Concern = problem/topic; concept = architectural solution.

Name six cross-cutting concerns.

Persistence, communication, GUI, error handling, concurrency, energy efficiency, logging, security, observability.

Why is logging cross-cutting?

Because many components must produce compatible operational information.

Does every concern require a separate service?

No.

Why assess interdependencies?

Because one concept can influence qualities or constraints of another.

How can retries affect performance and availability?

Retries may improve resilience but can increase load and create retry storms.

What can a persistence concept contain besides database choice?

Ownership, transactions, migrations, locking, consistency, caching, backup, access patterns, encryption.

Can cross-cutting concepts be reused?

Yes.

Why do organization-wide rules matter for Staff Engineers?

They reduce inconsistent local decisions and improve operability, security, maintainability, and alignment.

Mini exam check

Which statement best describes a cross-cutting concern?
Answer: A concern affecting multiple architectural elements. It need not belong to one class, be a microservice, or be relevant only to infrastructure.
Which is explicitly listed in LG 03-10?
Answer: Persistence. Variable naming, Git branching, and unit-test naming are not architectural cross-cutting concerns.
Which statement is correct?
Answer: Architects should identify and assess interdependencies between cross-cutting concepts. Concepts do influence each other, not every component needs its own error strategy, and concepts can be reused.
Why define a common logging concept?
Answer: It reduces inconsistency and supports system-wide observability. It does not mandate one framework, replace monitoring, or require a separate service.
A policy requires sensitive data never to appear in logs. What does this demonstrate?
Answer: Cross-cutting concepts can have interdependencies (logging ↔ security). This is not about layers reducing coupling, isolating every concern, or deployment tiers.
