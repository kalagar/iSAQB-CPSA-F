اهداف یادگیری

در پایان این درس، باید بتوانید لایه‌ها (Layers)، لوله‌ها و صافی‌ها (Pipes and Filters) و میکروسرویس‌ها (Microservices) را توضیح داده و به‌کار ببرید، هر الگو را به نیازمندی‌های کیفی مرتبط کنید، مصالحه‌های آن‌ها را مقایسه کنید، و درباره انتخاب الگو در سطح Staff Engineer استدلال کنید.

الگوهای معماری

یک الگوی معماری یک رویکرد قابل استفاده مجدد برای یک مسئله تکرارشونده معماری در یک زمینه (context) خاص است. یک الگو صرفاً یک نمودار نیست؛ بلکه یک مسئله تکرارشونده، ایده یک راه‌حل ساختاری، مسئولیت‌ها، تعاملات و پیامدها را توصیف می‌کند.

معماری لایه‌ای

الگوی لایه‌ها یک سیستم را به گروه‌های مرتب‌شده‌ای از مسئولیت‌ها سازمان‌دهی می‌کند.

┌─────────────────────────┐
│ Presentation Layer      │
├─────────────────────────┤
│ Application Layer       │
├─────────────────────────┤
│ Domain / Business Layer │
├─────────────────────────┤
│ Infrastructure Layer    │
└─────────────────────────┘

مسئولیت‌های معمول: لایه نمایش (Presentation) — کنترلرها، APIها، مدیریت درخواست/پاسخ. لایه اپلیکیشن (Application) — هماهنگی موارد کاربرد (use case) و مرزهای تراکنش. لایه دامنه (Domain) — قوانین کسب‌وکار و مفاهیم دامنه. لایه زیرساخت (Infrastructure) — پایگاه‌های داده، پیام‌رسانی، APIهای خارجی.

مزایای احتمالی

نگهداشت‌پذیری، قابل‌فهم‌بودن، جداسازی دغدغه‌ها، آزمون‌پذیری، جایگزین‌پذیری مکانیزم‌های فنی.

مصالحه‌های ممکن

انتزاع‌های اضافی، کد نگاشت (mapping)، لایه‌بندی غیرمستقیم، لایه‌های صرفاً عبوری (pass-through)، سربار احتمالی کارایی.

لایه در برابر لایه استقرار (Tier)

یک لایه (Layer) عمدتاً یک ساختار منطقی است. یک Tier معمولاً به جداسازی استقرار (deployment) اشاره دارد. یک استقرار سه‌لایه (three-tier) هنوز می‌تواند شامل لایه‌های منطقی زیادی باشد.

Browser
   ↓
Application Server
   ↓
Database Server

لوله‌ها و صافی‌ها (Pipes and Filters)

الگوی لوله‌ها و صافی‌ها پردازش را به مراحل مستقل تبدیل (transformation) سازمان‌دهی می‌کند. هر صافی (Filter) یک تبدیل انجام می‌دهد؛ هر لوله (Pipe) داده را بین صافی‌ها منتقل می‌کند.

Raw XML
   ↓
Parse
   ↓
Validate
   ↓
Normalize
   ↓
Enrich
   ↓
Persist

نقاط قوت احتمالی

قابلیت ترکیب (composability)، آزمون‌پذیری، استفاده مجدد، پردازش تدریجی، موازی‌سازی، جداسازی تبدیل‌ها.

مصالحه‌های ممکن

سربار سریال‌سازی، دشواری مدیریت وضعیت، اشکال‌زدایی بین مراحل، پیچیدگی مدیریت خطا، تأخیر (latency).

اگر صافی چهارم پس از موفقیت صافی‌های ۱ تا ۳ شکست بخورد، ممکن است به تلاش مجدد، ایدمپوتنسی، نقاط بازرسی (checkpoints)، مدیریت پیام‌های ناموفق (dead-letter) و جبران (compensation) نیاز داشته باشید.

میکروسرویس‌ها

یک معماری میکروسرویس، سیستم را به سرویس‌های متمرکز و مستقل از نظر استقرار تجزیه می‌کند.

                    ┌──────────────┐
                    │ API Gateway  │
                    └──────┬───────┘
                           │
         ┌─────────────────┼─────────────────┐
         ↓                 ↓                 ↓
   Order Service     Customer Service   Payment Service
         │                 │                 │
     Order DB          Customer DB        Payment DB

مزایای احتمالی: قابلیت استقرار مستقل، مقیاس‌پذیری انتخابی، خودمختاری تیم‌ها، قابلیت تکامل، جداسازی خطا (fault isolation).

هشدار مهممیکروسرویس‌ها به‌طور خودکار به معنای کوپلینگ سست نیستند. اگر همه سرویس‌ها باید هم‌زمان در دسترس باشند، کوپلینگ زمانی همچنان می‌تواند قوی باشد — کوپلینگ داده‌ای، معنایی، نسخه‌بندی و عملیاتی نیز ممکن است باقی بمانند.
Order Service
   ↓ HTTP
Customer Service
   ↓ HTTP
Inventory Service
   ↓ HTTP
Payment Service

هزینه‌های سیستم توزیع‌شده

میکروسرویس‌ها دغدغه‌هایی مانند خرابی شبکه، تأخیر، تلاش مجدد، پیام‌های تکراری، ردیابی توزیع‌شده (tracing)، کشف سرویس، سازگاری نهایی (eventual consistency)، احراز هویت بین‌سرویسی، سازگاری نسخه API و هماهنگ‌سازی استقرار را وارد می‌کنند.

یک فراخوانی محلی:

paymentService.pay(order);

به یک تعامل دوردست تبدیل می‌شود که باید در نظر بگیرید:

Timeout?
Retry?
Authentication?
Network failure?
Duplicate request?
Version mismatch?
Partial success?

میکروسرویس‌ها در برابر مونولیت ماژولار

مونولیت ماژولار

ممکن است زمانی مناسب باشد که تیم کوچک است، سادگی عملیاتی اهمیت دارد، مقیاس‌پذیری مستقل هنوز لازم نیست، سازگاری قوی ارزشمند است، یا مرزها هنوز در حال تکامل‌اند.

میکروسرویس‌ها

ممکن است زمانی جذاب باشند که تیم‌ها به تحویل مستقل نیاز دارند، مؤلفه‌ها ویژگی‌های مقیاس‌پذیری متفاوتی دارند، جداسازی خطا اهمیت دارد، مرزهای دامنه بالغ‌اند، یا توانایی عملیاتی قوی است.

هیچ‌کدام همیشه بهتر نیست.

دام‌های رایج آزمون CPSA-F

  1. میکروسرویس‌ها به‌طور خودکار کوپلینگ سست ایجاد می‌کنند. — نادرست.
  2. لایه‌ها (Layers) و Tierها یکسان‌اند. — نادرست.
  3. یک سیستم باید فقط از یک الگوی معماری استفاده کند. — نادرست.
  4. لوله‌ها و صافی‌ها یعنی هر صافی باید به‌صورت یک سرویس جداگانه اجرا شود. — نادرست.
  5. میکروسرویس‌ها بهتر از مونولیت هستند. — بیش از حد مطلق.
  6. الگوها اساساً انتخاب‌های فناوری هستند. — نادرست.

اصطلاحات کلیدی برای به‌خاطرسپاری

الگوی معماری (Architectural pattern)رویکرد معماری قابل استفاده مجدد برای مسائل تکرارشونده در یک زمینه معین.
لایه (Layer)گروه‌بندی منطقی مسئولیت‌ها بر اساس انتزاع یا هدف.
لوله (Pipe)اتصالی که داده را بین صافی‌ها منتقل می‌کند.
صافی (Filter)مرحله مستقل پردازش یا تبدیل.
میکروسرویس (Microservice)سرویسی متمرکز، مستقل از نظر استقرار، با رابط‌های صریح.
قابلیت استقرار مستقل (Independent deployability)توانایی استقرار یک سرویس بدون نیاز به استقرار هم‌زمان کل سیستم.
پیامد الگو (Pattern consequence)اثر مثبت یا منفی حاصل از استفاده یک الگو.

تمرین عملی

در حال طراحی یک پلتفرم پردازش اسناد هستید. نیازمندی‌ها: کاربران فایل‌های PDF آپلود می‌کنند؛ فایل‌های آپلودشده باید از نظر ویروس اسکن شوند؛ فراداده (metadata) باید استخراج شود؛ متن باید ایندکس شود؛ حجم کار به‌صورت دسته‌ای (batch) بزرگ می‌رسد؛ مراحل باید به‌طور مستقل قابل‌آزمون باشند؛ مراحل ناموفق باید قابل تلاش مجدد باشند؛ تیم محصول فقط شش توسعه‌دهنده دارد.

مدیر ارشد فناوری (CTO) پیشنهاد می‌دهد: «هر مرحله پردازشی باید میکروسرویس مستقل خودش باشد.»

  1. کدام الگوی معماری به‌طور طبیعی با این جریان کاری سازگار است؟
  2. جریان پردازش را رسم کنید.
  3. کدام نیازمندی‌های کیفی از انتخاب شما پشتیبانی می‌کنند؟
  4. آیا لوله‌ها و صافی‌ها نیاز دارد هر صافی یک میکروسرویس جداگانه باشد؟
  5. میکروسرویس‌های جداگانه چه پیچیدگی اضافه‌ای وارد می‌کنند؟
  6. آیا یک مونولیت ماژولار حاوی این خط لوله معقول خواهد بود؟
  7. چه شواهدی توجیه می‌کند که بعداً یک صافی را به سرویسی مستقل تبدیل کنید؟

بسط Staff Engineer

فرض کنید مرحله استخراج اکنون به پردازش GPU نیاز دارد و ۲۰ برابر بیشتر از مراحل دیگر بار دریافت می‌کند. بپرسید:

Does Extraction need independent scaling?
Does it require different infrastructure?
Does it fail independently?
Does it have a stable input/output contract?
Would deployment independence provide measurable value?
دیدگاه Staff Engineerاگر پاسخ چند مورد بله باشد، جدا کردن آن مرحله به یک سرویس مستقر مستقل، توجیه معماری قوی‌تری دارد.

آزمون کوتاه

کدام الگو مستقیماً بر پایه زنجیره‌ای از مراحل تبدیل داده است؟
پاسخ: لوله‌ها و صافی‌ها. لایه‌ها بر اساس انتزاع سازمان‌دهی می‌شوند و میکروسرویس‌ها بر اساس قابلیت استقرار مستقل — هیچ‌کدام با یک زنجیره تبدیل تعریف نمی‌شوند.
کدام گزینه درست‌تر است؟
پاسخ: چندین الگوی معماری می‌توانند در یک سیستم ترکیب شوند. لایه‌ها نیازی به ماشین‌های جداگانه ندارند، میکروسرویس‌ها نیازی به زبان‌های متفاوت ندارند، و لوله‌ها و صافی‌ها نیازی به پیام‌رسانی ناهمگام ندارد.
شش تیم مستقل به استقرار مستقل و ویژگی‌های مقیاس‌پذیری متفاوت نیاز دارند. کدام الگو به‌ویژه شایسته بررسی است؟
پاسخ: میکروسرویس‌ها. قابلیت استقرار مستقل و مقیاس‌پذیری انتخابی نقاط قوت اصلی آن‌اند.
کدام گزینه درباره الگوهای معماری درست است؟
پاسخ: الگوها به دستیابی به ویژگی‌های کیفی برای مسائل و زمینه‌های خاص کمک می‌کنند. یک الگو معماری خوب را تضمین نمی‌کند، نیاز به تصمیم‌گیری را از بین نمی‌برد، و صرفاً یک انتخاب فناوری نیست.
کدام گزینه احتمالاً یک نقطه‌ضعف میکروسرویس‌هاست؟
پاسخ: پیچیدگی سیستم توزیع‌شده را وارد می‌کنند. آن‌ها می‌توانند به‌طور مستقل مقیاس یابند، ارتباط شبکه را اضافه می‌کنند (نه حذف)، و به یک پایگاه داده مشترک نیاز ندارند.
