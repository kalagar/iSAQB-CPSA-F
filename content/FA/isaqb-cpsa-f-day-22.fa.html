معماری به‌ندرت یک پاسخ جهان‌شمول دارد. هر انتخاب نسبت به نیازمندی‌ها، محدودیت‌ها، محرک‌ها، ریسک‌ها، فرض‌ها و زمینه ارزیابی می‌شود.

نیاز → محرک معماری → گزینه‌ها → پیامدهای کیفی
     → مصالحه → تصمیم → اعتبارسنجی → بازخورد

گزینه A:      فراخوانی همگام SAP.
گزینه B:      یکپارچه‌سازی ناهمگام بادوام.
تصمیم:        B.

هزینه‌ها:      سازگاری نهایی، تکرار پیام، عملیات.
اعتبارسنجی:   شبیه‌سازی ۳۰ دقیقه قطعی SAP.

سناریو — یکپارچه‌سازی با SAP

نیازمندی‌ها:

دسترس‌پذیری پذیرش سفارش >= ۹۹٫۹۵٪
SAP حدود ۲۰ دقیقه در هفته در دسترس نیست
تأیید سفارش < ۱ ثانیه
همگام‌سازی با SAP تا ۱۰ دقیقه تأخیر مجاز است
هیچ سفارش پذیرفته‌شده‌ای نباید گم شود

گزینه A

Order Service → REST همگام → SAP

گزینه B

Order Service → ذخیره سفارش
  → صف بادوام → SAP Worker → SAP

محرک‌های غالب: دسترس‌پذیری، تأخیر، ماندگاری داده.

گزینه B احتمالاً قوی‌تر است، چون تأخیر در همگام‌سازی صراحتاً پذیرفته شده است. هزینه‌های آن واقعی‌اند: سازگاری نهایی، عملیات صف، مدیریت تکرار و بازیابی.

امنیت در برابر کاربردپذیری

احراز هویت مجدد برای هر عملیات مدیریتی شاید امنیت را بالا ببرد اما کاربردپذیری را تخریب می‌کند. احراز هویت پلکانی (step-up) تنها برای عملیات پرریسک، معمولاً مصالحه بهتری است.

حتی معماری امنیت هم مصالحه دارد.

استانداردسازی در برابر خودگردانی تیم

شش تیم رویکردهای متفاوتی برای retry، لاگ، ردیابی و احراز هویت انتخاب می‌کنند. خودگردانی حداکثری، انعطاف محلی را بالا می‌برد اما ممکن است عملیات‌پذیری، یکدستی، امنیت و اشتراک دانش را کاهش دهد.

معماری در سطح Staff معمولاً از حفاظ (guardrail) استفاده می‌کند:

نتایج الزامی:
- انتشار trace ID
- حذف فیلدهای حساس
- محدود بودن تعداد retry
- اعتبارسنجی claimهای احراز هویت

پیاده‌سازی:
تیم‌ها آزادی کنترل‌شده خود را حفظ می‌کنند

حفاظ در برابر تجویز

تجویز

هر سرویس باید از کتابخانه X
نسخه Y استفاده کند.

حفاظ

هر فراخوانی HTTP خروجی باید:
- timeout داشته باشد؛
- فقط برای خطاهای واجد شرایط،
  retry محدود انجام دهد؛
- متریک تأخیر/خطا منتشر کند.

حفاظ‌ها کیفیت‌های معماری را حفظ می‌کنند و در عین حال انعطاف پیاده‌سازی را نگه می‌دارند.

تصمیم ← قاعده ← راستی‌آزمایی

تصمیم:        منطق دامنه مستقل از فریم‌ورک بماند.
قاعده:        پکیج‌های دامنه نباید Spring، JPA یا
              زیرساخت را import کنند.
راستی‌آزمایی:  تست معماری در CI.

زنجیره کامل:

محرک → تصمیم → قاعده → راستی‌آزمایی → بازخورد

تله‌های آزمون

«همیشه از پیام‌رسانی ناهمگام برای کاهش کوپلینگ استفاده کنید.»نادرست. این کار شکل‌های دیگری از پیچیدگی و کوپلینگ معنایی می‌آورد.
فناوری پیش از نیازمندیضعیف است. ترتیب درست: نیازمندی ← محرک ← گزینه ← انتخاب.
یک متریک = حکم نهایینادرست. ۱۸ وابستگی یک نشانه است که به زمینه نیاز دارد.
نبودِ مصالحهوقتی گزینه‌ای ظاهراً همه کیفیت‌ها را بهتر و همه هزینه‌ها را کمتر می‌کند، مشکوک باشید.

تمرین عملی — یکپارچه‌سازی سیستم قدیمی

سیستم:

فرانت‌اند Angular
بک‌اند Spring Boot
PostgreSQL
سیستم بیرونی SOAP
REST API جدید
پردازش دسته‌ای (Batch)

نیازمندی‌ها:

R1. مصرف‌کنندگان فعلی SOAP تا ۱۸ ماه کار کنند.
R2. مصرف‌کنندگان جدید از REST استفاده کنند.
R3. بار پیک سه برابر می‌شود.
R4. سیستم SOAP گاهی ۱۵ ثانیه طول می‌کشد.
R5. درخواست‌های کاربر در کمتر از ۲ ثانیه کامل شوند.
R6. داده نباید گم شود.
R7. کد مختص SOAP باید به‌تدریج حذف شود.

وظیفه شما:

  1. چهار محرک اصلی معماری را شناسایی کنید.
  2. مقایسه کنید: بک‌اند ← SOAP همگام؛ بک‌اند ← نمای REST ← SOAP همگام؛ بک‌اند ← یکپارچه‌سازی ناهمگام بادوام ← SOAP.
  3. دسترس‌پذیری، تأخیر، تغییرپذیری، سازگاری، عملیات و هزینه مهاجرت را مقایسه کنید.
  4. یک ADR بنویسید.
  5. یک سناریوی کیفی قابل اندازه‌گیری تعریف کنید.
  6. یک قاعده معماری خودکار تعریف کنید.
نمایش استدلال ممکن

محرک‌های محتمل:

تأخیر کاربر < ۲ ثانیه
سازگاری با SOAP تا ۱۸ ماه
عدم از دست رفتن داده
حذف تدریجی SOAP / تغییرپذیری

تصمیم پیشنهادی:

یک مرز یکپارچه‌سازی داخلی پایدار معرفی کنید.
هرجا تأیید فوری SOAP از نظر معنایی لازم نیست،
از پردازش ناهمگام استفاده کنید.
آداپترهای قدیمی را ایزوله کنید.

مزایا: ایزوله‌سازی سیستم قدیمی، حفاظت از تأخیر کاربر، مسیر مهاجرت.
هزینه‌ها: سازگاری نهایی، عملیات بیشتر، پیچیدگی مهاجرت.

مهم: اگر تأیید فوری SOAP از نظر کارکردی الزامی باشد، پردازش ناهمگام ممکن است اصلاً معتبر نباشد.

شفاف‌سازی نیازمندی‌ها و محرک‌ها.

چرا ارتباط ناهمگام می‌تواند دسترس‌پذیری را بهبود دهد؟

می‌تواند وابستگی زمانی به دسترس‌پذیری سیستم پایین‌دستی را حذف کند.

ارتباط ناهمگام چه مشکلاتی می‌آورد؟

سازگاری نهایی، پیام تکراری، ترتیب، ردیابی، عملیات.

چرا پایگاه‌داده مشترک به‌طور خودکار اشتباه نیست؟

در برخی زمینه‌ها تراکنش قوی و سادگی بر هزینه کوپلینگ آن می‌چربد.

چه زمانی انتزاع از نظر معماری موجه است؟

وقتی تنوع مورد انتظار یا محرکی دیگر، هزینه آن را توجیه کند.

چرا ویژگی‌های کیفی را اولویت‌بندی می‌کنیم؟

چون کیفیت‌ها با هم تعارض دارند.

هدف ماتریس تصمیم چیست؟

آشکار کردن اولویت‌ها و پیامدها، نه اثبات ریاضی یک تصمیم.

چرا تصمیم‌های سخت‌برگشت را زود اعتبارسنجی می‌کنیم؟

چون اصلاح اشتباه در آن‌ها گران است.

فرض در برابر شواهد؟

فرض باوری راستی‌آزمایی‌نشده است؛ شواهد آن را تأیید یا رد می‌کند.

سه شکل از شواهد معماری نام ببرید.

آزمون بار، نمونه اولیه، تله‌متری، تزریق خطا، تاریخچه حوادث.

میکروسرویس چگونه هم کوپلینگ را کم و هم زیاد می‌کند؟

کوپلینگ انتشار و کد را کم و کوپلینگ شبکه‌ای و معنایی را زیاد می‌کند.

حفاظ (guardrail) چیست؟

قاعده‌ای که کیفیت‌های معماری را حفظ می‌کند و مقداری آزادی پیاده‌سازی باقی می‌گذارد.

چرا متریک‌ها باید در زمینه تفسیر شوند؟

یک عدد به‌تنهایی مناسب بودن معماری را اثبات نمی‌کند.

یک Staff Engineer چگونه تصمیم‌گیری معماری را مقیاس‌پذیر می‌کند؟

شفاف‌سازی محرک‌ها، تسهیل تصمیم‌ها، مستندسازی دلایل، ساخت حفاظ‌ها و بازخورد.
