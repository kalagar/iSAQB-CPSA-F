اهداف یادگیری

در پایان این درس، باید بتوانید توضیح دهید چرا کار معماری اغلب باید تکراری (iterative) باشد، عدم قطعیت، ریسک، بازخورد و قابلیت پیش‌بینی را به هم مرتبط کنید، تصمیمات معماری را به‌صورت تدریجی اتخاذ کنید، و بازخورد ذی‌نفعان را به‌صورت نظام‌مند دریافت کنید.

عدم قطعیت در برابر ریسک

عدم قطعیت (Uncertainty)

هنوز به‌اندازه کافی نمی‌دانیم. نمونه‌ها: آیا API جدید می‌تواند ۱۰٬۰۰۰ درخواست در ثانیه را پردازش کند؟ آیا کاربران به نتایج بی‌درنگ نیاز دارند؟ آیا API یک تأمین‌کننده به‌اندازه کافی قابل‌اعتماد است؟ آیا تیم می‌تواند Kubernetes را به‌طور مؤثر عملیاتی کند؟

ریسک (Risk)

یک شرایط نامطمئن ممکن است بر یک هدف مهم اثر منفی بگذارد.

Uncertainty:
Can the external payment provider handle peak load?

Risk:
Checkout availability may fall below 99.95%.

هر عدم قطعیتی از نظر معماری مهم نیست. ریسک زمانی اهمیت دارد که در دسترس‌پذیری، امنیت، کارایی، نگهداشت‌پذیری، هزینه، انطباق (compliance) یا اهداف کسب‌وکار را تهدید کند.

ریسک معماری از محرک‌ها آغاز می‌شود

        ↓
Architecture Driver
Payment availability must not unnecessarily block ordering
        ↓
Architecture Decision
Synchronous payment interaction
        ↓
Risk
Payment outage causes checkout outage

معماری از هر دو استفاده می‌کند.

پیش‌بینی (Prediction)

استدلال درباره ترافیک مورد انتظار، خرابی‌ها، نیازمندی‌ها و نیازهای تیم.

بازخورد (Feedback)

مشاهده نمونه‌های اولیه، کاربران، متریک‌های محیط عملیاتی، توسعه‌دهندگان و خرابی‌های واقعی.

معماری قوی این‌ها را ترکیب می‌کند:

Reason → Decide → Validate → Learn → Adjust

تکنیک‌های بازخورد

بازخورد معماری می‌تواند از موارد زیر به‌دست آید:

  • نمونه اولیه (Prototype) — اعتبارسنجی امکان‌پذیری.
  • اثبات مفهوم (Proof of Concept) — آزمودن اینکه آیا یک فناوری یا یکپارچه‌سازی می‌تواند مسئله را حل کند.
  • اسپایک (Spike) — بررسی زمان‌محدود برای کاهش عدم قطعیت.
  • تست بار (Load Test) — اعتبارسنجی کارایی/مقیاس‌پذیری.
  • تست خرابی (Failure Test) — اعتبارسنجی تاب‌آوری.
  • بازبینی معماری (Architecture Review) — دریافت نظر ذی‌نفعان باتجربه.
  • بازخورد توسعه‌دهندگان — آشکار کردن کوپلینگ، مسئولیت‌های نامشخص، رابط‌های ضعیف.
  • بازخورد عملیات (Operations) — آشکار کردن تأخیر، نرخ خرابی، مصرف منابع، شکاف‌های رصدپذیری (observability).

دریافت نظام‌مند بازخورد ذی‌نفعان

به این تکیه نکنید: «اگر کسی مخالف باشد، به ما می‌گوید.» از یک فرآیند آگاهانه استفاده کنید:

Decision
   ↓
Identify affected stakeholders
   ↓
Identify concerns
   ↓
Choose feedback method
   ↓
Collect feedback
   ↓
Resolve conflicts / update decision

مثال تصمیم: تحویل ناهمگام اعلان‌ها (notifications). دغدغه‌های احتمالی ذی‌نفعان:

  • توسعه‌دهندگان ← پیچیدگی و آزمون
  • SRE ← قابلیت اطمینان و تلاش مجدد بروکر
  • محصول ← تأخیر قابل‌مشاهده برای کاربر
  • امنیت ← داده‌های رویداد حساس
  • مالی ← هزینه زیرساخت

بازخورد به معنای اجماع نیست

بازخورد به تصمیم‌گیری کمک می‌کند اما به معنای آن نیست که همه باید موافق باشند.

Stakeholder A prefers A.
Stakeholder B prefers B.
Architecture Driver favors B.
Decision: B.
Rationale documented.

معماری شامل مصالحه‌هاست.

ADRها به‌عنوان ابزار بازخورد

ADR-042: Asynchronous notification delivery

Context:
Notification outages currently block checkout.

Architecture Driver:
Checkout availability >= 99.95%.

Options:
1. Synchronous HTTP
2. Queue + async processing

Decision:
Use asynchronous delivery.

Risks:
- duplicates
- delayed emails
- broker dependency

Validation:
- failure test
- load test
- retry simulation

Review Date:
After first production release

بخش مهم اعتبارسنجی (validation) است. با تغییر شواهد می‌توان تصمیمات را بازبینی کرد.

سناریوی Staff Engineer

در حال طراحی یک پلتفرم پردازش سفارش هستید. نیازمندی‌ها: ۲٬۰۰۰ سفارش در دقیقه امروز؛ احتمال رشد به ۲۰٬۰۰۰؛ دسترس‌پذیری ۹۹.۹۵٪ برای پذیرش سفارش؛ سفارش‌های تأییدشده هرگز نباید گم شوند؛ SAP الزامی است؛ SAP گاهی از دسترس خارج می‌شود؛ تیم تاکنون Kafka را عملیاتی نکرده است.

SAP outages → outage simulation

توابع تناسب (Fitness Functions) — ارتباط پیشرفته

یک تابع تناسب یک بررسی خودکار یا قابل‌اندازه‌گیری است که نشان می‌دهد آیا معماری همچنان یک ویژگی مهم را برآورده می‌کند.

p95 latency < 500 ms
No forbidden dependency from Domain → Infrastructure
Recovery time < 60 seconds

این کانون اصلی LG 03-05 نیست، اما برای تمرین Staff Engineer بسیار مفید است زیرا بازخورد را پیوسته می‌کند.

دام‌های رایج آزمون CPSA-F

  1. تصمیمات معماری باید پیش از پیاده‌سازی نهایی شوند. — نادرست.
  2. تکرار ریسک معماری را حذف می‌کند. — نادرست.
  3. بازخورد فقط زمانی لازم است که یک تصمیم شکست بخورد. — نادرست.
  4. بازخورد فقط به معنای پایش محیط عملیاتی است. — نادرست.
  5. برنامه‌ریزی بیشتر همیشه قابلیت پیش‌بینی بیشتری ایجاد می‌کند. — نادرست.
  6. همه تصمیمات به یک میزان اعتبارسنجی نیاز دارند. — نادرست.
  7. بازخورد ذی‌نفعان به معنای الزامی‌بودن اجماع است. — نادرست.
