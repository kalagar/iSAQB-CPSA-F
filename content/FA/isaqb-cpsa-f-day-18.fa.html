انطباق معماری، زوال ساختاری و توابع تناسب

معماری موردنظر و معماری پیاده‌شده، میان‌بر به میان‌بر، از هم فاصله می‌گیرند. تصمیم‌ها را به قاعده تبدیل کنید و قاعده‌ها را به بررسی‌هایی که خودکار اجرا می‌شوند.

سطح: پایه (Foundation) محور: انطباق، انحراف، فرسایش، قواعد معماری، توابع تناسب برنامه درسی: CPSA-F 2025.1-rev2

اهداف یادگیری

در پایان این درس باید بتوانید انطباق معماری را توضیح دهید، معماری موردنظر را از پیاده‌شده تفکیک کنید، انحراف و فرسایش را تشخیص دهید، بازبینی کد / بازبینی معماری / تحلیل ابزارمحور را توضیح دهید، تصمیم‌ها را به قواعد صریح تبدیل کنید، آزمون‌های معماری و توابع تناسب را بشناسید، بررسی‌های ساختاری را از عملیاتی و بررسی‌های رویدادی را از پیوسته تفکیک کنید و حفاظ‌های سبک معماری طراحی کنید.

تطابق رسمیLG 05-03 — ارزیابی انطباق با تصمیم‌های معماری (R2). مرتبط با LG 05-01 و LG 05-02.

تمرکز رسمی CPSA-F

انتظار اصلی: ارزیابی اینکه آیا پیاده‌سازی با طراحی و تصمیم‌های معماری منطبق است.

برنامه درسی صراحتاً بازبینی کد، بازبینی معماری و تحلیل ابزارمحور را نام می‌برد. توابع تناسب توسعه‌ای عملی‌اند که از بازخورد پیوسته پشتیبانی می‌کنند — مفیدند، اما عین عبارت هدف یادگیری نیستند.

معماری موردنظر در برابر پیاده‌شده

موردنظر

آنچه طراحی و تصمیم‌گیری کرده‌ایم.

پیاده‌شده

آنچه کد و زمان اجرا واقعاً انجام می‌دهند.

معماری سالم این دو را به‌اندازه معقول همسو نگه می‌دارد — نه یکسان، اما نه متناقض.

انطباق معماری

انطباق می‌پرسد: آیا سیستم پیاده‌شده از قواعد و تصمیم‌های موردنظر پیروی می‌کند؟

Domain must not depend on UI.
Only Payment Adapter may use the payment SDK.
Services may not read another service's database directly.
All external communication must use TLS.
All events must contain eventId and schemaVersion.

چرا انطباق اهمیت دارد

بدون بررسی:

Design documentation
        ≠
Source code
        ≠
Runtime behavior

پیامدها: مستندات کهنه، وابستگی‌های پنهان، مرزهای تضعیف‌شده، افت ویژگی‌های کیفی.

انحراف در برابر فرسایش

انحراف (Drift)

پیاده‌سازی از طراحی موردنظر فاصله می‌گیرد.

One service bypasses another's
API and reads its database.

فرسایش (Erosion)

انحراف‌های انباشته ویژگی‌های معماری را تضعیف می‌کنند.

Many services now read
each other's databases.
Small deviations
      ↓
Repeated exceptions
      ↓
Drift
      ↓
Accumulation
      ↓
Erosion

زوال ساختاری چگونه رخ می‌دهد

معمولاً از طریق میان‌برهای محلی:

"We only need one direct DB query."

بعدتر:

"We already do it in one place."

در نهایت:

Many services
     ↓
Shared Database

قواعد معماری باید صریح باشند

ضعیف: «معماری را تمیز نگه دارید.»

قوی:

Domain must not depend on:
- web
- persistence implementation
- messaging implementation

حالا این قاعده قابل بازبینی، آزمون و خودکارسازی است.

تصمیم ← قاعده ← راستی‌آزمایی

Architecture Decision
       ↓
Architecture Rule
       ↓
Verification Method
       ↓
Feedback

نمونه ADR: هر ماژول دامنه مالک پایداری خودش است. قاعده مشتق: دسترسی بین‌ماژولی به پایگاه داده ممنوع است.

بهترین گزینه برای قواعد ساختاری عینی و تکرارپذیر.

آزمون‌های معماری

assert no classes in "domain"
       depend on classes in "infrastructure"
assert payment-sdk
       is only referenced from "payment-adapter"

آزمون‌های معماری، قواعد معماری را اجراپذیر می‌کنند.

نمونه لایه‌ای

domain
application
infrastructure
web
web → application
application → domain
infrastructure → domain

domain → nothing technical

بررسی‌های ممکن: دامنه نباید به فریم‌ورک وب وابسته باشد؛ دامنه نباید به فریم‌ورک پایداری وابسته باشد؛ لایه وب نباید مستقیماً به repository دسترسی داشته باشد.

نکته آزمونArchUnit ابزاری رایج در جاواست، اما مفهوم آزمون تحلیل ابزارمحور است، نه نام محصول.

نمونه میکروسرویس

تصمیم: هر سرویس مالک داده خودش است.

Intended:
Order → Order DB
Payment → Payment DB
Customer → Customer DB

Violation:
Order → Payment DB directly

راه‌های اعمال: اعتبارنامه‌های پایگاه داده، سیاست شبکه، بازبینی مخزن، بررسی‌های زیرساختی، لاگ‌های دسترسی.

حفاظ در برابر دروازه

دروازه (Gate)

تغییر را مسدود می‌کند.

Forbidden dependency
→ build fails

حفاظ (Guardrail)

رفتار را هدایت می‌کند و استثنای کنترل‌شده را می‌پذیرد.

Violation
→ warning
→ ADR required
دام«همه قواعد باید build را مسدود کنند» نادرست است. دروازه را برای قواعد عینی، پرارزش و مستعد بازگشت نگه دارید.

توابع تناسب (Fitness Functions)

یک تابع تناسب، یک ویژگی معماری را به‌شکل عینی ارزیابی می‌کند.

ساختاری

No domain → infrastructure
dependencies

کارایی

p95 latency < 500 ms

تاب‌آوری

Recovery < 60 s

امنیت

No public endpoint
without authentication

تابع تناسب در برابر تست معمولی

Unit test:
calculatePrice() returns 42.00

Fitness function:
No module violates allowed dependency direction.
پرسش کلیدیآیا این بررسی از یک ویژگی معماری محافظت می‌کند؟

ساختاری در برابر عملیاتی

ساختاری

نبود چرخه؛ استقلال دامنه از فریم‌ورک‌ها؛ SDK فروشنده فقط در آداپتورها.

عملیاتی

p95 تأخیر؛ دسترس‌پذیری؛ زمان failover؛ سن صف.

رویدادی در برابر پیوسته

رویدادی

Pull Request
→ CI
→ architecture dependency test

پیوسته

Production
→ observability
→ p95 latency
→ threshold

معماری مبتنی بر تابع تناسب

Define desired characteristic
       ↓
Define measurable fitness function
       ↓
Change architecture
       ↓
Measure
       ↓
Repeat
Goal:
Reduce Orders–Payments coupling.

Fitness function:
Payment SDK imports outside adapter = 0

انطباق در زمان اجرا

Decision:
Checkout should not depend on Notification availability.

Runtime fitness function:
Given Notification unavailable,
checkout acceptance remains within SLO.

برخی تصمیم‌های معماری را فقط می‌توان به‌صورت پویا اعتبارسنجی کرد — تحلیل ایستا نمی‌تواند هر تصمیمی را راستی‌آزمایی کند.

انطباق در نماهای مختلف

  • بلوک ساختمانی: قواعد وابستگی.
  • زمان اجرا: رفتار تعامل و خطا.
  • استقرار: جای‌گذاری زیرساخت و مرزها.
  • زمینه: وابستگی‌های بیرونی مستندنشده.

نشانه‌های زوال ساختاری

Increasing dependency cycles
Growing shared utility module
More cross-module DB access
Increasing architecture exceptions
Frequent changes across many modules
Docs contradicting code

دام ماژول مشترک و وابستگی‌های چرخه‌ای

shared-utils
├── SecurityUtils
├── DatabaseUtils
├── PaymentHelper
└── OrderRules

در ابتدا: استفاده مجدد. بعدتر: یک قطب کوپلینگ.

Orders → Payments
Payments → Customers
Customers → Orders

پیامدهای محتمل: تغییر مستقل دشوار، تست دشوار، مالکیت مبهم. تابع تناسب مفید:

Number of module cycles = 0

دسته‌های قواعد معماری

قواعد وابستگی · قواعد فناوری · قواعد مالکیت داده · قواعد ارتباطی · قواعد امنیتی · قواعد عملیاتی · قواعد استقرار. هر دسته به سازوکار راستی‌آزمایی متفاوتی نیاز دارد.

پرهیز از حکمرانی افراطی

Bad:
500 mandatory rules
+ manual approval for every decision

Better:
Few high-value rules
+ automation where possible
+ clear rationale
+ explicit exception process
نگاه Staff Engineerهدف، یکپارچگی بالای معماری با هزینه هماهنگی پایین است. هر قاعده‌ای که اضافه می‌کنید مالیاتی است که همه تیم‌ها برای همیشه می‌پردازند — فقط جایی وضعش کنید که چیزی بخرد.

چه چیزی را خودکار کنیم

نامزدهای خوب عینی، تکرارشونده، مهم، ارزان برای بررسی و مستعد بازگشت‌اند.

  • نبود چرخه وابستگی؛
  • نبود دسترسی بین‌سرویسی به پایگاه داده؛
  • فیلدهای الزامی رویداد؛
  • نبود وابستگی‌های ممنوع بین بسته‌ها.

دام‌های رایج آزمون CPSA-F

  • انطباق یعنی بررسی درستی نیازمندی‌ها. → نادرست
  • انطباق فقط دستی قابل بررسی است. → نادرست
  • بازبینی کد بی‌ربط است. → نادرست

  • همه قواعد باید build را مسدود کنند. → نادرست

  • مستندات به‌تنهایی انطباق را اثبات می‌کند. → نادرست

تمرین عملی

با این قواعد:

1. Domain must not depend on the web framework.
2. Presentation may not access repositories directly.
3. Payment SDK only in PaymentAdapter.
4. Domain modules must not depend cyclically.
5. Customer PII must never be logged.

و این یافته‌ها:

6 domain classes import the persistence framework.
3 controllers call repositories directly.
Payment SDK imported in 9 application classes.
Orders ↔ Customers form a cycle.
One production log contains customer email addresses.
  1. هر نقض را طبقه‌بندی کنید.
  2. تعیین کنید کدام‌یک را می‌توان به‌صورت ایستا خودکار کرد.
  3. تعیین کنید کدام‌یک به تحلیل زمان اجرا یا لاگ نیاز دارد.
  4. بزرگ‌ترین ریسک ماژولاریتی را شناسایی کنید.
  5. آزمون‌های معماری را تعریف کنید.
  6. یک تابع تناسب برای لاگ‌گیری PII تعریف کنید.
  7. تعیین کنید کدام بررسی‌ها باید CI را مسدود کنند.

پرسش‌های مروری

انطباق معماری چه چیزی را ارزیابی می‌کند؟

اینکه آیا پیاده‌سازی از طراحی و تصمیم‌های معماری موردنظر پیروی می‌کند.

کدام سه روش صریحاً به LG 05-03 مربوط‌اند؟

بازبینی کد، بازبینی معماری، تحلیل ابزارمحور.

انحراف در برابر فرسایش؟

انحراف = فاصله گرفتن از قصد؛ فرسایش = انحراف انباشته که ویژگی‌های معماری را تضعیف می‌کند.

چرا قواعد را صریح کنیم؟

فقط قاعده صریح قابل بازبینی، آزمون یا خودکارسازی است.

آزمون معماری چیست؟

بررسی اجراپذیر یک قاعده معماری، معمولاً درباره ساختار یا وابستگی‌ها.

تابع تناسب چیست؟

ارزیابی عینی یک ویژگی معماری.

ساختاری در برابر عملیاتی؟

ساختار و وابستگی‌ها در برابر رفتار زمان اجرا مانند تأخیر، دسترس‌پذیری و بازیابی.

رویدادی در برابر پیوسته؟

رویدادی با یک رخداد مانند pull request اجرا می‌شود؛ پیوسته محیط عملیات را رصد می‌کند.

چرا تحلیل ایستا نمی‌تواند هر تصمیمی را اعتبارسنجی کند؟

برخی تصمیم‌ها درباره رفتار زمان اجرا هستند و فقط در شرایط واقعی آشکار می‌شوند.

چرا حکمرانی افراطی خطرناک است؟

هزینه هماهنگی را بالا می‌برد، تیم‌ها را کند می‌کند و کار را به دور زدن قواعد سوق می‌دهد.
