دغدغه‌های فراگیر و مفاهیم فراگیر

دغدغه‌هایی را شناسایی کنید که کل معماری را در بر می‌گیرند، و مفاهیم منسجمی — برای پایداری، ارتباطات، مدیریت خطا، همزمانی، رابط کاربری، امنیت و رصدپذیری — در سطح Staff Engineer طراحی کنید.

سطح: پایه (Foundation) محور: دغدغه‌های فراگیر، مفاهیم فراگیر، وابستگی‌های متقابل برنامه درسی: CPSA-F 2025.1-rev2
در این صفحه اهداف یادگیری دغدغه فراگیر چیست؟ دغدغه در برابر مفهوم چرا دغدغه‌های فراگیر اهمیت دارند دغدغه فراگیر ≠ سرویس جداگانه پایداری به‌عنوان یک مفهوم ارتباطات به‌عنوان یک مفهوم مدیریت خطا لاگ‌گیری و رصدپذیری امنیت همزمانی (Concurrency) رابط کاربری بهره‌وری انرژی وابستگی‌های متقابل نمونه Staff Engineer: سیاست تلاش مجدد استانداردسازی در برابر انعطاف‌پذیری استفاده مجدد در سیستم‌ها دام‌های رایج آزمون CPSA-F اصطلاحات کلیدی تمرین عملی بسط Staff Engineer پرسش‌های مروری آزمون کوتاه منابع پیشرفت

اهداف یادگیری

در پایان این درس، باید بتوانید دغدغه‌های فراگیر را توضیح دهید، یک دغدغه را از یک مفهوم فراگیر تشخیص دهید، دغدغه‌های فراگیر را در یک معماری شناسایی کنید، مفاهیم منسجمی برای پایداری، ارتباطات، مدیریت خطا، همزمانی، رابط کاربری، امنیت و رصدپذیری طراحی کنید، وابستگی‌های متقابل بین مفاهیم فراگیر را شناسایی کنید، دام‌های رایج آزمون CPSA-F را تشخیص دهید، و این ایده‌ها را در سطح Staff Engineer به‌کار ببرید.

هم‌راستایی رسمیLG 03-10 — شناسایی، طراحی و پیاده‌سازی دغدغه‌های فراگیر (R1). مرتبط: LG 04-07 — مستندسازی و ارتباط دغدغه‌های فراگیر (R2).

دغدغه فراگیر چیست؟

یک دغدغه فراگیر بر چند بخش از معماری اثر می‌گذارد، به‌جای آنکه صرفاً متعلق به یک بلوک سازنده باشد.

Order Service
Customer Service
Payment Service
Inventory Service

همه این‌ها ممکن است به موارد زیر نیاز داشته باشند:

Logging
Authentication
Authorization
Error handling
Monitoring
Tracing
Configuration
Persistence rules
Communication conventions

این دغدغه‌ها چند عنصر معماری را همزمان در بر می‌گیرند.

دغدغه در برابر مفهوم

دغدغه فراگیر (Cross-Cutting Concern)

مسئله یا موضوعی که چند بخش از سیستم را تحت تأثیر قرار می‌دهد.

How should errors be handled consistently?

مفهوم فراگیر (Cross-Cutting Concept)

راه‌حل معماری‌ای که برای پاسخ به آن دغدغه به‌کار می‌رود.

Standard error taxonomy
Correlation IDs
Retry rules
Safe API error responses
Centralized exception mapping
Structured logging
تمایز مهم برای آزموندغدغه = آنچه باید حل شود. مفهوم = چگونگی حل آن توسط معماری.

چرا دغدغه‌های فراگیر اهمیت دارند

بدون یک مفهوم مشترک، تیم‌ها ممکن است همان مسئله را به‌شکل‌های متفاوت حل کنند.

Order Service    → JSON logs
Payment Service  → plain-text logs
Customer Service → stack traces
Inventory Service→ almost no logging

پیامدهای احتمالی:

  • عیب‌یابی دشوار؛
  • رصدپذیری ناهمگون؛
  • فقدان همبستگی (correlation) بین سرویس‌ها؛
  • افشای اطلاعات امنیتی؛
  • تلاش تکراری در پیاده‌سازی.

یک مفهوم لاگ‌گیری مشترک ممکن است این موارد را تعریف کند:

Log format
Log levels
Mandatory fields
Correlation IDs
Sensitive-data policy
Retention
Central collection

دغدغه فراگیر ≠ سرویس جداگانه

یک دغدغه فراگیر لزوماً به یک مؤلفه مستقل خودش نیاز ندارد.

لاگ‌گیری ممکن است با موارد زیر پیاده‌سازی شود:

  • یک کتابخانه مشترک؛
  • یک SDK پلتفرمی؛
  • یک ایجنت (agent)؛
  • یک سایدکار (sidecar)؛
  • پیکربندی فریم‌ورک؛
  • سیاست زیرساخت.

امنیت ممکن است شامل موارد زیر باشد:

  • یک ارائه‌دهنده هویت (identity provider)؛
  • قواعد API Gateway؛
  • مجوزدهی در سطح برنامه؛
  • مدیریت گواهی (certificate)؛
  • ذخیره‌سازی رازها (secrets)؛
  • لاگ‌گیری ممیزی (audit).

مفهوم می‌تواند چند عنصر معماری را در بر بگیرد.

پایداری (Persistence) به‌عنوان یک مفهوم فراگیر

پایداری چیزی بیش از انتخاب یک پایگاه‌داده است. یک مفهوم پایداری می‌تواند شامل این موارد باشد: مالکیت داده، مرزهای تراکنش، قراردادهای repository، مهاجرت schema، کش، کنترل همزمانی، سازگاری (consistency)، پشتیبان‌گیری و بازیابی، رمزنگاری، الزامات ممیزی.

Database:
PostgreSQL

Ownership:
Each domain module owns its tables.

Access:
Only repository adapters access SQL.

Transactions:
One business use case = one local transaction.

Schema Changes:
Versioned migrations.

Concurrency:
Optimistic locking.

ارتباطات به‌عنوان یک مفهوم فراگیر

سؤالات شامل این‌هاست: همگام یا ناهمگام؟ REST، پیام‌رسانی یا gRPC؟ قواعد تایم‌اوت؟ قواعد تلاش مجدد؟ ایدم‌پوتنسی؟ نسخه‌بندی؟ احراز هویت؟ سریال‌سازی؟ ردیابی (tracing)؟ معنای خطاها؟

Internal synchronous calls:
REST/JSON

Default timeout:
2 seconds

Retries:
Only idempotent operations

Correlation:
X-Correlation-ID propagated

Versioning:
Backward-compatible APIs

مدیریت خطا

بدون یک مفهوم مشترک:

Service A → HTTP 500 for everything
Service B → internal stack traces
Service C → swallows exceptions
Service D → retries forever

یک مفهوم قوی‌تر:

Business errors
→ explicit domain error codes

Transient technical errors
→ bounded retry

Permanent technical errors
→ fail fast + alert

Public API
→ no internal stack traces

Logs
→ technical detail + correlation ID

این کار قابلیت اطمینان، پشتیبان‌پذیری، امنیت و رصدپذیری را بهبود می‌دهد.

یک مفهوم رصدپذیری در سطح کل سیستم ممکن است این موارد را تعریف کند:

لاگ‌گیری

Structured JSON
Correlation ID

متریک‌ها

Tracing:

در سطح Staff Engineer، رصدپذیری موضوعی معماری است زیرا مشخص می‌کند آیا تیم‌ها می‌توانند رفتار محیط عملیاتی را درک کنند یا نه.

امنیت به‌عنوان یک دغدغه فراگیر

سؤالات شامل این‌هاست:

Who authenticates users?
How do services authenticate each other?
Where is authorization enforced?
How are secrets stored?
How is data encrypted?
What is audited?

مثال مفهوم:

Authentication:
Central OpenID Connect provider

Authorization:
Domain permissions enforced server-side

Service identity:
OAuth2 client credentials

Secrets:
Managed secret store

Transport:
TLS

Audit:
Security-relevant changes recorded

امنیت را نمی‌توان صرفاً با افزودن یک «مؤلفه امنیتی» حل کرد.

همزمانی (Concurrency)

همزمانی به‌صراحت در LG 03-10 نام برده شده است. یک مفهوم همزمانی می‌تواند به این موارد بپردازد: نخ‌ها (threads)، تسک‌های ناهمگام، وضعیت مشترک، همگام‌سازی، قفل‌گذاری، شرایط رقابتی (race conditions)، همزمانی خوش‌بینانه در برابر بدبینانه، ترتیب (ordering).

Order updates:
Optimistic locking

Background processing:
Worker pool

Shared mutable state:
Avoided between requests

Duplicate events:
Handled idempotently

رابط کاربری (UI / GUI)

یک مفهوم رابط کاربری می‌تواند این موارد را تعریف کند: ناوبری، مدیریت وضعیت، اعتبارسنجی، دسترس‌پذیری (accessibility)، نمایش خطا، سیستم طراحی، بومی‌سازی.

Design System:
Shared component library

Validation:
Client + authoritative server validation

Accessibility:
Defined accessibility target

Errors:
Consistent error component

بهره‌وری انرژی

بهره‌وری انرژی به‌صراحت در برنامه درسی نام برده شده است. دغدغه‌های معماری احتمالی: فرکانس polling، فراخوانی‌های شبکه غیرضروری، پردازش سنگین CPU، حجم داده منتقل‌شده، زمان‌بندی بار کاری، تخصیص بیش‌ازحد منابع ابری (overprovisioning).

به‌جای:

Every client polls every second

با توجه به نیازمندی‌ها، اعلان‌های push یا polling تطبیقی (adaptive) را در نظر بگیرید.

مفاهیم فراگیر مستقل از یکدیگر نیستند.

   ↓
Encrypted communication
   ↓

   ↓
Performance impact
Retry strategy
   ↓
More requests
   ↓
Higher load
   ↓
Possible cascading failure
Detailed logging
   ↓

   ↓

   ↓

برنامه درسی رسمی انتظار دارد معماران این وابستگی‌های متقابل را شناسایی و ارزیابی کنند.

نمونه Staff Engineer: سیاست تلاش مجدد (Retry Policy)

فرض کنید هر تیم به‌طور مستقل تصمیم می‌گیرد:

Retry failed calls 5 times immediately.

اگر Payment Service از کار بیفتد:

20 upstream instances
        ↓
each retries 5 times
        ↓
traffic multiplier
        ↓
Payment receives even more load

این می‌تواند یک طوفان تلاش مجدد (retry storm) ایجاد کند.

یک مفهوم تاب‌آوری مشترک ممکن است این موارد را تعریف کند:

Retries:
Maximum 2

Backoff:
Exponential + jitter

Allowed for:
Idempotent transient operations only

Timeout:
Per call + overall request budget

Circuit breaker:
For unstable dependencies
دیدگاه Staff Engineerاین نمونه‌ی معمول کار معماری بین‌تیمی در سطح Staff Engineer است: یک تصمیم محلی نادرست که در ۲۰ فراخوان‌کننده تکرار می‌شود، به یک قطعی سیستمی تبدیل می‌شود.

استانداردسازی در برابر انعطاف‌پذیری

یک مدل مفید این است:

Standardize architectural rules
Allow flexibility inside those rules

الزامی:

All services propagate trace IDs.
All logs are structured.
Secrets are not stored in source code.

انعطاف‌پذیر:

Java → Logback
Python → structlog
Node → pino

معماری رفتار موردنیاز را تعریف می‌کند، نه لزوماً یک کتابخانه پیاده‌سازی واحد را.

استفاده مجدد در سیستم‌ها

مفاهیم فراگیر می‌توانند در سیستم‌های مختلف استفاده مجدد شوند.

Company Authentication Concept
Company Logging Standard
API Error Model
Deployment Concept
Observability Standard

مزایا: کاهش تلاش طراحی، تسهیل onboarding، عملیات یکدست، حاکمیت (governance) قوی‌تر، کاهش تکرار اشتباهات.

دام‌های رایج آزمون CPSA-F

  1. یک دغدغه فراگیر همیشه به مؤلفه‌ی خودش نیاز دارد. — نادرست.
  2. دغدغه‌های فراگیر فقط موضوعات زیرساختی هستند. — نادرست.
  3. مفاهیم فراگیر مستقل از هم هستند. — نادرست.
  4. پایداری یعنی انتخاب یک پایگاه‌داده. — بیش‌ازحد محدود.
  5. هر تیم می‌تواند لاگ‌گیری را مستقل تعریف کند بدون تأثیر معماری. — نادرست.
  6. مفاهیم فراگیر نمی‌توانند در سیستم‌های مختلف استفاده مجدد شوند. — نادرست.
  7. استانداردسازی به معنای استفاده از دقیقاً یک کتابخانه پیاده‌سازی است. — نادرست.

اصطلاحات کلیدی برای به‌خاطرسپاری

دغدغه فراگیر (Cross-Cutting Concern)دغدغه‌ای که چند عنصر معماری را تحت تأثیر قرار می‌دهد.
مفهوم فراگیر (Cross-Cutting Concept)راه‌حل معماری منسجم برای یک دغدغه فراگیر.
وابستگی متقابل (Interdependency)رابطه‌ای که در آن یک مفهوم معماری بر مفهوم دیگری اثر می‌گذارد.
سازگاری (Consistency)اعمال یکدست قواعد معماری در بخش‌های مرتبط سیستم.
استفاده مجدد (Reuse)به‌کارگیری یک مفهوم تثبیت‌شده در چند سیستم.
حاکمیت (Governance)مکانیزم‌هایی که تضمین می‌کنند قواعد معماری رعایت می‌شوند.

  7. کدام تصمیمات باید در سطح سازمان گرفته شوند؟
  8. کدام انتخاب‌های پیاده‌سازی می‌توانند مختص هر تیم باقی بمانند؟

بسط Staff Engineer

یک نقشه مفهومی (concept map) بسازید:

                Security
                /      \
               /        \
      Communication    Logging
           |              |
           |              |
      Error Handling — Observability
           |
           |
       Persistence

برای هر اتصال، وابستگی متقابل را توضیح دهید.

مثال:

Logging ↔ Security

Logging needs enough detail for investigations.

But logs can expose:
- tokens
- passwords
- personal data

Therefore the logging concept must include security/privacy rules.

آیا هر دغدغه به یک سرویس جداگانه نیاز دارد؟

خیر.

چرا باید وابستگی‌های متقابل را ارزیابی کرد؟

زیرا یک مفهوم می‌تواند بر ویژگی‌ها یا محدودیت‌های مفهومی دیگر اثر بگذارد.

تلاش‌های مجدد چگونه می‌توانند بر کارایی و دسترس‌پذیری اثر بگذارند؟

تلاش مجدد می‌تواند تاب‌آوری را بهبود دهد اما می‌تواند بار را افزایش داده و طوفان تلاش مجدد ایجاد کند.

یک مفهوم پایداری علاوه بر انتخاب پایگاه‌داده چه چیزهایی می‌تواند شامل شود؟

مالکیت، تراکنش‌ها، مهاجرت‌ها، قفل‌گذاری، سازگاری، کش، پشتیبان‌گیری، الگوهای دسترسی، رمزنگاری.

آیا مفاهیم فراگیر می‌توانند استفاده مجدد شوند؟

بله.

چرا قواعد سراسری سازمان برای Staff Engineerها اهمیت دارد؟

این قواعد تصمیمات محلی ناهماهنگ را کاهش داده و قابلیت بهره‌برداری، امنیت، نگهداشت‌پذیری و همسویی را بهبود می‌بخشند.

پاسخ: پایداری (Persistence). نام‌گذاری متغیر، شاخه‌بندی Git، و نام‌گذاری تست واحد دغدغه‌های فراگیر معماری نیستند.
کدام گزینه درست است؟
پاسخ: معماران باید وابستگی‌های متقابل بین مفاهیم فراگیر را شناسایی و ارزیابی کنند. مفاهیم واقعاً بر یکدیگر اثر می‌گذارند، هر مؤلفه نیازی به استراتژی خطای خودش ندارد، و مفاهیم می‌توانند استفاده مجدد شوند.
چرا یک مفهوم لاگ‌گیری مشترک تعریف می‌شود؟
پاسخ: ناهماهنگی را کاهش داده و از رصدپذیری سراسری سیستم پشتیبانی می‌کند. این کار یک فریم‌ورک واحد را الزامی نمی‌کند، جایگزین پایش نمی‌شود، و به یک سرویس جداگانه نیاز ندارد.
یک سیاست الزام می‌کند داده‌های حساس هرگز در لاگ‌ها ظاهر نشوند. این نشان‌دهنده چیست؟
پاسخ: مفاهیم فراگیر می‌توانند وابستگی متقابل داشته باشند (لاگ‌گیری ↔ امنیت). این موضوع درباره کاهش کوپلینگ توسط لایه‌ها، جداسازی هر دغدغه، یا سطوح استقرار نیست.
