نمایش پاسخ

پرسش ۳. تیم فرض می‌کند بار اوج زیر ۲٬۰۰۰ درخواست در ثانیه می‌ماند. قوی‌ترین واکنش چیست؟

  1. آن را برای همیشه یک واقعیت قطعی بدانیم
  2. فرض را صریح کنیم و اگر تصمیم‌های مهمی به آن وابسته‌اند، اعتبارسنجی‌اش کنیم
  3. تا زمان شکست در محیط عملیاتی نادیده بگیریم
  4. مستقیماً آن را به یک ADR تبدیل کنیم
نمایش پاسخ

B — فرض‌ها مشروع‌اند، اما باید ثبت شوند و به تناسب آنچه بر آن‌ها استوار است اعتبارسنجی شوند.

پرسش ۴. کدام گزاره درباره محرک‌های معماری دقیق‌تر است؟

  1. هر نیازمندی یک محرک است
  2. فقط نیازمندی‌های کیفی می‌توانند محرک باشند
  3. محرک‌ها آن تأثیرهایی هستند که تصمیم‌های معماری را به‌طور معنادار شکل می‌دهند
  4. محدودیت‌ها هرگز نمی‌توانند محرک باشند
نمایش پاسخ

C — محرک با میزان تأثیر تعریف می‌شود، نه با دسته‌بندی. نیازمندی کارکردی، نیازمندی کیفی و محدودیت همه می‌توانند محرک باشند.

پرسش ۵. قوی‌ترین نیازمندی کیفی کدام است؟

  1. سیستم باید سریع باشد
  2. API باید عملکرد خوبی داشته باشد
  3. در بار اوج، ۹۵٪ جست‌وجوها در کمتر از ۴۰۰ میلی‌ثانیه کامل می‌شوند
  4. توسعه‌دهندگان باید کدشان را بهینه کنند
نمایش پاسخ

C — محرک (بار اوج)، معیار (۴۰۰ میلی‌ثانیه) و پوشش (۹۵٪) را نام می‌برد، پس آزمون‌پذیر است. بقیه آرزوهای غیرقابل‌اندازه‌گیری‌اند.

  4. تعداد کم رابط‌ها
نمایش پاسخ

B — مسئولیت‌های نامرتبط در یک عنصر جمع شده‌اند؛ هر تغییر نامرتبطی به همان نقطه می‌رسد.

پرسش ۷. افزودن یک تأمین‌کننده پرداخت جدید مستلزم تغییر در هشت ماژول نامرتبط است. کدام کیفیت مستقیم‌تر تهدید می‌شود؟

  1. قابلیت تغییر (Modifiability)
  2. دسترس‌پذیری برای معلولان (Accessibility)
  3. قابلیت انتقال (Portability)
  4. یادگیری‌پذیری (Learnability)
نمایش پاسخ

A — هزینه یک تغییر قابل‌پیش‌بینی، دقیقاً تعریف قابلیت تغییر است.

پرسش ۸. یک توسعه‌دهنده پیشنهاد می‌کند دور یک کتابخانه پایدار که بعید است تغییر کند، لایه انتزاع بگذاریم. بهترین پاسخ چیست؟

  1. هر وابستگی به انتزاع نیاز دارد
  2. انتزاع تنها وقتی ارزشمند است که منافعش پیچیدگی افزوده را توجیه کند
  3. انتزاع همیشه معماری را بهتر می‌کند
  4. همه کتابخانه‌های ثالث باید پنهان شوند
نمایش پاسخ

B — انتزاع هزینه واقعی دارد. بدون تنوع مورد انتظار یا محرکی دیگر، این هزینه چیزی نمی‌خرد.

پرسش ۹. بهترین گزاره درباره جفت‌شدگی (coupling) کدام است؟

  1. معماری خوب جفت‌شدگی را حذف می‌کند
  2. جفت‌شدگی همیشه نامطلوب است
  3. وابستگی‌ها باید مناسب و آگاهانه کنترل‌شده باشند
  4. جفت‌شدگی فقط بین میکروسرویس‌ها وجود دارد
نمایش پاسخ

C — سیستمی بدون هیچ جفت‌شدگی هیچ کاری نمی‌کند. هدف، وابستگی‌های آگاهانه، آشکار و توجیه‌شده است.

پرسش ۱۰. یک سرویس مستقلاً قابل استقرار است، اما مصرف‌کنندگانش به ترتیب مستندنشده رویدادها تکیه می‌کنند. این چیست؟

  1. بدون جفت‌شدگی
  2. جفت‌شدگی معنایی
  3. فقط جفت‌شدگی استقرار
  4. فقط جفت‌شدگی کد منبع
نمایش پاسخ

B — وابستگی به معنا و ترتیب است، نه به کد یا استقرار. استقرار مستقل آن را پنهان می‌کند، نه حذف.

بخش ج — الگوها، سبک‌ها و مصالحه‌ها

پرسش ۱۱. یک تیم ۱۰ نفره با بار متوسط، نیازمندی‌های تراکنشی قوی و تجربه عملیاتی کم. قوی‌ترین گزاره کدام است؟

  1. میکروسرویس‌ها به‌طور خودکار ترجیح داده می‌شوند
  2. یک مونولیت ماژولار می‌تواند مناسب باشد اگر استقرار و مقیاس‌پذیری مستقل محرک‌های ضعیفی باشند
  3. معماری رویدادمحور الزامی است
  4. هر قابلیت به فرایند مجزای خود نیاز دارد
نمایش پاسخ

B — با محرک‌های توزیع ضعیف و محرک‌های تراکنشی قوی، توزیع بیشتر هزینه اضافه می‌کند. محرک‌ها سبک را تعیین می‌کنند.

پرسش ۱۲. پیامد معمول پیام‌رسانی نامتقارن (asynchronous) چیست؟

  1. همه جفت‌شدگی‌ها را حذف می‌کند
  2. سازگاری فوری را تضمین می‌کند
  3. می‌تواند جداسازی زمانی را بهبود دهد و در عوض سازگاری نهایی و پیچیدگی عملیاتی اضافه کند
  4. نیاز به مدیریت پیام‌های تکراری را از بین می‌برد
نمایش پاسخ

C — نامتقارن‌سازی، سازگاری فوری و عملیات ساده را با جداسازی زمانی و بافر کردن معاوضه می‌کند.

پرسش ۱۳. پیش از افزودن کش، مهم‌ترین پرسش معماری چیست؟

  1. کدام محصول کش زیباترین لوگو را دارد؟
  2. چه میزان کهنگی داده قابل‌قبول است و چه هدف تأخیر و باری باید محقق شود؟
  3. کدام محصول محبوب‌تر است؟
  4. آیا می‌توان همه چیز را برای همیشه کش کرد؟
نمایش پاسخ

B — نخست هدف کیفی و تازگی قابل‌قبول؛ انتخاب فناوری پس از آن می‌آید.

پرسش ۱۴. الگوها (patterns) چه هستند؟

  1. بهترین‌شیوه‌های مستقل از زمینه
  2. رویکردهای راه‌حل قابل استفاده مجدد، همراه با منافع و پیامدها
  3. جانشین تصمیم‌های معماری
  4. تضمین کیفیت
نمایش پاسخ

B — یک الگو راه‌حل را همراه با مصالحه‌ای که تحمیل می‌کند مستند می‌کند و هرگز نیاز به تصمیم‌گیری را حذف نمی‌کند.

پرسش ۱۵. یک پایگاه‌داده مشترک تراکنش‌های ساده می‌دهد اما جفت‌شدگی شِما ایجاد می‌کند. این چیست؟

  1. اثباتی بر این‌که پایگاه‌داده مشترک همیشه غلط است
  2. یک مصالحه معماری
  3. به‌طور تعریفی نقض انطباق
  4. فقط یک مشکل مستندسازی
نمایش پاسخ

B — منفعت و هزینه با هم، سنجیده در برابر محرک‌های همین سیستم، دقیقاً همان مصالحه است.

بخش د — رابط‌ها و مفاهیم فراگیر

  4. زبان پیاده‌سازی
نمایش پاسخ

C — قرارداد یعنی آنچه مصرف‌کننده می‌تواند بر آن تکیه کند. نحو تنها، همه حالت‌های خطا را تعریف‌نشده می‌گذارد.

پرسش ۱۷. یک مصرف‌کننده کد ۴۰۴ را «حذف‌شده برای همیشه» تفسیر می‌کند، اما ارائه‌دهنده فقط «در حال حاضر یافت نشد» را تضمین می‌کند. این چیست؟

  1. جفت‌شدگی استقرار
  2. جفت‌شدگی معنایی
  3. جفت‌شدگی بصری
  4. جفت‌شدگی سخت‌افزاری
نمایش پاسخ

B — نحو مطابق است؛ معنا نه. عدم تطابق معنا همان جفت‌شدگی معنایی است.

پرسش ۱۸. شش تیم از راهبردهای retry ناسازگار استفاده می‌کنند. بهترین واکنش چیست؟

  1. اجازه retry نامحدود در همه‌جا
  2. تعریف یک مفهوم فراگیر منسجم برای تاب‌آوری و ارتباطات
  3. افزودن فقط نمودارهای زمان اجرا
  4. تغییر نام سرویس‌ها
نمایش پاسخ

B — رفتار retry، timeout و backoff یک دغدغه سیستم‌گستر است و به یک مفهوم منسجم نیاز دارد، نه شش اختراع محلی.

پرسش ۱۹. کدام گزاره درست است؟

  2. یک مفهوم فراگیر راه‌حلی منسجم در میان چندین عنصر ارائه می‌دهد

  4. لاگ‌برداری نمی‌تواند فراگیر باشد

پرسش ۲۰. لاگ‌برداری تفصیلی از درخواست‌ها اشکال‌زدایی را بهتر می‌کند اما خطر افشای داده‌های شخصی دارد. این چیست؟

  3. اثباتی بر این‌که لاگ‌برداری باید خاموش شود

نمایش پاسخ

پرسش ۲۴. یک تست کارایی، یک فرض کلیدی را رد می‌کند. گام بعدی چیست؟

  2. بازارزیابی فرض و همه تصمیم‌هایی که به آن وابسته بودند

  4. توقف تست

  2. انتخاب فناوری بر اساس مُد روز.
  3. برخورد با الگوها به‌عنوان راه‌حل جهان‌شمول.
  4. برخورد با یک سنجه به‌عنوان نتیجه‌گیری.
  5. اشتباه گرفتن نمودار با نمای معماری.
  6. این فرض که نامتقارن یعنی بدون جفت‌شدگی.
  7. این فرض که انتزاع به‌طور خودکار خوب است.
  8. این فرض که مستندسازی بیشتر همیشه بهتر است.

تمرین عملی

برای Claims Platform در بخش ح، این موارد را آماده کنید:

1. Five architecture drivers
2. Five risks
3. Two explicit assumptions
4. Three candidate decisions
5. Consequences of each
6. One availability scenario
7. One modifiability scenario
8. Three architecture rules
9. One automated conformance/fitness check
10. One ADR title + rationale

در سراسر تمرین از این زنجیره استفاده کنید:

Evidence → Driver → Option → Trade-Off → Decision → Validation

نمونه حل‌شده:

Evidence:
Fraud provider sometimes takes 12 seconds.

Driver:
Response < 2 seconds; availability >= 99.95%.

Assumption:
Fraud approval may happen after durable claim acceptance.

Option:
Persist claim, acknowledge it, evaluate fraud asynchronously.

Benefit:
Fraud latency no longer blocks acknowledgement.

Cost:
Eventual consistency and retry/failure handling.

Validation:
Simulate provider outage and verify availability + no lost claims.
لولای تصمیماگر فرض غلط باشد، تصمیم را بازنگری کنید. آنچه طرح بر آن استوار است، فرض است — نه صف پیام.
