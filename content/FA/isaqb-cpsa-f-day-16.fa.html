رابط‌ها، تصمیم‌های معماری و ADR

رابط یک قرارداد است، نه یک امضای متد — و تصمیمی بدون دلیل، تصمیمی است که هیچ‌کس نمی‌تواند با اطمینان بازبینی‌اش کند. هر دو را آن‌گونه مستند کنید که یک Staff Engineer مستند می‌کند.

سطح: پایه (Foundation) محور: قرارداد رابط، کوپلینگ معنایی، دلیل تصمیم، ADR برنامه درسی: CPSA-F 2025.1-rev2
در این صفحه اهداف یادگیری رابط به‌عنوان قرارداد نمونه: رابط پرداخت رابط درونی و بیرونی رابط ارائه‌شده و موردنیاز کوپلینگ معنایی نسخه‌بندی و سازگاری پرسش‌های Staff Engineer درباره رابط تصمیم معماری چیست؟ اهمیت معماری چرا تصمیم‌ها را مستند کنیم؟ مبانی ADR نمونه ADR وضعیت ADR وابستگی میان تصمیم‌ها چه زمانی ADR ننویسیم ADR صورت‌جلسه نیست ADR و حلقه‌های بازخورد مستند رابط + ADR دام‌های رایج آزمون اصطلاحات کلیدی تمرین عملی پرسش‌های مروری منابع پیشرفت

اهداف یادگیری

در پایان این درس باید بتوانید توضیح دهید چه چیزی به مستند رابط تعلق دارد، رابط درونی را از بیرونی تفکیک کنید، قرارداد را از جزئیات پیاده‌سازی جدا کنید، توضیح دهید چرا تصمیم‌های معماری به دلیل نیاز دارند، هدف و ساختار ADR را شرح دهید، وابستگی میان تصمیم‌ها را شناسایی کنید و از ADR به‌عنوان ابزار Staff Engineer استفاده کنید.

رابط به‌عنوان قرارداد معماری

یک رابط چیزی بیش از امضای متد است.

Building Block A
      |
      | Interface Contract
      v
Building Block B

قراردادهای مفید ممکن است شامل معناشناسی، محدودیت ورودی، تضمین خروجی، رفتار خطا، انتظارات زمانی، امنیت، خاصیت idempotency، نسخه‌بندی و پیش‌شرط/پس‌شرط باشند.

نمونه: رابط پرداخت

Purpose:
Authorize and capture a payment.

Request:
POST /payments

Required:
orderId
amount
currency
paymentMethodToken

Errors:
409 PAYMENT_ALREADY_PROCESSED
422 PAYMENT_DECLINED
503 PAYMENT_PROVIDER_UNAVAILABLE

Idempotency:
Idempotency-Key required

Security:
OAuth2 service identity

هر خط بالا از نظر معماری مهم است: هر کدام نحوه ساخت مصرف‌کننده را تغییر می‌دهد.

رابط درونی در برابر بیرونی

درونی

میان بلوک‌های ساختمانی داخل سیستم.

بیرونی

از مرز سیستم عبور می‌کند.

رابط‌های بیرونی معمولاً به مستندسازی قوی‌تری در زمینه نسخه‌بندی، سازگاری، SLA و امنیت نیاز دارند — اما این گزاره که «فقط رابط‌های بیرونی نیاز به مستند دارند» نادرست است.

رابط ارائه‌شده در برابر موردنیاز

Order Service

Provides:
Order API

Requires:
Payment API
Inventory API

این کار وابستگی‌ها را صریح می‌کند و گراف فراخوانی ضمنی را به چیزی تبدیل می‌کند که بازبین می‌تواند درباره‌اش استدلال کند.

کوپلینگ معنایی

پایداری نحو، کوپلینگ پایین را تضمین نمی‌کند.

{"status":"READY"}

اگر معنای READY مستند نشده باشد، مصرف‌کننده به‌جای قرارداد به فرض‌ها کوپل می‌شود. محتوای پیام هرگز تغییر نمی‌کند — اما درک مشترک بی‌سروصدا تغییر می‌کند.

نسخه‌بندی و سازگاری

  • توسعه سازگار با نسخه قبل؛
  • نسخه‌بندی صریح API؛
  • تکامل شمای رویداد؛
  • سیاست منسوخ‌سازی؛
  • آزمون سازگاری.

نگاه Staff Engineerاین نُه پرسش یک چک‌لیست بازبینی‌اند. رابطی که نتواند به آن‌ها پاسخ دهد، بعداً توسط یک حادثه عملیاتی پاسخ داده می‌شود.

تصمیم معماری چیست؟

تصمیمی با پیامدهای مهم برای ساختار، ویژگی‌های کیفی، وابستگی‌ها، فناوری، تکامل آینده یا هزینه تغییر.

Use Kafka for order events.
Use PostgreSQL for transactions.
Use a modular monolith instead of microservices.
Use OIDC for authentication.

اهمیت معماری

High impact?
Hard to reverse?
Affects multiple teams?
Influences quality requirements?
Constrains future choices?

اگر پاسخ چند مورد مثبت باشد، تصمیم احتمالاً معماری است.

چرا تصمیم‌ها را مستند کنیم؟

بدون دلیل، مهندسان آینده می‌دانند چه چیزی وجود دارد اما نمی‌دانند چرا.

Decision:
Use PostgreSQL.

Reason:
- strong consistency
- relational reporting
- existing operational expertise

نکته آزمونهیچ قالب واحدی از ADR برای CPSA-F الزامی نیست. آنچه اهمیت دارد حفظ زمینه، دلیل و پیامدهاست.

نمونه ADR

# ADR-017: Asynchronous Order-to-SAP Integration

Status:
Accepted

Context:
SAP outages must not block order acceptance.

Drivers:
Availability
Durability
Throughput

Options:
1. Direct REST
2. Database queue
3. Kafka

Decision:
Publish accepted orders to Kafka.

Positive:
+ decouples order acceptance from SAP
+ buffers bursts

Negative:
- eventual consistency
- duplicate handling
- operational complexity

Validation:
- throughput test
- broker failure test
- SAP outage simulation

وضعیت ADR

Proposed
Accepted
Rejected
Deprecated
Superseded

تاریخ معماری را بی‌سروصدا بازنویسی نکنید. تصمیم‌های قدیمی را صریحاً جایگزین (superseded) کنید تا زنجیره استدلال خوانا بماند.

وابستگی میان تصمیم‌ها

Use async events
      ↓
Need idempotent consumers
      ↓
Need event identifiers
      ↓
Need schema versioning

تصمیم‌های معماری یک گراف می‌سازند، نه یک فهرست.

چه زمانی ADR ننویسیم

تمرین عملی

برای یک سرویس تشخیص تقلب (Fraud Service):

  1. هدف، ورودی‌ها، خروجی‌ها، خطاها، timeout، تلاش مجدد، idempotency، نسخه‌بندی و امنیت را تعریف کنید.
  2. REST همگام، پیام‌رسانی ناهمگام و کش محلی را مقایسه کنید.
  3. برای انتخاب خود یک ADR کوتاه بنویسید.
  4. سه تصمیم وابسته به آن را شناسایی کنید.

پرسش‌های مروری

LG 04-06 چه چیزی را الزام می‌کند؟

اینکه رابط‌ها به‌عنوان قرارداد مستند شوند، نه صرفاً به‌عنوان نحو.

چرا امضای متد کافی نیست؟

معناشناسی، خطاها، زمان‌بندی، امنیت، idempotency و قواعد تکامل را حذف می‌کند.

رابط ارائه‌شده در برابر موردنیاز؟

ارائه‌شده = قابلیتی که عرضه می‌شود؛ موردنیاز = قابلیتی که به آن وابسته‌ایم.

چه چیزی یک تصمیم را از نظر معماری مهم می‌کند؟

تأثیر بالا، برگشت دشوار، پیامد بین‌تیمی، اثر بر کیفیت یا محدودسازی آینده.

چرا دلیل تصمیم را حفظ کنیم؟

تا مهندسان آینده بدانند تصمیم در زمینه خودش چرا منطقی بوده است.

ADR چیست؟

ثبت مستند یک تصمیم معماری همراه با زمینه، دلیل و پیامدها.

پنج فیلد ADR را نام ببرید.

عنوان، وضعیت، زمینه، تصمیم، پیامدها.

چرا ADRهای جایگزین‌شده را نگه داریم؟

تاریخچه استدلال را حفظ می‌کنند و از تکرار گزینه‌های ردشده جلوگیری می‌کنند.

چرا وابستگی تصمیم‌ها مهم است؟

هر تصمیم برای تصمیم‌های دیگر الزام ایجاد می‌کند؛ تصمیم‌ها گراف‌اند.

تفاوت ADR با صورت‌جلسه چیست؟

صورت‌جلسه گفت‌وگو را ثبت می‌کند؛ ADR دانش معماری را.
