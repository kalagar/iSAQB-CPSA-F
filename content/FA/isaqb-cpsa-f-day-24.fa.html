بازبینی آزمون II و ترمیم نهایی نقاط ضعف

تمایزهای دشوار و استدلال «دو گزینه درست به‌نظر می‌رسند» — چیزی که پیش از آزمون آزمایشی رسمی iSAQB لازم دارید — به‌همراه یک بازبینی کامل معماری در نقش Staff Engineer.

سطح: پایه (Foundation) تمرکز: تمایزهای دشوار، تمرین ابهام، مطالعه موردی بازبینی برنامه درسی: CPSA-F 2025.1-rev2
در این صفحه مهارت اصلی آزمون آزمون اهمیت محرک ویژگی، نیازمندی و سناریوی کیفی محدودیت در برابر تصمیم نحو در برابر معنای رابط جفت‌شدگی معنایی انسجام و محلی‌بودن تغییر الگو در برابر تصمیم نماهای معماری — نگاشت دشوار تصمیم، دلیل، پیامد تکامل ADR تحلیل، اعتبارسنجی و انطباق تحلیل کیفی در برابر کمی تله متریک انحراف، تکامل و فرسایش قاعده در برابر تابع تناسب تمرین‌های «دو گزینه درست» بازبینی معماری Staff Engineer تمرین شما پاسخ پیشنهادی جدول نهایی تمایزها پرسش‌های مرور منابع رسمی iSAQB منابع پیشنهادی حفظ کردن در برابر درک کردن بعدی — روز ۲۵ پیشرفت

مهارت اصلی آزمون

روزهای ۱ تا ۲۳ کامل شده‌اند. امروز آخرین ترمیم مبتنی بر تئوری است: وقتی چند گزینه محتمل به‌نظر می‌رسند، آزمون یک «رویه استدلال» را می‌سنجد، نه یک تعریف را.

1. What concept is actually being tested?
2. What are the architecture drivers?
3. What constraints apply?
4. Which answer addresses the concern most directly?
5. Which makes fewer unsupported assumptions?
6. Which avoids unjustified absolutes?

این زنجیره استدلال را ترجیح دهید:

Concern → Driver → Options → Trade-off → Decision → Evidence
نگاه Staff Engineerاین یک ترفند آزمون نیست. دقیقاً همان شکلی است که یک بازبینی معماری معتبر در برابر تیم‌هایی که اختلاف‌نظر دارند استدلال می‌شود.

محرک معماری — آزمون اهمیت

R1

Users can sort claims by date.

در سطح قابلیت. بعید است معماری را تغییر دهد.

R2

Claims remain available when
Fraud Provider fails.

می‌تواند تعامل زمان اجرا، مدیریت خطا، پایداری، ارتباط، سیاست تایم‌اوت/تلاش مجدد و سازگاری داده را تغییر دهد.

پرسشی که باید پرسیداگر این نیازمندی به‌طور اساسی تغییر کند، آیا معماری ما احتمالاً تغییر می‌کند؟ اگر بله، احتمالاً یک محرک معماری است.
تلهقابل اندازه‌گیری بودن به‌طور خودکار به معنای اهمیت معماری نیست.

نحو در برابر معنای رابط

رویداد:

claimId: string
status:  APPROVED

نحو، فیلدها، انواع، اسکیما و سریال‌سازی را توصیف می‌کند. معنا به این پرسش‌ها پاسخ می‌دهد:

What exactly does APPROVED mean?
Can it later change?
Can delivery duplicate?
Does ordering matter?
When is the event final?
میان‌بررابط پایدار نیازمند «معنای مشترک» است، نه صرفاً JSON سازگار.

جفت‌شدگی معنایی

سرویس B فرض می‌کند:

CustomerUpdated always arrives
before InvoiceCreated.

هیچ قراردادی این را تضمین نمی‌کند. این جفت‌شدگی معنایی/رفتاری از راه یک فرض ترتیبی مستندنشده است.

تلهتغییر REST به Kafka آن را از بین نمی‌برد. جفت‌شدگی در پروتکل نیست، در همان فرض است.

نماهای معماری — نگاشت دشوار

پرسشنما
چه سیستم‌های بیرونی مشارکت دارند؟زمینه (Context)
چه بخش‌های نرم‌افزاری داخلی وجود دارند؟بلوک ساختمانی
وقتی Fraud تایم‌اوت می‌شود چه رخ می‌دهد؟زمان اجرا
Fraud Adapter کجا مستقر شده است؟استقرار
میان‌برنما یک منظر معماری ذی‌نفع‌محور است. نمودار تنها یکی از بازنمایی‌های ممکن آن است.

تصمیم، دلیل، پیامد

Decision:
Use durable asynchronous SAP synchronization.

Rationale:
Order acceptance must survive SAP outages and
delayed sync is acceptable.

Positive consequence:
Temporal decoupling.

Negative consequence:
Eventual consistency and duplicate handling.

اینها سه قطعه متفاوت از دانش معماری‌اند — گزینه‌ای که آنها را در هم می‌آمیزد معمولاً پاسخ ضعیف‌تر است.

تکامل ADR

Proposed → Accepted → Deprecated/Superseded
چرا مهم استوقتی تصمیمی تغییر می‌کند، تاریخچه را حفظ کنید و دلیل قدیمی را بی‌سروصدا بازنویسی نکنید. رکورد جایگزین‌شده توضیح می‌دهد چرا سیستم امروز این شکلی است.

تحلیل، اعتبارسنجی و انطباق

Analysis:
Will the architecture satisfy required qualities?

Validation:
Does observed evidence support our assumptions?

Conformance:
Does implementation follow intended architecture?

نمونه‌ها:

Analyze synchronous Fraud dependency  → analysis
Inject Fraud outage                   → validation/evidence
Check domain cannot import vendor SDK → conformance

انحراف، تکامل و فرسایش

  • تکامل عمدی نیت معماری را از راه یک تصمیم صریح تغییر می‌دهد.
  • انحراف (Drift) واگرایی میان پیاده‌سازی و نیت فعلی معماری است.
  • فرسایش (Erosion) انحراف مضرِ انباشته است که ویژگی‌های معماری را تضعیف می‌کند.
One unauthorized direct DB access → drift

Years of cross-DB access causing
coordinated releases             → erosion

تمرین‌های دشوار «دو گزینه درست به‌نظر می‌رسند»

نیازمندی p95 < 500 ms و مشاهده p95 = 900 ms. حالا چه؟

الف. فوراً PostgreSQL را جایگزین کن · ب. نیازمندی نقض شده است؛ پیش از انتخاب راه‌حل، عوامل مؤثر را تحلیل کن · ج. Redis اضافه کن · د. به میکروسرویس بشکن

پاسخ: ب. شواهد مسئله را مشخص می‌کنند، نه ریشه آن را.

Fraud API ۱۵ ثانیه طول می‌کشد؛ هدف کاربر کمتر از ۲ ثانیه است. اولین پرسش؟

الف. کدام صف؟ · ب. آیا ارزیابی تقلب می‌تواند پس از پذیرش پایدارِ ادعا کامل شود؟ · ج. Kafka یا RabbitMQ؟ · د. چند replica؟

پاسخ: ب. معنای کسب‌وکاری بر مکانیزم مقدم است.

بیست کلاس یک SDK فروشنده را import می‌کنند و فروشنده جدیدی در راه است. کدام کیفیت غالب است؟

الف. کارایی · ب. محلی‌سازی تغییر / تغییرپذیری · ج. دسترس‌پذیری برای معلولان · د. یکدستی رابط کاربری

پاسخ: ب.

سازمان استفاده از Java 21 را الزامی کرده است. کدام گزاره درست است؟

الف. Java 21 خودبه‌خود بهینه است · ب. Java 21 یک محدودیت است، حتی اگر معماران هم همان را انتخاب می‌کردند · ج. یک نیازمندی کیفی است · د. یک نمای زمان اجراست

پاسخ: ب. آنچه آن را محدودیت می‌کند تحمیلی بودن انتخاب است، نه کیفیت آن.

Product Owner مرز سیستم و سیستم‌های همسایه را می‌خواهد. چه تولید می‌کنید؟

الف. نمودار کلاس تفصیلی · ب. نمای زمینه متناسب با ذی‌نفع · ج. مانیفست‌های Kubernetes · د. DDL

پاسخ: ب.

یک ADR می‌گوید: Decision: Kafka. Reason: Kafka is scalable. ضعف اصلی؟

الف. ADR نمی‌تواند نام فناوری ببرد · ب. دلیل به‌اندازه کافی به محرک‌ها، جایگزین‌ها و پیامدها گره نخورده است · ج. Kafka مقیاس‌پذیر نیست · د. ADR به کد منبع نیاز دارد

پاسخ: ب.

تیم‌ها سیاست‌های تلاش مجدد متفاوتی دارند. مفهوم فراگیر درست چیست؟

الف. تعداد تلاش یکسان برای هر عملیات · ب. اصول مشترک برای خطاهای واجد شرایط، سقف‌ها، backoff، idempotency و استثناها · ج. غیرفعال کردن همه تلاش‌های مجدد · د. فقط انتخاب توسعه‌دهنده

پاسخ: ب.

قاعده: Domain → Infrastructure forbidden. بیلد یک نقض را تشخیص می‌دهد. این چیست؟

الف. شکست سناریوی کیفی · ب. نقض انطباق · ج. مشکل نمای زمینه · د. تعارض نیازمندی

پاسخ: ب.

کدام گزاره درباره انتخاب الگو قابل دفاع است؟

الف. رویدادمحور برای سیستم‌های مقیاس‌پذیر بهترین است · ب. لایه‌ای همیشه ساده‌ترین است · ج. الگوها را در برابر محرک‌ها و پیامدها ارزیابی کن · د. میکروسرویس تغییرپذیری را بیشینه می‌کند

پاسخ: ج. سه گزینه دیگر مطلق‌گویی بی‌پشتوانه‌اند.

پنج تیم مکرراً تصمیم‌های معماری ناسازگار می‌گیرند. پاسخ Staff Engineer؟

الف. شخصاً هر PR را تأیید کن · ب. محرک‌های مشترک، رکوردهای تصمیم، اصول، سازوکار بازبینی و حفاظ‌های خودکار را برقرار کن · ج. همه کد را به یک تیم بده · د. تصمیم محلی را ممنوع کن

پاسخ: ب. اهرم مقیاس می‌گیرد؛ بازبینی شخصی نه.

بازبینی عملی معماری در نقش Staff Engineer

Angular Web
    ↓
Spring Boot
 ├── PostgreSQL
 ├── Legacy SOAP
 ├── New REST
 ├── Document Service
 └── Kafka

شواهد:

 1. SOAP sometimes takes 20 seconds.
 2. User-facing p95 target < 2 seconds.
 3. Some operations need immediate external confirmation.
 4. Others may synchronize within 15 minutes.
 5. Four teams use different timeout/retry policies.
 6. 23 classes know SOAP-generated types.
 7. SOAP retires within two years.
 8. No accepted transaction may be lost.
 9. Async troubleshooting is difficult.
10. Teams want independent feature delivery.

نگاه Staff Engineerانجام این کار از صفحه سفید — نه تشخیص آن وقتی نشانتان می‌دهند — تفاوت میان قبولی در آزمون و اداره کردن یک بازبینی است.

پاسخ پیشنهادی

محرک‌ها

D1. User-facing p95 < 2 seconds
D2. Zero loss of accepted transactions
D3. SOAP retirement within two years
D4. Different consistency semantics by operation
D5. Independent team delivery
D6. Operability of async flows

ریسک‌ها

R1. Slow SOAP violates latency.
R2. SOAP types across 23 classes increase migration cost.
R3. Inconsistent retries create duplicate effects/retry storms.
R4. Async flows are hard to troubleshoot.
R5. Making immediate-confirmation operations async
    may violate semantics.

فرض‌هایی که باید اعتبارسنجی شوند

A1. Which operations can legally/business-wise
    complete asynchronously?
A2. Can external operations be idempotent?
A3. Can persistence/queue meet no-loss requirements?
A4. Is 15-minute sync acceptable to all consumers?
A5. Can correlation IDs propagate across SOAP/REST/Kafka?

تصمیم‌ها و هزینه‌هایشان

۱ — مرز یکپارچه‌سازی قدیمی

Create a domain-oriented
integration port.
Keep SOAP-generated types
inside legacy adapters.

مزایا: محلی شدن مهاجرت، کاهش جفت‌شدگی با فروشنده، گذار آسان‌تر به REST.

هزینه‌ها: تلاش مهاجرت، کد نگاشت، لایه انتزاعی اضافی.

۲ — ناهم‌زمانی انتخابی

Use durable async
synchronization only where
business semantics allow
delayed confirmation.

مزایا: حفاظت از تأخیر، جداسازی زمانی، بافر کردن خطا.

هزینه‌ها: سازگاری نهایی، مدیریت تکرار/تلاش مجدد، رصدپذیری دشوارتر.

۳ — مفهوم مشترک تاب‌آوری

timeouts
retry eligibility
retry limits
backoff/jitter
idempotency
circuit-breaking criteria
metrics

مزایا: رفتار خطای یکدست، کاهش طوفان تلاش مجدد، عملیات آسان‌تر.

هزینه: حاکمیت و مدیریت استثناها.

سناریوهای کیفی

کارایی

Source:      Interactive user
Stimulus:    Submit operation
             whose external sync
             may be delayed
Environment: Peak load
Artifact:    Application +
             integration subsystem
Response:    Persist transaction
             and acknowledge
             without slow SOAP
Measure:     p95 < 2 seconds

قابلیت اطمینان

Source:      SOAP provider
Stimulus:    Provider unavailable
             30 minutes
Environment: Production
Artifact:    Delayed-sync workflow
Response:    Accepted transactions
             remain durable and
             retry per policy
Measure:     0 accepted
             transactions lost

قواعد معماری

1. SOAP-generated types only inside legacy adapters.
2. Every outbound remote call defines a timeout.
3. Retries only for classified transient failures
   and are bounded.
4. Async messages carry correlation IDs.
5. Domain code cannot depend on vendor/transport classes.

تابع تناسب زمان اجرا

هر شب:

2. Submit 1,000 delayed-sync transactions.
3. Verify user-facing p95 < 2 s.
4. Restore provider.
5. Verify all accepted transactions synchronize.
6. Verify duplicate business effects = 0.
